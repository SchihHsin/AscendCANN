## 二、真实任务回顾

- **最近一次任务与完成标准：**算子开发；功能没有错误，性能达到要求。
- **不同 AI 的分工：**较弱的模型用于对话，Coding 使用较好的模型。
- **多 Agent 协作：**开多个对话。
- **任务时间分配：**图中只有问题，未记录回答。
- **多任务管理：**使用默认方式；一个对象正在修改时，另一个就没办法操作。
- **查找多轮对话中的有效信息：**不太好找，没有搜索功能。曾让 Agent 跑过一版数据；之后想找，只能手动往上翻。
- **任务过程：**先把需求描述、功能和目标给 Agent，让它设计方案并形成文档；用户检查并纠正错误、选一个最优方向，然后让 Agent 开发。
- **可回看的材料：**图中只有问题，未记录回答。

## 三、AI 如何参与任务

- **AI 帮助的步骤：**各步骤都有参与；选方案时人的参与较多。
- **没有 AI 时的做法：**人工完成。
- **访问官方文档、社区或 Sample 的时机：**给 AI 提供示例，一般在任务过程中用于纠错。
- **AI 找到官方知识来源仍无法解决问题的原因：**模型能力不够。

## 四、人何时介入

- **AI 卡住或反复报错的情况：**语料比较少。
- **接手方式：**先换模型，再给新的线索，例如之前的测试结果。
- **依赖经验的判断：**常见 API 的使用方式。
- **昇腾等专有技术场景的缺口与 Skill：**需要昇腾架构知识；性能优化最好提供 Skill。官方已有一些 Skill，但强约束较多、比较耗 Token，例如强制完成若干步骤，其中有些不必要。算子开发时会强制开多个子进程跑同一份数据集，要求所有结果都通过才合格；受访者认为跑一次即可。
- **一次关键转折：**思考过程中用了错误的环境，之后补充了信息。
- **改变问法、模型、工具或资料：**补充资料、制定方案。
- **答案参考来源：**希望看到来源，以确认真实性。早期很多答案是编的；希望在结果后附上参考来源。

## 逐字稿补充（ASR 校订）

以下补充手记未充分记录的流程与判断；时间为转写文件时间，按语义整理，不作为逐字引文。

- **算子任务与多模型分工（01:18:14–01:20:35）：**算子完成标准是功能正确、性能达标。较弱模型用于对话或并发设计，较强模型用于写代码；会在同一客户端开不同窗口，让不同模型检查同一任务。
- **方案到实现（01:23:29–01:28:21）：**先给需求、功能和目标，让 AI 形成方案文档；本人检查、纠错并选方向后再开始开发。过程中会根据前一步的数据让 AI 分析原因，并比较 benchmark 基线与改动后的性能；仍会检查实现代码和测试脚本。
- **错误恢复与性能优化（01:31:33–01:41:04）：**发现错误环境会及时补充环境信息；模型能力不足或语料缺少时，会换更强模型，再提供此前测试结果。受访者认为算子性能优化应给出明确 Skill / 优化方向；官方流程若强制多步或对同一数据集开多个子进程，可能增加 Token 消耗，简单任务可以缩短流程。
- **结果证据（01:42:15–01:50:39）：**希望答案附来源链接。验收时看实际用例、输入规则、执行结果及最终值；若没有可查看的中间数据，会怀疑结果是编造的。对于特定算法，会重点核对代码是否正确实现公式。
- **学习与知识沉淀（01:58:21–02:17:29）：**学习多由具体任务触发；会把找到的资料交给 AI 阅读，并希望 AI 帮忙规划路线、解释知识、生成图表。受访者认为真正掌握仍要自己看原理、做实践；希望对话检索和知识沉淀更方便。
