# AI Coding 中，开发者何时把工作交给 AI，又何时接回来？

## 一、研究目的与材料范围、受访者概况

本研究追问一个具体动作：当 AI 给出下一步时，开发者凭什么让它继续？我们按先后顺序梳理六人的任务，再对照三种时刻：人把什么交出去，什么信号使人介入，最后由谁用什么证据作判断。学习部分另问：即使任务已经推进，开发者能否解释原因并自己再做一次？

**材料盘点。** 完整读取指定目录的 8 份 Markdown。《AI-Coding访谈提纲》包含补充提纲、原版问法与任务回放记录表；《昇腾学习及Agent场景用户访谈提纲-30分钟精简版》明确以回忆和口述为主，学习影响按需追问。其余六份为具名访谈记录，逐一列于下表。六人均称每天使用 AI Coding，这批材料适合比较熟悉工具后的做法，不能推断初用者或整个行业的分布。

## 二、两类典型角色的用户画像与旅程

### 高校学生｜王鹤锦：先确定实验值得做，再决定谁写代码

实验室里要解释的是跨视角定位的方差问题。王鹤锦先读论文，与老师讨论方法，才把可以快速试验的问题交给 AI。他的决策权体现在两处：要验证哪条假设，以及实际加进模型的模块是否符合原意。即使额度充足，这两个判断仍需要他理解研究目标。记录写道：“先看论文、想方法和方案，再和 AI 讨论可不可行”（王鹤锦，手记摘录）。在另一段学习 vLLM 的经历里，他主动保留逐点实现的工作。学生身份下有研究、工程与学习三种不同目标。

**主旅程（王鹤锦的研究经历）**　发现定位方差大 → 查论文、同老师讨论白化思路 → 与 AI 讨论可行性，让它写短探针 → 方向可行后细化机制，交给 AI 实现 → 本人检查核心逻辑是否符合方法。记录还描述了实验里模块加错时，他会指出具体误解，再让 AI 修改。此处作为可能回到实现阶段的分支；材料未证实该错误出现在同一次白化实验，也未给出白化前后的指标。对照学习分支：学习 vLLM → AI 列技术点和计划 → 本人逐点编写 → 借实现理解结构。（王鹤锦，01:44:01–01:47:50、01:51:38–01:53:52、02:21:22–02:30:44）

**组内差异。** 梁淼城做后端 Demo 时，将任务拆到模块接口再审查；徐立桂跑算子会后台启动、约每五分钟查看进度，拿回结果再对 baseline。他们都可能比一次课程学习更关心工程产出。徐的手记把地图、算子和知识库连续记载，三者不拼接成一次项目。（梁淼城，手记“任务过程”；徐立桂，01:44:41–01:52:41、01:53:13–02:03:58）

### 企业员工｜王伟：自己对算子结果负责，把实现交给 AI 后仍持续读代码

王伟在 IDE 中开发算子，按一个项目一个平台组织工作。较长的前置工作是写详设、找 API 链接，避免 AI 猜接口。难处在于一个功能涉及多个 API 配合，单份文档只能回答局部问题。他把代码段引回对话，告诉 AI 怎样改；功能成立后，还要处理多余封装和变量传递。按其个人估计，AI 执行与人工审查交替约占 70%，不能外推为六人的时间分配。（王伟，手记“任务时间分配”；01:41:02–01:45:45、01:52:12–01:55:20）

**主旅程（综合王伟对算子开发的回顾）**　定义功能、精度和性能要求 → 将 API 链接写入详设，交给 Cursor → AI 出初版，本人读代码、引用问题段反馈 → 精度久调不通，展开已做尝试、停止原方向，查官方思路后重定向 → 用 CPU golden 的最大／平均相对误差看精度，再将性能与改动前基线比较。功能可用后还可能继续清理结构。记录形容精度反复调不通像“左右脑互搏”（王伟，手记原词；验收见 01:59:15–02:07:14）。王伟也使用自建的方案文档 Skill，但本次算子最终是否更新了它，记录未说明。

**两个边界案例。** 彭椒的测试脚本可以让服务器反馈驱动多轮自动修正，人工复跑集中在交付前；郑雨豪先让 AI 写方案文档，再亲自选方向，验收会下探中间值和公式。两人帮助界定王伟画像的适用范围：当反馈可由机器直接读取时，人不必像王伟那样在每轮代码修改间介入。（彭椒，01:29:01–01:33:32、01:49:56–01:50:19；郑雨豪，01:23:29–01:28:21、01:42:15–01:50:39）

**访谈原声（ASR）**

> “我会和他对话，让他指导，但是代码就是我会自己写。”——王鹤锦，02:21:22

> “这一版可能是精度是通过的，但是性能不达标，然后这个时候的话就要去人工去审查。”——王伟，01:36:16

## 三、跨案例发现：人机分工、交接、判断、验证、失败恢复

|任务回放|第一次交接|触发人工判断的信号|人接手以后，工作交到哪里|
|---|---|---|---|
|梁淼城 · 后端 Demo|AI 查库、估算代码量并出架构；人确认后建空骨架|模块完成，接口或函数形态偏离预期|看核心逻辑，要求分模块检查；另一次 910B 排障中，AI 未找到线索，本人转浏览器查到版本线索|
|王鹤锦 · 方法实验|人和导师确定值得试的方法，AI 写短探针|方向可行才投入完整实现；若模块含义被误解则检查代码|指出误解交回 AI；当目的是学习，改为本人实现|
|徐立桂 · 算子生成|通过环境后台运行生成任务，定时查看|结果与 baseline 的对照决定是否值得继续；提示含糊或实现偏离是另一类信号|实现偏离时回到上一版本、改写提示与上下文；开放问题上的多 Agent 讨论也可能无法收敛|
|王伟 · 算子开发|详设与 API 链接交到 IDE，AI 出初版|代码段不合理可立即反馈；精度久调不通则暂停当前尝试|人找官方解法、给出新线索；用误差和性能对照验收，再审结构|
|彭椒 · 测试脚本|给内部工具目标，由服务器返回驱动修改|业务输出不合理，或工具彻底停摆|前者改提示，后者换工具；交付前看源码和 Pass，再手动跑一次|
|郑雨豪 · 算子优化|AI 列候选，人纠偏选定后再实现|环境用错、看不到中间数据，或实现与公式不符|分别补环境、要求可查用例和中间值、核对代码；能力不足时换模型并附上次测试结果|

**交出的首先是一项有边界的工作。** 梁淼城把“确认后建项目骨架（空文件），每做一个模块就检查一次，主要看接口”作为检查节奏（手记摘录）。骨架把一次大生成拆成可审查的交付。王鹤锦用探针解决的是方法值不值得实现，彭椒给测试方案后让 AI 批量生成同质用例，新场景仍由本人把关。三种做法都减少了当下要判断的范围，交接物分别是接口、实验信号和测试方案。（王鹤锦，01:51:38–01:53:52；彭椒，01:38:36–01:39:36）

**“看过程”有不同的时机。** 徐立桂看后台作业是否结束；梁淼城在模块边界看接口；王伟在精度长时间不改善后才展开 AI 的尝试。一次看任务存活，一次看结构，一次看排错是否陷入重复。同样的“进度可见”无法替代这三种判断。（徐立桂，01:44:41–01:52:41；梁淼城，手记“任务过程”；王伟，01:52:12–01:55:20）

**验收证据随所担心的错误而改变。** 脚本会不会通过，可以再跑一次；算子是否算对，需要同一输入下的参考结果；优化有没有收益，需要改动前的基线；算法有没有照原意实现，还需看公式如何落到代码。郑雨豪在缺中间数据时会怀疑最终数值；王伟会在功能完成后继续清除层层传递的变量。因此“能运行”“数值正确”“速度改善”“以后能维护”是不同的判断。材料未记录团队签字或上线验收。（彭椒，01:49:56–01:50:19；郑雨豪，01:42:15–01:50:39；王伟，01:52:12–01:55:20、01:59:15–02:07:14）

**恢复动作取决于人认为哪里错了。** 目标理解错，王鹤锦指出加错的模块；条件用错，郑雨豪补环境和旧测试数据；实现方向错，徐立桂回退再提问；工具停摆，彭椒切换工具。梁淼城也会新开对话换模型，但在 CANN 版本问题上，突破口来自自己搜到的第三方页面。该页提供了线索，记录未交代升级后是否跑通。把这几条路径合成“失败就重试”，会遗漏人如何重定问题。（六人手记“人何时介入”；徐立桂，02:05:31–02:06:12；梁淼城，02:19:12–02:21:55）

**访谈原声（ASR）**

> “从接口看，就是一个接口，因为这个项目不大，所以有时间慢慢看。”——梁淼城，02:12:53

> “它使用了错误的环境，然后这边就可以及时去补充对应的这个信息”——郑雨豪，01:31:33

> “我一般会自己再手跑一遍”——彭椒，01:47:08

## 五、知识获取、学习路径、可信来源与知识沉淀

**先确定要回答哪一种问题，才有来源优先级。** 梁淼城做研究会追来源，做工程更信自己运行命令的结果。徐立桂核对 API 时先看开发包中的头文件和动态库，再看官方文档、第三方材料；她在判断的是当前安装物究竟提供什么。王鹤锦遇到第三方资料说法不一时，曾租卡、打印实际状态。彭椒的情境又不同：能搜到相似公开资料，内部业务约定却未必可访问，公开来源再多也无法替他判断内部规则。（梁淼城，02:23:05–02:40:27；徐立桂，01:53:13–02:03:58；王鹤锦，手记“可信知识来源”；彭椒，01:39:51–01:44:05）

**出现“找到了，仍然不会用”的时候，缺口可能在知识之间。** 王伟常把 API 链接放进详设，却仍要说明多 API 如何配合才满足功能。梁淼城对“找到官方知识来源仍无法解决问题”回答“没有”（手记原词）；他另述的版本排障是 AI 根本没检索到线索。一个是已有片段如何组合，一个是资料没有进入当前任务。郑雨豪认为来源链接能帮助确认真实性，但核验具体算法时仍会看公式。三者分别对应查得着、用得上和能核对。（王伟，01:41:02–01:45:45；梁淼城，手记“AI 如何参与任务”；郑雨豪，01:42:15–01:50:39）

**任务驱动的求知与主动学习有不同终点。** 徐立桂的手记原文为“听说，查，拉到本地，AI hack”；遇到问题再追问，根据回答决定下一步。王伟排错时要最相关知识，主动学时才想理清来龙去脉。王鹤锦最清楚地展示了掌握领域知识的过程：先请 AI 把 vLLM 拆成技术点和实现计划，把阅读对象缩小，随后亲自逐点实现。梁淼城以看过代码且能复现为学会的依据，并指出自动排错可能跳过对错误成因的理解。这些是自述的掌握标准，材料没有延迟复测或陌生任务迁移成绩。（王伟，02:19:26–02:27:39；王鹤锦，02:21:22–02:30:44；梁淼城，02:30:50–02:40:27）

**沉淀物取决于以后想找回什么。** 要找回讨论脉络，徐立桂筛选 Markdown 放入 Obsidian；要再次执行一套流程，王鹤锦把重复对话整理成 Skill；要让团队使用内部业务知识，彭椒指出 Skill 要随业务更新。梁淼城表示愿意整理 Skill，是意愿；郑雨豪希望能检索先前数据，是未满足的需求。不能将二者计作已经建立个人知识库。（徐立桂，02:37:55–02:39:35；王鹤锦，01:44:01–01:47:50；彭椒，01:39:51–01:44:05；梁淼城，02:30:50–02:40:27；郑雨豪，手记“查找多轮对话中的有效信息”）

**访谈原声（ASR）**

> “开发包里边有一些头文件，然后还有一些动态库什么的。”——徐立桂，02:03:17

> “除非我看过代码，然后确定自己能复现。我才觉得自己是学会的”——梁淼城，02:35:04

## 六、五条有证据支撑的研究发现

1. **目标会改变谁来写同一类代码。** 王鹤锦的手记摘录：“AI 可以快速验证、写探针，比较节省时间。”验证研究方法时让 AI 实现；学习 vLLM 时让 AI 列计划、自己逐点写。对照发生在同一个人身上，角色标签不足以预测其分工。（王鹤锦，02:21:22–02:30:44）

   原声（ASR）：“我需要很快的验证，那就直接让他做。然后我只是把核心逻辑看一看”——王鹤锦，02:21:22。 “我会和他对话，让他指导，但是代码就是我会自己写。”——王鹤锦，02:21:22
2. **可审查的中间物决定下一次交接时机。** 梁淼城手记摘录：“每做一个模块就检查一次，主要看接口。”郑雨豪先审方案文档才放行开发；彭椒允许服务器反馈推动连续修正，直到最终人工复跑。交接频率与是否存在可独立判断的接口、方案或运行信号有关。（郑雨豪，01:23:29–01:28:21；彭椒，01:29:01–01:33:32、01:49:56–01:50:19）

## 七、对设计的启发

以下是由发现引出的设计判断及可验证的问题，尚未经过原型测试。

|来自哪条发现|设计应支持的判断|可以怎样检验|
|---|---|---|
|① 研究验证与主动学习的分工会切换|同一项实现允许开发者决定这一步谁来写。学习时保留自己动手的机会；试验时可以直接委托|给同一人“快速验证方法”和“学会实现方法”两项目标，观察其交出和保留哪些步骤|
|② 以中间物交接|让交接停在有工程含义的位置，如一个接口、一份候选方案或一次服务器返回|开发者能否仅凭该处的证据说出“可以继续”或“需要改哪里”|
|③ 失败常源于错误前提|恢复时能辨认 AI 刚才依据的环境、假设和已试方法，并把改正后的前提交回去|在环境错配情境中，观察人能否识别错配、补入正确条件并避免重复尝试|
|④ 疑点决定证据|把引用、所用版本、输入、参考值和实测值放回到各自要验证的结论旁|分别给出“接口是否可用”和“精度是否正确”的问题，看开发者能否选对证据并解释理由|
|⑤ 找回、复用、掌握各有终点|按要取回的对象保留实验结果、可重复做法或原理与练习；允许记录业务条件和失效原因|间隔一段时间后，分别观察找回旧结果、在新版本重用流程、脱离原对话复现的表现|
