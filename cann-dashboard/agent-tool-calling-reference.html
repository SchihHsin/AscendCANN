REFERENCE · AGENT TOOL CALLING

真实 API 的共同机制：工具调用不是“指向能力卡”

模型先返回响应；只有响应包含工具调用时，应用侧才解析、校验并执行工具。工具输出作为中间消息回传模型，模型后续生成的 final response 才是开发者看到的最终交付。

跨平台共同循环

厂商字段名称不同，但“模型请求 → tool call → 应用执行 → tool result → 下一轮请求”是同一协议关系。

01 · INPUT任务与现场用户目标、代码、环境、历史消息
02 · REQUEST发送模型请求messages + tools / function schema
03 · RESPONSE模型返回响应final text，或一个 / 多个 tool call
04 · VALIDATE应用侧校验工具名、参数、权限与风险
05 · EXECUTE执行具体工具检索、外部连接、命令或委派
06 · MESSAGE回传 tool result携带 call_id / tool_use_id
07 · END最终响应模型基于工具结果生成答案
边界：知识库、MCP、子 Agent 是工具实现；tool_result 是发给模型的中间消息。二者都不是最终交付结果。

公开 API 字段对照

只保留决定流程走向的字段。不能把某一家 API 的专有字段直接写成跨平台通用节点。

OPENAI · CHAT COMPLETIONS

tool_calls / tool_call_id

assistant message 携带 tool_calls；应用执行后，以 tool message 回传对应 tool_call_id。

assistant.tool_calls[] → execute(name, arguments) tool.tool_call_id + content → next messages request
OPENAI · RESPONSES API

function_call / function_call_output

调用和输出是 response items；应用执行 function_call 后，以相同 call_id 回传 function_call_output。

response.output: function_call → execute(name, arguments) function_call_output + call_id → next response request
ANTHROPIC · MESSAGES

tool_use / tool_result

assistant content 出现 tool_use block；下一条 user message 放入关联 tool_use_id 的 tool_result block。

assistant.content: tool_use → execute(name, input) user.content: tool_result + tool_use_id → next messages request
DEEPSEEK / KIMI

OpenAI-compatible tool calling

公开接口沿用 tools、tool_calls、tool_call_id 结构；平台差异不改变“执行后回传再请求”的关系。

assistant.tool_calls[] → application executes tool tool.tool_call_id + content → next chat request

对报告 Workflow 的硬约束

必须画出的关系
  • 模型响应和工具执行之间有应用侧解析与校验
  • 能力卡只连接具体执行动作
  • 所有工具分支回到同一个 tool result 消息节点
  • tool result 回到下一轮模型请求
不能出现的表达
  • 把知识库、MCP 或子 Agent 画成最终结果
  • 把 tool_result 和 final response 画成两个 End
  • 用单一厂商的 stop_reason 代表所有 API
  • 让 Hook 长线穿过流程节点
