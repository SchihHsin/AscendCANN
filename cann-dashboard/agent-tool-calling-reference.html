REFERENCE · AGENT TOOL CALLING

真实 API 的共同机制：模型决策、客户端执行与结果回填

模型先返回响应；只有响应包含工具调用时，应用侧才解析、校验并执行工具。工具输出作为中间消息回传模型，模型后续生成的 final response 是候选交付；是否真正完成任务，还要由应用侧按目标、结果与验证证据验收。

机制图的证据口径

平台对照图同时记录公开协议、可复核运行机制和待验证假设，并用 H / M / L 清楚区分证据强度。

可画入机制图的两类事实

  • 实证·未公开：有可复核的一手运行证据、请求 / 响应记录、可审阅代码、可信技术材料或用户提供的接口资料支持。
  • 图中注明证据类型与来源位置；实证观察作为运行机制参与对照，并与官方 API 字段分层表达。
待验证内容的表达方式
  • 待验证假设：由结果或体验反推、尚缺可复核来源的内部策略，例如具体系统提示、模型选工具阈值、重试 / 并发调度算法。
  • 这类内容使用实验假设或虚线节点，并写明所需日志、抓包、源码或复现实验。
  • 平台能力排名由同任务集实测产生，机制图负责提出变量和假设。

跨平台共同循环

厂商字段名称不同，但“模型请求 → tool call → 应用执行 → tool result → 下一轮请求”是同一协议关系。

01 · INPUT任务与现场用户目标、代码、环境、历史消息
02 · REQUEST发送模型请求messages + tools / function schema
03 · RESPONSE模型返回响应final text，或一个 / 多个 tool call
04 · VALIDATE应用侧校验工具名、参数、权限与风险
05 · EXECUTE执行具体工具检索、外部连接、命令或委派
06 · MESSAGE回传 tool result携带 call_id / tool_use_id
07 · END最终响应模型基于工具结果生成答案
边界：知识库、MCP、子 Agent 是工具实现；tool_result 是发给模型的中间消息。二者都不是最终交付结果。API 层只分流 tool call 与 message / final，不负责判断业务任务是否完成。

公开 API 字段对照

只保留决定流程走向的字段。不能把某一家 API 的专有字段直接写成跨平台通用节点。

OPENAI · CHAT COMPLETIONS

tool_calls / tool_call_id

assistant message 携带 tool_calls；应用执行后，以 tool message 回传对应 tool_call_id。

assistant.tool_calls[] → execute(name, arguments) tool.tool_call_id + content → next messages request
OPENAI · RESPONSES API

function_call / function_call_output

调用和输出是 response items；应用执行 function_call 后，以相同 call_id 回传 function_call_output。

response.output: function_call → execute(name, arguments) function_call_output + call_id → next response request
ANTHROPIC · MESSAGES

tool_use / tool_result

assistant content 出现 tool_use block；下一条 user message 放入关联 tool_use_id 的 tool_result block。

assistant.content: tool_use → execute(name, input) user.content: tool_result + tool_use_id → next messages request
DEEPSEEK / KIMI

OpenAI-compatible tool calling

公开接口沿用 tools、tool_calls、tool_call_id 结构；平台差异不改变“执行后回传再请求”的关系。

assistant.tool_calls[] → application executes tool tool.tool_call_id + content → next chat request

Anthropic 专属流程图：字段与边界

用于报告新增页；只描述 Messages API 公开协议，不把客户端实现选择写成 Anthropic API 固有步骤。

公开协议直接规定
  • 请求含 messages，并可提供 tools 定义。
  • assistant 的 content 可以含一个或多个 tool_use block，包含 id、name 与 input。
  • stop_reason: tool_use 表示需要客户端执行工具；end_turn 是本轮 assistant 响应结束的一种结果。
  • 工具结果在下一条 user message 中以 tool_result block 回传，并以 tool_use_id 关联。
客户端如何实际处理一个 tool_use
  • 读取每个 block 的 id / name / input；按 name 匹配客户端已注册的函数、连接器或子流程。
  • 客户端可校验 input、权限与运行条件，然后把该 JSON 输入传给匹配实现；成功输出或失败信息都收集为结果。
  • 为每一个调用创建一个 tool_result block，令 tool_use_id = tool_use.id，并把所有结果放进下一条 user message。
  • 多个 tool use 是并行还是串行、错误是否重试，以及 MCP、Skill、Hook、子 Agent 是否参与，均是客户端实现策略。
  • 将 assistant 文本视为业务交付，或如何验收任务成功，也属于应用层。

Claude Code：方法约束的真实生命周期

本节描述 Claude Code Host 的产品实现，并与 Anthropic Messages API 协议字段分层记录。规则、能力描述、方法正文、委派上下文和强制门禁在不同时间进入不同作用域。

01 · START启动规则CLAUDE.md、无条件 Rules 与 Auto Memory 在会话启动时进入主 Context，负责持续行为指导。
02 · DISCOVER只暴露能力描述Skill 与 Subagent 的 description 进入主 Context，供模型选择；完整正文尚未加载。
03 · LAZY RULES按路径补规则嵌套 CLAUDE.md 与 path-scoped Rules 在读取匹配目录或文件时延迟进入 Context。
04 · SKILL调用后加载正文完整 SKILL.md 作为消息进入当前 Context 并跨轮保留；allowed-tools 只授权当前调用轮次。
05 · DELEGATE创建独立 ContextAgent 或 context: fork 启动 Subagent；其 system prompt、配置的完整 Skills、Tools 与 Permission 独立。
06 · ACTION GATE动作前强制门禁PreToolUse 可 allow / deny / ask / defer、改写 input 或加入 Context；随后仍受权限设置约束。
07 · STOP GATE阻止过早结束Stop / SubagentStop 可返回 block + reason；reason 进入下一轮，Agent 继续工作。
Skill 采用“描述常驻、正文按需”的两阶段加载
  • 普通 Skill 默认只有 description 常驻，完整正文在用户或模型调用时加载。
  • disable-model-invocation: true 将 Skill 设为用户显式调用模式。
  • 相同正文重复调用复用已加载内容；参数或动态注入改变时追加新内容。
  • 自动压缩后，最近调用的 Skill 可按预算重附：每个最多保留 5,000 tokens，合计 25,000 tokens；较旧 Skill 可能被丢弃。
连续约束由多种机制协作形成
  • CLAUDE.md / Rules 提供持续指导，遵循效果受规则冲突与模型选择影响。
  • Skill 把任务方法按需带入当前或 forked Context；Subagent 隔离上下文与权限。
  • Skill frontmatter Hook 调用后默认可在后续会话中持续；Subagent frontmatter Hook 只在该 Subagent 生命周期存在。
  • Permission、同步 PreToolUse、Stop 与 SubagentStop 提供确定性阻断；异步 Hook 用于非阻断型后续处理。
比较边界：Codex、Cursor、OpenCode 等也有 Context 规则、Skill / Agent 或 Hook 类能力。Claude Code 公开材料能确认的是它对加载时机、作用域和生命周期事件的接口定义更细；这是否更稳定地减少偏航，必须用同任务、同模型 / 预算 / 权限 / 环境的 Benchmark 验证。

对报告 Workflow 的硬约束

必须画出的关系
  • 模型响应和工具执行之间有应用侧解析与校验
  • 能力卡只连接具体执行动作
  • 所有工具分支回到同一个 tool result 消息节点
  • tool result 回到下一轮模型请求
  • final / message 之后仍需应用侧验收任务完成条件
不能出现的表达
  • 把知识库、MCP 或子 Agent 画成最终结果
  • 把 tool_result 和 final response 画成两个 End
  • 用单一厂商的 stop_reason 代表所有 API
  • 让 Hook 长线穿过流程节点
  • 把 final response 直接等同于任务已经验收通过

MCP 与子 Agent 的关系

二者没有固定前后顺序：Host 根据 tool name 选择执行器；子 Agent 内部可以再次发起自己的模型与工具循环。

MCP 是连接协议与执行适配器

AI 应用作为 MCP Host，为每个 Server 建立 MCP Client。请求构造前可通过发现 / tools/list 获得工具定义；模型选中该工具后，Host 再通过 Client 调用 Server 的 tools/call。

Host discovers MCP tools → model request includes schemas → tool call selects MCP adapter → MCP Client → Server tools/call → result returns to Host

子 Agent 是嵌套的 Agent 运行循环

主 Agent 将一个有边界的子任务委派给子 Agent。子 Agent 拥有独立上下文、指令与工具权限；它可以只靠模型完成，也可以继续调用本地工具或 MCP，最后把子任务结果回传主 Agent。

Main Agent delegates task → Subagent starts its own loop → optional local / MCP tool calls → subagent result → main Agent tool_result
