# Ascend Studio PC｜三大场景用户测试提纲与任务书

版本：2026-11-04 · 探索性原型测试
测试对象：<https://schihhsin.github.io/AscendCANN/ascstudio-pc/>
结构依据：PC Demo 的三大用户旅程场景及其 16 个设计点

## 1. 测试目的

- 看用户是否理解并愿意继续三段旅程：**让学习贴合当前需要与现有基础**、**在开发过程中掌握知识**、**让学习随时继续**。
- 按原型设计点观察入口发现、操作预期、内容衔接、状态理解和继续意愿，不以具体示例业务或任务名称划分研究结论。
- 每个场景结束后分别评价该场景的 UI 满意度；体验完全部场景后，对 16 个设计点逐项进行 Kano 需求分析。
- 本轮是小样本探索，用于发现理解断点、体验阻塞和需求倾向，不用于估算总体满意度或用户比例。

## 2. 参与者与场次

- 建议 8 人，约 110–120 分钟/人。招募可覆盖 CANN 学习者、AI / 应用开发者、算子 / CANN 开发者、高校教学者，以及有跨设备学习习惯的用户；角色允许重叠。
- 每位参与者体验全部三个场景。按六种场景顺序轮换分配，尽量平衡先后顺序影响；8 人时前六人各用一种顺序，后两人补到人数较少的顺序。
- 每个场景结束后立即填写该场景的 UI 评分；全部场景体验完后填写 Kano 问卷，避免提前看到设计点标题影响任务探索。
- 预先准备 Ascend Studio PC 入口、稳定网络、计时器、场景顺序表、记录表和备用录屏方案。仅在参与者同意后录音 / 录屏；使用参与者编号，不记录姓名或无关个人信息。
- Kano 问卷包含 16 个设计点的成对题，建议预留约 20 分钟。

## 3. 主持人流程（约 110–120 分钟）

| 时间 | 环节 | 主持人动作 |
|---|---|---|
| 0–5 分 | 开场 | 说明今天评估的是体验，不是参与者能力；征求记录 / 录制同意。 |
| 5–10 分 | 背景 | 了解参与者的学习、开发和跨设备使用习惯，不先介绍设计点。 |
| 10–28 分 | 场景 01：学习 | 约 14 分钟自由探索；结束后用约 4 分钟填写该场景的 UI 评分。 |
| 28–53 分 | 场景 02：开发 | 约 21 分钟自由探索；结束后用约 4 分钟填写该场景的 UI 评分。 |
| 53–84 分 | 场景 03：移动续学 | 约 27 分钟自由探索；结束后用约 4 分钟填写该场景的 UI 评分。 |
| 84–104 分 | Kano 问卷 | 按三大场景顺序完成 16 个设计点的“提供 / 不提供”成对题。 |
| 104–114 分 | 回顾 | 比较三段旅程，追问最有价值、最难理解和最想调整的设计点。 |
| 114–120 分 | 缓冲 | 补充记录、回答参与者问题并结束。 |

如果场次需要压缩，优先缩短回顾和缓冲；三个场景的首次探索、场景 UI 评分及 Kano 问卷都要保留。超时或未触达的设计点记为“未观察”，不要由主持人补演。

## 4. 开场话术与主持规则

### 开场话术

> 谢谢你参加。今天会体验 Ascend Studio PC 中的三段用户旅程。我们想了解页面是否容易理解、哪些设计点对你有帮助；测试的是体验，不是在评价你的能力。请按你觉得自然的方式操作，并说说你在找什么、预期会发生什么。你可以随时暂停或跳过问题。
>
> 这是交互概念 Demo，部分内容和状态由预设演示驱动。移动端、通知和经验回流等流程用来讨论交互方向，不代表真实服务、模型或 NPU 已接通。我们不会提前讲页面应该怎么操作。

### 主持规则

1. 每个场景只读出对应的“朗读给参与者”文字；不要念设计点清单或指出按钮名称。
2. 用户停顿时先留出约 10 秒；再中性地问：“你现在在找什么？你觉得下一步会发生什么？”
3. 用户问“应该点哪里”时回答：“请按你认为自然的方式继续；如果拿不准，也可以告诉我你期待什么。”
4. 不替用户完成操作、不纠正判断。记录实际动作、停顿、求助和原话；研究者解释单独记录。
5. 场景结束后再填写该场景 UI 评分。Kano 问卷放在三个场景结束之后。
6. 记录用户未触达的设计点与跳过原因，不把未观察写成“用户不需要”。

## 5. 三大场景与参与者任务书

参与者只看每个场景的“朗读给参与者”部分。设计点编号、观察点与完成判断留给主持人。

### 场景 01｜让学习贴合当前需要与现有基础

**朗读给参与者**

> 你想继续学习一项和当前目标有关的 CANN 知识。请看看这个工作台能否帮你决定下一步，并把学习内容调整成适合自己的安排。试着沿着学习内容继续到练习；遇到不明白的地方，就按你自然的方式提出疑问。最后告诉我，你是否愿意按这个安排继续学，以及还有什么没弄清楚。

**主持人观察点（不读出）**

| 编号 | 原型设计点 | 观察重点 |
|---|---|---|
| S1.1 | 基于当前进度推荐下一步 | 用户能否理解建议和当前目标的关系，是否愿意查看或继续。 |
| S1.2 | 和 AI 一起调整学习路径 | 用户是否能表达基础、目标或时间条件，并判断生成的路径是否可接受、可修改。 |
| S1.3 | 共创路径连接理解与实践 | 用户能否从讲解继续到练习、结果核对，并知道下一步是什么。 |
| S1.4 | 框选内容，直接指着说 | 用户能否发现对具体内容提问的方式，并判断问题是否带着足够上下文。 |

**完成判断**：用户能说明是否愿意继续这条学习旅程，指出至少一个有帮助的设计点或一个尚未解决的问题。记录各设计点是否自然触达，不要求用户说出原型标题。

### 场景 02｜在开发过程中掌握知识

**朗读给参与者**

> 你正在处理一个原因还不明确的开发问题。请先找到能帮助你理解判断依据的材料，再试着在一个可对照的副本里做修改。假设问题已经处理完，继续看看你会怎样保存经验、整理成可分享的内容，以及选择后续去向。最后告诉我，你觉得哪些步骤适合放在同一个开发过程里。

**主持人观察点（不读出）**

| 编号 | 原型设计点 | 观察重点 |
|---|---|---|
| S2.1 | 打开图解看懂判断依据 | 用户如何找到图解，是否理解图解与当前问题 / 对话的联系。 |
| S2.2 | 在示例副本里动手修改 | 用户能否识别这是可编辑副本，是否知道原始内容如何保留与对照。 |
| S2.3 | 处理完成后回流经验 | 用户能否理解经验回流入口为何出现、何时适合使用。 |
| S2.4 | 把处理过程整理成社区经验 | 用户是否知道要整理哪些上下文、尝试和验证信息，是否愿意继续补充。 |
| S2.5 | 把经验带到更多平台 | 用户能否理解不同渠道的预览与发布边界，是否知道下一步会发生什么。 |

**完成判断**：用户能用自己的话描述一条从理解依据、尝试修改到整理经验的路径，并指出其中至少一个不确定或需要真实证据的环节。

### 场景 03｜让学习随时继续

**朗读给参与者**

> 你在电脑上看到一条有用的知识，但现在没有时间细看。请试着把它留到稍后，在手机场景里继续阅读；再告诉我你如何标记已经理解或还想回看的内容。之后看看你能否安排定期回访，以及在没有当前任务时如何发现新的知识。

**主持人观察点（不读出）**

| 编号 | 原型设计点 | 观察重点 |
|---|---|---|
| S3.1 | 从电脑端的一条回答，接上手机里的下一步 | 用户能否从当前电脑任务保存知识，并理解即时查看与稍后回访的区别。 |
| S3.2 | 电脑端选“现在看”，微信列表收到同一条知识 | 用户能否辨认通知来源，确认电脑端内容和移动端消息是同一条。 |
| S3.3 | 手机短读卡，把一个知识点拆成几分钟 | 用户能否快速找到重点、完成理解检查，并标记兴趣或疑问。 |
| S3.4 | 看懂后回到电脑，理解状态也跟着回来 | 用户是否注意到跨设备状态变化，能否回到之前的学习或开发上下文。 |
| S3.5 | 把关注或存疑的内容，放进每周回访 | 用户能否选择主题、时间并理解订阅 / 通知边界。 |
| S3.6 | 每周一条重点资讯，再补两张个性化卡片 | 用户能否理解速览内容的组成，以及个人关注线索如何影响内容。 |
| S3.7 | 没有当前任务，也能主动发现下一点新知 | 用户能否通过搜索、分类或推荐继续探索，并理解发现内容如何进入后续回访。 |

**完成判断**：用户能说出知识如何从电脑延伸到移动端、如何标记理解状态，以及之后如何继续学习；记录任何断开的交接或难以理解的状态。

## 6. UI 界面满意度评分

每个场景结束后分别评分一次。所有题目均为 **1–10 分**：1 表示“非常不满意”，10 表示“非常满意”。评分按场景保存，不把三段旅程合并成一个总分。

- **品质美感**：视觉美观度、视觉舒适性。
- **简单易用**：信息理解性、易发现性、布局合理性、易学性、易操作性、防错与容错性。

问卷共 3 组场景评分，每组 8 项。请参与者依据刚结束的场景作答；不要比较其他场景后再回填。

## 7. Kano 用户需求分析

- Kano 问卷按三个场景分组，对 **16 个原型设计点**逐项提问。每个设计点需回答两问：“如果提供这项设计点，你会怎样？”和“如果不提供这项设计点，你会怎样？”
- 选项统一为：**1 我很喜欢、2 理应如此、3 无所谓、4 勉强接受、5 我很不喜欢**。
- 问卷入口：[Ascend Studio PC 三大场景评分与 Kano 问卷](./questionnaire.html)。每位参与者单独填写并使用编号；答卷下载为本地 CSV，不上传到网站。

### Kano 评价矩阵

行表示“提供该设计点时”的回答，列表示“不提供该设计点时”的回答。

| 提供 \ 不提供 | 我很喜欢 | 理应如此 | 无所谓 | 勉强接受 | 我很不喜欢 |
|---|---|---|---|---|---|
| 我很喜欢 | Q | A | A | A | O |
| 理应如此 | R | I | I | I | M |
| 无所谓 | R | I | I | I | M |
| 勉强接受 | R | I | I | I | M |
| 我很不喜欢 | R | R | R | R | Q |

- **M 必备型**：缺少时容易引发不满；**O 期望型**：做得越好越满意，缺少会不满；**A 魅力型**：有了会惊喜，缺少时通常不明显不满。
- **I 无差异型**：有无影响较小；**R 反向型**：用户倾向于不要这项设计；**Q 可疑回答**：成对回答矛盾，需要回看原话或理解情况。
- 按场景和设计点分别统计 A/O/M/I/R/Q 人数；最多的一类作为当前主类，并保留并列为“混合”。Q 单独检查，不强行归类。8 人样本报告人数和角色背景，不换算为总体比例。

## 9. 分析与输出

1. 先按三大场景汇总，再下钻到 16 个设计点；不把示例业务名称作为报告的主分组。
2. 对每个设计点分别记录是否触达、完成度、用时、主持帮助、路径偏差、原话和 UI 评分；把观察事实、参与者原话与研究者解释分开。
3. UI 评分按三个场景分别呈现 8 项的原始分布与中位数；小样本不据此推断总体满意度。
4. Kano 按“场景 × 设计点”统计 A/O/M/I/R/Q 人数；并列时标为混合，不能因样本少将人数表述为总体比例。
5. 问题定级：**P0 阻断 / 误导**、**P1 主要摩擦**、**P2 次要摩擦**。每条结论回指场景、设计点、参与者编号、原话或观察事实。
6. 结论区分已观察行为、原型交互问题和待验证假设；预设演示状态不能作为真实模型、设备、通知或经验发布已运行的证据。
