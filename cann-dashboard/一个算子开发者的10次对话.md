# 一个算子开发者的 10 次对话

> 同一个人，平时在几个项目之间来回切。下面是他向 AI 助手提问的 10 段对话，提问方式没什么章法，想到哪问到哪。

---

## 1. 图像组留下的机器，容器里看不到卡

**他**：接了图像组的预处理项目，机器是上一任留下的，8 卡 910B。CANN 我重装了一遍，`npu-smi info` 还是报：

```
DrvMngGetConsoleLogLevel failed. return = 1
dcmi module initialize failed. ret is -8005
```

是不是得重装系统？

**助手**：先别重装，这跟 CANN 装没装好关系不大，是设备管理通道没起来。先看两个东西：`ls /dev/davinci*` 和 `lsmod | grep -i davinci`。

**他**：两个都空。/dev 下一个都没有，lsmod 也没输出。那我是不是驱动没装？我直接在容器里装一遍驱动行不行？

**助手**：不行。容器共享宿主内核，驱动是内核态模块，装不进去，`insmod` 也会失败。先确认你在不在容器里：`ls /.dockerenv`。

**他**：在容器里。

**助手**：那 `/dev` 空是正常的，设备节点要由 `docker run` 映射进来。加四个：

```bash
--device=/dev/davinci0 \
--device=/dev/davinci_manager \
--device=/dev/devmm_svm \
--device=/dev/hisi_hdc
```

**他**：我 `--privileged` 是不是就够了？

**助手**：不够。`--privileged` 只放开权限，不会凭空产生设备节点。没有 `--device`，容器里就是看不到。

**他**：加了，报 `open /dev/davinci_manager: Permission denied`。另外这个 manager 是干嘛的？跟 davinci0 有什么区别？

**助手**：`davinci0` 是算力设备，`manager` 是管理通道（查询、复位、监控）。所以缺它时报的是"设备管理接口初始化失败"，特别容易误判成装坏了。

权限问题：这些节点属于 `HwHiAiUser` 组，容器用户不在组里就只有 root 能用。启动时加：

```bash
--group-add $(getent group HwHiAiUser | cut -d: -f3)
```

**他**：能看到了。但 Health 是 Warning，驱动版本和板卡 Firmware 版本不一样。这个 Warning 我之前一直没管，会有事吗？

**助手**：有事。驱动和固件必须配套，错位时常见"能查到卡、能跑小算子，一上重负载就超时或者报设备异常"。

```bash
npu-smi info -t board -i 0
npu-smi info -t health -i 0
```

固件要用配套包整包刷，刷之前把版本号记下来。

**他**：晚上还有训练任务，只刷一张卡行不行？

**助手**：技术上能，但不建议。多卡固件不一致会在调度和集合通信上出问题。稳妥的是申请维护窗口，停业务、全部卡刷到同版本、`npu-smi info` 全绿再恢复。

**他**：行。对了，`/var/log` 下面那一堆 ascend 的日志是干嘛的？我一直没敢删。

**助手**：那是 `plog`，host 侧运行日志，排障时有用，别删。想看细节可以调 `ASCEND_GLOBAL_LOG_LEVEL` 再复现一次。它跟 device 侧日志是两回事，后者要用 `msnpureport` 导。

**他**：那这些东西我每次都得手动查一遍？有没有个脚本。

**助手**：可以封一个，按依赖顺序查，失败就退出：

```bash
#!/bin/bash
set -e
npu-smi info | head -5                                    # 设备
test -n "$ASCEND_HOME_PATH"                               # toolkit
test -f "$ASCEND_OPP_PATH/vendors/config.ini" || echo warn # opp
head -3 /usr/local/Ascend/driver/version.info              # 驱动
```

**他**：我们 CI 每次拉新容器跑测试，环境老不一致，这个能放进去吗？

**助手**：能。但先分清：驱动/固件属于宿主机，靠 `--device` 和 `-v` 挂；CANN 和算子包属于镜像，版本号写进 tag，别用 `latest`。

**他**：那为什么驱动不能打进镜像，打进去不就一致了吗。

**助手**：驱动跟宿主机内核绑定，容器共享内核。打进去也没法加载，反而版本错乱。一句话：内核态跟机器走，用户态跟镜像走。

**他**：懂了，我先把晚上那波业务停了再说。

## 2. 换了新镜像，编译又过不去

**他**：新项目的镜像，`msopgen gen` 生成工程，`bash build.sh` 报：

```
fatal error: kernel_operator.h: No such file or directory
```

**助手**：先 `echo $ASCEND_HOME_PATH`，大概率是空的。

**他**：是空的。我 source 过 `set_env.sh` 啊，是不是这次 CANN 装坏了？

**助手**：不是。每个新 shell 都是新环境，你 source 的那个终端和跑 build 的不是同一个。`source ... && bash build.sh` 写一行里就行。

**他**：好。不过我先干了个事：把 include 改成绝对路径了，能编过。这样行吗？

**助手**：别这么干。换机器、换 CANN 版本就废，而且团队里每个人的路径可能不一样。改回 `#include "kernel_operator.h"`。

**他**：改回来变 `undefined reference to 'AscendC::...'` 了。这跟前面那个有关系吗？

**助手**：有，但不是同一个问题。这是链接阶段，说明 kernel 源码被当普通 C++ 编了。

**他**：等等，我 CMakeLists 里怎么知道哪个文件该给谁编？

**助手**：按目录和文件名约定：`op_kernel/` 下的 `*_kernel.cpp`、`*.asc` 给 ascendc 编译器；`op_host/` 下的 `*_tiling.cpp`、`*_host.cpp` 给 g++。不确定就看编译命令行：

```bash
cmake --build build -- VERBOSE=1 2>&1 | grep -E "ccec|g\+\+"
```

有 `--cce-aicore-arch=...` 的是 ccec。

**他**：我发现 ccec 报错信息特别难读，一堆模板，是我用法不对吗？

**助手**：不是你用法的问题，模板展开的报错就是这样。只看第一个 error，后面的基本都是级联。

**他**：编过了。顺嘴问一句，我算子叫 `AddCustom`，会不会跟内置 `Add` 撞？

**助手**：`AddCustom` 不撞，但算子类型名是全局唯一注册键。直接叫 `Add`、`Softmax` 就危险了——注册可能被覆盖，或者运行时查到内置实现，你以为跑的是自己的代码。

**他**：那会不会有人已经注册过 `AddCustom`？我在这个镜像里。

**助手**：查一下比较稳：`cat $ASCEND_OPP_PATH/vendors/config.ini` 看装了哪些 vendor 包，以及各自路径。重名的时候优先级高的会赢，很难查。团队前缀最省事。

**他**：装完了，但调用时说算子不存在。

**助手**：装成功和能被找到是两件事。先看 `$ASCEND_OPP_PATH/vendors/` 下有没有你的目录。

**他**：没有。

**助手**：`.run` 默认装到当前用户目录（`~/Ascend/...`），你的 `ASCEND_OPP_PATH` 指向 `/usr/local/...`。指定路径重装：

```bash
./custom_opp_*.run --install --install-path=$ASCEND_OPP_PATH
```

装完必须重新 source。

**他**：每次改一行都要重装一遍，太烦了。能不能不装直接跑？

**助手**：可以，kernel 直调：写个 `main.cpp`，直接 `<<<>>>` 调 kernel。

```cpp
add_custom_kernel<<<blockDim, nullptr, stream>>>(xGm, yGm, zGm, totalLength);
```

配合 CPU 调试还能先跑仿真。先直调跑通再打包。

**他**：直调是对的，装完就偏。

**助手**：kernel 一样，参数不一样。直调里 `totalLength` 是你手填的，打包后由 host tiling 算。打印对比一下：`printf("%d %d\n", blockIdx, totalLength);`

**他**：找到了，tiling 里 tail 没算对。

**助手**：那就对了。顺一遍链路：原型 → tiling → kernel → 编译 → 打包 → 上层调用，每步都有可验证的产物。

**他**：行，我先把这六步记下来。

## 3. 给图像组写的 scale，1000 个元素输出全 0

**他**：`{1,1024}` fp16 结果全对，`{1,1000}` 输出全 0。不报错，不崩。

**助手**：1024×2=2048 字节，1000×2=2000 字节。2048 是 32 的倍数，2000 不是。`DataCopy` 要求 32 字节对齐。

**他**：2000 不是偶数吗？偶数也不行？

**助手**：不是"偶数"的问题，是"32 的倍数"。fp16 要 16 个元素一组，fp32 是 8 个。

**他**：哦，那我这个 1024 的 case 是不是也危险？它只是碰巧对？

**助手**：对，碰巧。只要总长度不是 32B 的整数倍，就可能出错；1024 刚好是，所以没暴露。

**他**：那改 `DataCopyPad`。是不是所有地方都换成 Pad 就行？

**助手**：搬运可以全换，但计算不能直接拿补齐后的数据做归约——多出来的填充值会污染 sum、max。逐元素算子无所谓，归约类必须按真实长度处理。

**他**：我全换了，1024 那个 case 反而慢了 20%。

**助手**：主块本来就对齐，用 `DataCopy` 更快。只有尾块用 `DataCopyPad`：

```cpp
if (isTailBlock) DataCopyPad(...); else DataCopy(...);
```

**他**：那我 shape 要是有 100 万呢，尾块占比很小，是不是就无所谓了？

**助手**：对，尾块占比越小影响越小。真正难受的是几千到几万这种"不大不小"的 shape。

**他**：还有个事我先不问性能了——我怎么确认写回没踩到别人？

**助手**：留哨兵。输出 tensor 前后各留 64 字节，填固定魔数，跑完检查有没有被改。

**他**：魔数填什么好？0 行吗？

**助手**：别用 0，容易被"本来就初始化成 0"骗过去。用 `0x5A5A` 这种不像正常数据的值。

**他**：我试了，确实被改了。说明写越界。

**助手**：那就是 CopyOut 没对齐。`{1,1000}` 写回 2000 字节，非对齐写会覆盖相邻内存。CopyOut 也要用 Pad，它会把 dummy 自动丢掉。

**他**：改完哨兵没动了。不过我发现一个怪事：CPU 调试里 1000 一直是对的。

**助手**：仿真器逐字节搬，不关心 32B 对齐。真机 DMA 按块搬。所以仿真过、真机挂，先查对齐和容量。

**他**：那我以后是不是都得上真机验一遍？仿真就没意义了？

**助手**：仿真验逻辑（公式、边界、分支），真机验硬件约束。两层都要，只是分工不同。

**他**：行。我顺便把 1023 和 1 也加进用例了，跑出来 1023 果然也挂。

**助手**：对，1023 是典型的"差一个"。1 和 1023 这两个数能提前抓出大部分尾块问题。
## 4. 推荐组的 ReduceSum，多核偶发错

**他**：`blockDim=8`，结果偶发错，错的位置还不固定。重跑有时候全对。

**助手**：偶发、位置不固定，先按竞争类查。第一件事：`blockDim` 改 1，跑一遍。

**他**：单核是对的。不过我只测了小 shape，1×1024 那种。

**助手**：那不算数。小 shape 流水几乎不重叠，时序碰巧对。单核 + 全 shape 也要跑。

**他**：全 shape 也过了。那是不是硬件有问题？这台机器之前报过 Warning。

**助手**：先别怀疑硬件。看切分：把每核的 `[start, end)` 打出来，检查有没有重叠或者空洞。

**他**：打出来了，第 7 核的 end 是 1002，但 total 也是 1002，看着没问题。等等，第 0 核到第 6 核每核 125 个，7×125=875，最后只有 127……

**助手**：127 还是 125+2？如果最后几个元素落在两核之间，就会漏算或者重算。

**他**：哦，我总算明白了。我是 `perCore = total / blockNum`，余数没人管。但我 total 是 1002 啊，1002 除 8 不是整数？

**助手**：1002/8 = 125 余 2。这 2 个元素就没算。改成余数摊到前几个核：

```cpp
int64_t perCore = total / blockNum;
int64_t tail    = total % blockNum;
int64_t start   = blockIdx * perCore + std::min<int64_t>(blockIdx, tail);
int64_t len     = perCore + (blockIdx < tail ? 1 : 0);
```

**他**：改完还对吗？我加了 `SyncAll()` 之后更奇怪了，有时候直接挂住。

**助手**：挂住一般是对不上：循环里有的核进了 `SyncAll`、有的没进，或者次数不一致。检查一下：所有核是否都走了同样次数的同步。

**他**：我是先写 workspace 再 SyncAll，然后 0 号核汇总。应该都走了吧。

**助手**：那再看两件事：workspace 有没有清零，同步基地址有没有设。基地址没设的时候，各核可能同步的不是同一个东西。

**他**：workspace 没清零，我以为是新分配的。基地址……这个我确实没设。

**助手**：两个都补上。首核先清零，或者每核写之前先写 0。

**他**：好。顺便问一句，workspace 到底是谁分配的？我一直以为是框架给的。

**助手**：你自己申请，或者由上层把指针传进来。长度要按 `blockNum × 每核槽位` 算，别只给一个 float 的大小。槽位按核独立：

```cpp
workspace[blockIdx * sizeof(float)] = partialSum;
```

**他**：那为什么错的位置不固定？如果是漏算，应该每次都错同一个位置吧。

**助手**：漏算是固定的，竞争是随机的。你这个 case 两种都有：余数漏算是固定的，但 SyncAll 之前读到别人没写完的 workspace，是随机的。所以现象混在一起。

**他**：怎么区分？

**助手**：打每核的部分和。同一输入跑 5 次，如果部分和每次不一样，是竞争；如果部分和稳定但总和不对，是汇总逻辑。

**他**：我跑了，部分和每次都不一样。所以是竞争。

**助手**：那就先把清零和基地址补上，再跑。还不对，就检查有没有核在读别人的槽位。

**他**：clear 了，跑 20 次都一致。不过我发现 7 号核基本没干什么活，这个能优化吗？

**助手**：那是尾块分配问题。余数摊到前几个核已经好一些；再进一步可以动态 blockDim，total 小的时候直接减核数。

**他**：先不管了，能跑对就行。我把这个 case 写进测试了。

## 5. 模型组的 Softmax，FP16 差一点点

**他**：Softmax fp16，MARE 3.2e-3，验收线 1e-3。fp32 就完全过。

**助手**：三处容易放大误差：减 max、sum 的累加精度、最后的除法精度。先只改 sum 试。

**他**：我把 sum 改成 fp32 了，掉到 1.8e-3。还差一截。

**助手**：再看 exp 之前有没有减 max。

**他**：减了啊，我一开始就减了。

**助手**：贴一段给我看看。

**他**：

```cpp
Exp(xLocal, xLocal, len);
ReduceMax(maxVal, xLocal, len);
... 减 max ...
```

**助手**：顺序反了。你是先 exp 再找 max。要先找 max，减完再 exp。

**他**：哦……那就是 `x - max` 之后再 exp。不过我不是很确定，这个减 max 到底是为了防溢出还是为了精度？我一直当成防溢出。

**助手**：两个作用都有。防溢出是必须的；精度上，减完之后结果落在 (0,1]，是 fp16 表示最密的地方。不减的话，exp 结果可能挤在稀疏区间，尾数不够。

**他**：明白了。改完 1.1e-3。这个算过还是不过？差一点点。

**助手**：看你们的验收口径。如果验收就是 1e-3，那就是不过。建议再压一点，别卡在边界上。

**他**：我看报告里还有 MERE，那个也要看吗？

**助手**：要。MARE 高但 MERE 低，说明少数元素炸了（边界值、除零附近）；两个都高才是整体精度不足。只报一个数会误导优化方向。

**他**：那我要是把中间量都换成 fp32，能压到多少？

**助手**：通常能到 1e-3 以下。但注意只转累加器和 max，别整块转。

**他**：为什么？全 fp32 不是更稳吗。

**助手**：UB 占用翻倍、Vector 吞吐下降，tile 只能变小。性能会掉不少。

**他**：行。我试了，9e-4，过了。但性能掉了 8%，这个值得吗？

**助手**：看这个算子是不是瓶颈。Softmax 在推理里通常是热点，8% 可能不能接受。折中方案：只在 fp16 输入、长序列时才走 fp32 累加。

**他**：还有个事，我发现误差集中在输入很小那一段，大值区反而很准。

**助手**：相对误差在小分母处放大。分母加 eps，或者用 `max(sum, eps)` 而不是 `sum + eps`——后者会引入系统性偏差。

**他**：那 eps 取多少？

**助手**：看数据分布，一般 1e-6 到 1e-5。但更该做的是把这段单独用 fp32 算。

**他**：行，先这样。我把这组输入固化成用例了。

## 6. 同事留下的一段 kernel，里面手写了 SetFlag

**他**：接手一段代码，`CopyIn` 和 `Compute` 之间手写了 `SetFlag`/`WaitFlag`。文档里说 `EnQue/DeQue` 已经做同步了，这段是不是可以删？

**助手**：看 buffer 是从 `TQue` 拿的还是 `TBuf` 拿的。

**他**：TBuf。因为这个 buffer 要复用做中间计算。

**助手**：那就不能删。`TBuf` 只保证分配，不保证顺序，你那两个 flag 是必需品。

**他**：那我能不能把这段直接重构成 TQue？反正也是复用。

**助手**：能，但先别。重构范围大，你现在还没完全搞清同步关系，容易把小问题变成大问题。

**他**：行吧。但我看这段代码里 EnQue 和 SetFlag 同时存在，是不是有一个多余的？

**助手**：看它们同步的是不是同一对生产者/消费者。如果是同一对，确实冗余；如果不是（比如 EnQue 管 CopyIn→Compute，SetFlag 管 Compute→CopyOut 之外的某段），就都得留。

**他**：说实话我一直不太理解，为什么 Ascend 要搞这么多同步原语？CUDA 里一个 `__syncthreads` 就完了。

**助手**：因为 CUDA 的同步是"线程级屏障"，你只有一个执行单元在跑；Ascend 是几条独立流水（MTE、V、Scalar）在并行，同步要精确到"哪条流水等哪条流水"。粒度更细，所以原语更多。

**他**：那 `PipeBarrier` 和 `SetFlag` 到底什么时候用哪个？

**助手**：`PipeBarrier` 是同核内所有 pipe 的顺序屏障，正确但慢；`SetFlag/WaitFlag` 是跨 pipe 的点对点事件，精确但容易出错。调试用前者，优化用后者。

**他**：eventId 有多少个？我这段代码用了 0 到 3。

**助手**：数量有限，而且框架内部也在用。手写的时候跟框架撞了，会出现"偶发读到旧数据"，特别难查。能用队列就让队列管。

**他**：那我这段用 0 到 3，会撞吗？

**助手**：可能。要么统一交给队列，要么查清楚框架在这段用了哪些。没有把握的话，最稳的是保持现状别动。

**他**：我改了一版，同一输入跑 100 次结果一致，是不是可以了？

**助手**：还不够。小 shape 下流水几乎不重叠；要加大 shape、多核，让危险窗口更容易命中，再跑 100 次。

**他**：加大之后，确实偶尔会错。那我这个改动还是有问题的。

**助手**：对，这就是"看起来对"的典型。单核小 shape 是同步问题最好的藏身处。

**他**：行，我把改动回滚了。顺便问一句，这种代码 review 的时候我该怎么提意见？别人写的，我不好直接说"这段多余"。

**助手**：先问"这两个 flag 同步的是哪一对"，让对方讲，通常讲着讲着自己就发现问题了。直接说多余容易变成立场之争。

**他**：有道理。我先记着。
## 7. 视频组的 elementwise，带宽只有 30%

**他**：elementwise 算子，实测带宽只有理论值 30%。`mte2_ratio` 18%、`vec_ratio` 60%。这算搬运瓶颈还是计算瓶颈？

**助手**：`mte2_ratio` 低不等于搬运没问题，它只说明搬运单元在采样窗口里忙的比例低。先看 tile 多大、`blockDim` 几个、Task Duration 和理论时间差多少倍。

**他**：tile 8KB，blockDim 8。我直接把 tile 改到 64KB 试试？

**助手**：会超 UB。tile 大了还得降队列深度，可能把 double buffer 也搞没了。

**他**：已经试了，跑起来报 UB 超限。那我怎么算能放多大？

**助手**：

```
UB ≈ 深度 × tile × 输入份数 + 深度 × tile × 输出份数 + 临时 buffer + 对齐
```

留 10%–20%。先用 16–32KB，深度 2。

**他**：16KB、深度 2，到 45% 了。还是差一半，是不是没救了。

**助手**：先做 ablation，别急着下结论。第一个实验：只 CopyIn + CopyOut，不做计算。

**他**：纯搬运能到 80%。那说明什么？

**助手**：说明这张卡、这个 shape 的搬运上限就是 80%，你现在 45%，中间还有 35% 耗在计算或同步上。同时说明你离"硬件不行"还远。

**他**：我这段有三次 Cast，这个贵吗？

**助手**：三块开销：多一次 UB 读写、占 UB 空间、和计算抢 Vector 单元。能在原 dtype 上算完的别转。

**他**：去掉一次，62%。说实话，再往下优化还值得投入几天吗？

**助手**：看三条：和同类算子差距是否在 10% 内、是否到 roofline 合理区间（elementwise 通常 70%–85%）、连续两轮收益是否小于 3%。

**他**：那 70% 到 80% 之间这段呢，还要不要追？

**助手**：通常不值。除非这个算子在整网里占比很高。

**他**：行，先到这儿。顺便问下，`{1,1000}` 这种小 shape 也按这个套路调吗？

**助手**：不用。小 shape 时间被启动开销主导，拿带宽口径评价会误判，应该看延迟。

**他**：那我看板上的数字不就废了？我们报表是按带宽算的。

**助手**：报表里小 shape 最好单独分组。混在一起会拉低整体，也会让优化方向跑偏。

**他**：懂了，我去改一下统计口径。

## 8. 把原来的 CUDA LayerNorm 搬过来

**他**：老模型要迁，里面有我之前写的 CUDA LayerNorm：block 内 `blockReduce`，`__syncthreads` 很密。想直接搬过来。

**助手**：别逐行翻译，按数据流重写。先给你映射：

| CUDA | Ascend C |
|---|---|
| `grid` / `block` | `blockDim`（核数） |
| `threadIdx` | 无，靠 Vector 指令的 lane |
| `shared memory` | UB，要显式搬运 |
| `__syncthreads()` | 队列同步 / `PipeBarrier` / 归约 API |
| `warp shuffle` | Reduce 类 API |
| `atomicAdd` | 有，但慎用 |

**他**：shared memory 那块我最不放心。UB 到底多大？我按多大来切行？

**助手**：不同型号差别很大，别写死，用接口取实际值。另外 UB 不完全给你用，队列、临时 buffer 都要占。

**他**：那我先按 N ≤ 4096 常驻 UB 写，超过就走两遍，行不行？

**助手**：可以。但要留余量，而且注意 fp32 累加会多占一块。

**他**：对了，我原来 `__syncthreads` 是在做跨 warp 的规约。现在换成 Reduce API，但我这个规约是跨行的，不是一个 tile 内。

**助手**：那要按轴切。行内规约用核内 API 就行；跨行的话，要么把行放同一个核上按列算，要么走 workspace 汇总。

**他**：骨架跑通了，但比 CUDA 慢两倍。

**助手**：先看两个数：blockDim 设了几个，是不是每行都读了两遍 GM。

**他**：blockDim 我设的 4。改到 20 好一些，但还是慢。

**助手**：两遍读 GM 是 LayerNorm 的固有成本。CUDA 版本能一遍，是因为数据在 shared memory 里。你的 N 有多大？

**他**：8192。

**助手**：8192 个 fp16 元素 = 16KB，加上 fp32 累加和输出 buffer，其实放得下。试试整行常驻 UB。

**他**：改成常驻之后快了不少，但 UB 有点紧。我再加一个算子就放不下了。

**助手**：那就按 N 分档：小于阈值常驻，大于走两遍。阈值用实测定，不要拍。

**他**：迁完精度差 1e-3。CUDA 那边是 fp32 累加的。

**助手**：那 Ascend 这边也要 fp32。再检查 eps 是否一致，以及有没有一边开了 fast math。

**他**：eps 都是 1e-5。那应该是累加的问题？

**助手**：先把 mean/var/rstd 三个中间量都打出来，两边逐段比，别只比最终输出。

**他**：找到问题了，我第二遍的 `x - mean` 用了 fp16 的 mean。

**助手**：对，中间量一旦回 fp16，前面的 fp32 就白做了。

**他**：行，我整理了一份 checklist，回头贴文档里。

**助手**：记得加两条容易被忽略的：shape=1 的边界，还有非对齐 shape。
## 9. 算子进推理服务，Python 里调不到

**他**：算子都过了，接进推理服务，Python 里报：

```
RuntimeError: Could not run 'my_add_custom' with arguments from the 'PrivateUse1' backend.
```

`config.ini` 里有我的 vendor，`nm -D` 也能找到符号。那是框架的问题？

**助手**：对，dispatcher 报的是"没有为这个 backend 注册实现"。两条路：改 op-plugin 注册，或者 pybind 直接调 aclnn。

**他**：能用 pybind 吗？我不太想动 op-plugin，改起来牵扯太多。

**助手**：可以，推理场景够用。aclnn 是两段式：

```cpp
uint64_t workspaceSize = 0;
aclOpExecutor* executor = nullptr;
aclnnMyAddCustomGetWorkspaceSize(x, y, z, &workspaceSize, &executor);
void* workspace = nullptr;
if (workspaceSize > 0) aclrtMalloc(&workspace, workspaceSize, ACL_MEM_MALLOC_HUGE_FIRST);
aclnnMyAddCustom(workspace, workspaceSize, executor, stream);
aclrtSynchronizeStream(stream);
```

**他**：workspace 还要我自己 malloc？我以为框架会分配。

**助手**：必须自己分配，同一 shape 下可以复用。注意用 `aclrtMalloc`，别用 `new`。

**他**：跑通了。但偶发报设备侧异常，日志里有个 507015。是不是我 workspace 释放早了？

**助手**：有可能，但也可能是越界。先别改代码，把 device 日志导出来：

```bash
msnpureport -d 0 -f .
```

**他**：导出来一堆，看哪？

**助手**：抓四个：`aicore error` 或 `trap` 附近的第一条、PC 地址、访问的地址、长度。最后一条通常是连锁反应，别从那里看。

**他**：找到了，访问长度比我分配的多了 128 字节。是我 tiling 里算错了。

**助手**：对。另外顺手检查一下：tensor 描述里的 length 和实际分配是否一致，这种"差一点"的越界很常见。

**他**：顺便问一句，这种设备侧异常会影响别的进程吗？我这台卡上还有别人的服务。

**助手**：会。同卡进程隔离有限，一个进程 trap 可能导致整卡复位。所以别在共用卡上做破坏性实验。

**他**：明白了。那我改完之后和 PyTorch 对不上，差了 1e-3。

**他**：全 1 也对不上。那是格式问题？

**助手**：很可能。NCHW 和 NHWC 的 stride 不一样，会整块错位，但看起来又"差不多对"。

**他**：确实是 NHWC。改了之后对上了。

**助手**：那精度就差在最后一点舍入了，量级正常。

**他**：最后问个事，这个算子要给业务团队，我交什么？

**助手**：六样：算子包（注明架构和 CANN 版本）、aclnn 接口说明、shape/dtype 支持矩阵、精度报告、性能数据、已知限制。

## 10. 评审被问住：为什么不能像 CUDA 一个 kernel 搞定

**他**：方案评审被问"为什么非要 host tiling + kernel 两段，不能像 CUDA 一样一个 kernel 里切分"。我当时答"文档就这么写的"，被追问就没词了。

**助手**：因为 AI Core 没有线程抽象，片上存储小且要显式管理，kernel 二进制又必须静态展开。切片策略只能放到 host 侧算好，通过 tiling 下发。

**他**：那 Scalar 是干嘛的？我看它性能很差，为什么不干脆去掉。

**助手**：算地址、判边界、控循环、发指令，这些都是控制流，Vector 指令表达不了。性能差但不可少。

**他**：Cube 和 Vector 能同时跑吗？

**助手**：能，它们是不同流水，可以重叠。前提是你把数据和同步安排好了。

**他**：可我写的 kernel 里它们看起来像串行的。

**助手**：那就是没编排流水，或者中间有依赖。比如你等 Cube 结果落到 GM 再读回来，那就必然串行。

**他**：UB 和 L1 是什么关系？我老看到 L0A、L0B、L0C。

**助手**：GM 下面是 L1，再往下是 L0A/L0B（Cube 的两个输入）和 L0C（Cube 输出）。UB 是另一块，Vector 的工作区。写 elementwise 基本只碰 UB，写 Matmul 才管 L1/L0。

**他**：那为什么不能把 L1 和 UB 合并？

**助手**：它们服务不同单元的访问模式和带宽需求。合并会让 Cube 和 Vector 抢同一块资源。具体设计原因要看架构文档，我只能讲到这层。

**他**：行。那图模式和单算子模式，对我的写法有影响吗？

**助手**：影响在谁来优化，不在 kernel 怎么写。图模式由 GE 做跨算子融合和调度；单算子模式直接调 aclnn，适合调试。

**他**：aclnn、aclop、GE 这三个我一直分不清。

**助手**：GE 管多个算子怎么排，aclnn 管一个算子怎么调（两段式），aclop 是老接口。OPP 是算子仓库，kernel 是仓库里的货。

**他**：那什么算子该用高阶 API？

**助手**：标准形态的（Matmul、Softmax、LayerNorm）优先用，省掉 tiling 和精度的坑。自定义融合逻辑才手写。

**他**：可我看有些示例，明明有高阶 API 还是手写了。

**助手**：通常是性能或特殊 shape 需求。先跑高阶 API 拿基线，不够再下沉。反过来的顺序很费时间。

**他**：好，最后帮我理一下，这一页该怎么写才不被追问。

**助手**：一页画三层：硬件（AI Core 四单元三流水）、存储（GM→L1→L0 / UB）、软件（host tiling → kernel → 上层 aclnn）。然后把"为什么不能一个 kernel 搞定"直接写成三个约束，配一句"CUDA 的 thread 在这里由指令 lane 替代"。

**他**：那我带新人的话，按什么顺序讲比较好？

**助手**：架构和编程模型 → 跑通样例 → 写 elementwise 和 reduce → 排一次故障 → 高阶 API 和融合。别跳过第四段，大部分人卡在"能跑通但交付不了"。

**他**：有道理，我上次就是卡在那儿。行，我去画图了。
