# 平台能力沙盘复用笔记

## 来源与边界

- 数据快照来自 [ai-development-behavior-system-report.html](../../ai-development-behavior-system-report.html) 的“平台能力沙盘”区块（原文件约第 1446–1470 行），逐格保留六个平台、十项能力 / 机制、原说明和状态 class。
- 以 [agent-tool-calling-reference.html](../../agent-tool-calling-reference.html) 交叉核对概念边界：MCP 是连接协议 / 执行适配器；Subagent 是可拥有独立上下文与工具权限的嵌套任务循环，二者没有固定前后顺序。Agent Loop 指同一任务内的行动—观察—再决策；定时 `/loop`、Hook 和跨任务自动化属于不同机制。
- 这是对历史沙盘的结构化提取，不是截至 2026-10-13 的新一轮平台能力审核。格内 `本轮未确认`、内置 / 有边界，以及来源的 H/M/L 证据等级不能被改写成“没有能力”或最新现状。
- 沙盘状态是“入口类型”记录：`direct` 表示直接配置，`install` 表示安装 / 接入；`limit` 是内置或有边界，`none` 是无同类入口，`unverified` 是未确认。只有前两类适合计入“可配置 / 可安装入口”，但数量只能描述入口覆盖，不能证明使用效果、质量或用户收益。
- Runtime / Agent Loop 在原沙盘中明确不计为开发者可直接装配入口。因此不能把运行时存在、Loop 可见或平台内有多步执行，统计成可安装能力。

## 十项能力 / 机制的候选干预映射

以下逐项对应沙盘行。它们是待验证的设计假设与候选交付，不代表组织职责已经确定，也不代表收益已经验证。

| 能力 / 机制 | 作用 | UX 设计介入 | 候选交付 | 工程 / 领域依赖 | 验证方法 |
|---|---|---|---|---|---|
| 项目规则 / 持久上下文 | 把项目约束带入任务 | 明确规则作用范围、优先级、来源与冲突处理 | 规则模板、作用域说明、冲突提示方案 | Host 加载机制、项目结构、领域规则维护者 | 用跨目录 / 冲突案例检查实际加载、理解与遵循情况 |
| 领域知识库 / 检索源 | 为任务提供相关文档、代码、样例及版本信息 | 定义检索范围、适用条件、引用呈现和过期 / 冲突提示 | 知识元数据字段、检索结果卡片、来源与版本标注规范 | 文档 / 代码索引、版本兼容数据、领域 Owner | 用代表性问题核对召回、引用可追溯性和适用性判断 |
| Harness / Agent Runtime | 装配上下文、工具与运行控制 | 找出用户可理解和可控制的状态、权限、中断、接管与恢复点 | 任务状态模型、控制点清单、运行事件 / 证据契约 | 平台 Host 能力、权限模型、日志和状态接口 | 在同一任务的成功、中断、拒绝和失败路径中检查状态一致性与可恢复性 |
| Skill / Workflow | 提供可发现、可复用的方法步骤 | 设计调用时机、输入前提、步骤 / 分支、停止条件及验收提示 | Skill 模板、任务流程卡、输入输出与验收契约 | Skill 加载 / 调用机制、准确的昇腾流程与例外知识 | 用多版本 / 多环境任务回放，检查步骤适配、遗漏和错误停止 |
| Command / Prompt | 显式启动固定或常见任务 | 降低发现与启动成本，并让任务范围、所需信息和预期结果清楚 | 命令目录、触发文案、缺参补充与结果说明 | 命令注册和执行入口、领域任务定义 | 观察目标用户能否选对命令、补齐必要输入并完成任务 |
| MCP / Connector | 连接外部系统并提供受控查询或动作 | 设计连接发现、授权说明、动作影响提示、执行状态与结果回传 | 工具目录、授权 / 确认流程、结果回执字段 | MCP Server / Connector、身份权限、目标系统 API 与可靠性 | 用只读查询及受控动作测试授权边界、失败反馈和结果可追溯性 |
| Plugin / Extension | 打包、安装和分发扩展能力 | 说明包内包含什么、权限与依赖，支持安装后发现、启停和移除 | 扩展清单、安装前说明、能力与权限卡片 | 扩展接口、签名 / 兼容性、版本发布与支持机制 | 测试安装、升级、冲突、卸载及权限理解，不把安装量当成效果 |
| Custom Agent / Subagent | 将有边界的子任务委派给独立角色或上下文 | 明确委派范围、可用工具、过程可见性、返回格式与人工接管条件 | 角色说明、委派契约、交接与汇总格式 | Agent 编排、上下文隔离、工具权限、任务 Owner | 用并行 / 失败 / 部分完成案例检查边界遵守、交接信息和主任务整合 |
| Hook / Lifecycle | 在工具或会话生命周期事件点触发动作 | 说明触发时机、影响、可逆性与失败后的用户选择 | 事件—动作映射、确认 / 撤销提示、运行记录规范 | Hook 事件接口、执行权限、幂等与错误处理 | 对触发、重复触发、拒绝、超时和失败进行事件级测试 |
| Agent Loop · 任务内 | 将行动结果回填后继续决策或停止 | 让用户看见当前步骤、观察结果、继续 / 停止理由及接管点 | 回合状态图、进度与结果呈现、停止 / 接管规则 | Host 循环、结果回填、停止条件、任务验收接口 | 回放成功、工具失败、用户中断和达到停止条件的多轮任务；检查状态与证据是否连贯 |

## “专家团”与人工专家升级的口径

“专家团”只是用户举例之一。沙盘记录 WorkBuddy 的 Expert Team 入口为 `limit`，说明是“可召唤；不等同自定义 Subagent”；这支持把它作为一种产品委派模式观察，不能据此推断其底层实现或效果。

专职 Agent / Subagent 与人工领域专家应分开建模：前者执行范围清晰、可定义输入输出的子任务；后者是证据不足、风险较高或需要责任判断时的升级路径。若设计人工升级流程，候选交付可包括触发条件、携带的任务现场、待回答问题、响应责任和结论回流；是否需要以及由谁承担，仍需结合实际任务与组织安排验证。人工专家不计入平台可配置 Agent 能力。

## 复用说明与推导边界

沙盘适合作为“能力入口 / 运行机制地图”复用：先用它定位某项能力是否直接配置、需要安装、属于内置机制、无同类入口或本轮未确认；再结合具体任务中的需求、失败证据、实现接口与责任边界，判断设计介入是否可行以及优先级。用户提到的 Skill、MCP、专家团是希望展开深度的例子，不构成唯一重点或预设优先级。

状态数量只能描述此历史快照中入口的覆盖情况，不能证明使用效果、质量、成熟度或用户收益；跨平台比较也受本轮资料范围和证据等级限制。每个干预方向都需要任务样例、实现验证及适当的用户 / 运行数据后，才能判断是否有效和是否值得优先投入。
