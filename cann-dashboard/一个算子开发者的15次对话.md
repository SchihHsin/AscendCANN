# 一个算子开发者的 15 次对话

> 同一个人，平时在几个项目之间来回切。下面是他向 AI 助手提问的 15 段对话，提问没什么章法，想到哪问到哪。

---

## 1. 图像组留下的机器，容器里看不到卡

**他**：接了图像组的预处理项目，机器是上一任留下的，8 卡 910B。CANN 我重装了一遍，`npu-smi info` 还是报：

```
DrvMngGetConsoleLogLevel failed. return = 1
dcmi module initialize failed. ret is -8005
```

是不是得重装系统？

**助手**：先别重装，这个报错我也见过不少次，八成不是系统坏了，而是**设备管理通道（DCMI）没起来**。

`dcmi module initialize failed` 的字面意思是：`npu-smi` 想通过 DCMI 接口去问驱动"这台机器上有几张卡"，但驱动那一侧没有响应。它不负责算力，只负责"发现和查询设备"，所以哪怕 CANN 装得完美无缺，只要这条通道不通，你看到的还是这个错。

按概率排，可能的原因有四个：

1. **你在容器里，设备节点没映射进来**（最常见，占我见过的大半）
2. 宿主机上驱动模块没加载
3. 设备节点在，但权限不对
4. 驱动和固件版本错配，管理通道拒绝服务

先做三个一分钟的检查，不用改任何东西：

```bash
ls -l /dev/davinci*                       # 节点在不在、属主是谁
lsmod | grep -i davinci                   # 驱动模块加载了没
cat /usr/local/Ascend/driver/version.info # 驱动装没装、什么版本
```

还有一个容易被忽略的认知点：**`npu-smi` 属于驱动包，不属于 CANN**。所以"CANN 装好了"和"npu-smi 能用"是两件独立的事——这也解释了为什么有人 CANN 都没装，`npu-smi setup` 照样能看到卡。

**他**：两个都空。/dev 下一个都没有，lsmod 也没输出。那我是不是驱动没装？我直接在容器里装一遍驱动行不行？

**助手**：先回答你最后那个问题：**不行，容器里装不了驱动**。

原因不难理解：驱动是内核态模块（`.ko`），它必须加载到**宿主机的内核**里，而容器共享宿主内核——容器里既没有加载模块的权限，也没有对应的内核头文件。你在容器里跑 `insmod` 或装 `.run` 包，通常会看到 `Operation not permitted` 或者干脆没有 `/lib/modules` 目录。这不是权限没给够，是模型上就不成立。

所以「`/dev` 空 + `lsmod` 空」这个组合，说明问题在**宿主机**这一层，而不是容器里缺什么。接下来分两步：

**第一步，先确认你到底在哪。**

```bash
ls /.dockerenv        # 有输出 → 在容器里
# 或者
cat /proc/1/cgroup | grep -i docker
```

**第二步，按结果分叉：**

- 如果**在容器里**：`/dev` 空是正常现象，设备节点不会自己长出来，必须由 `docker run` 映射进去。往下走映射。
- 如果**在物理机上**：`lsmod` 里没有 davinci 相关模块，说明驱动装了但没加载（或者没装成功）。这时看 `dmesg | grep -i davinci`，通常能看到加载失败的原因，比如版本和内核不匹配。

先告诉我你在容器还是物理机，我们再往下走，别在这两个分支之间来回猜。

**他**：在容器里。

**助手**：那路径就清晰了。容器里要看设备，`docker run` 必须满足两个条件：**设备节点映射** + **驱动库挂载**。少一个都不行。

一个能跑起来的最小启动命令长这样：

```bash
docker run -it \
  --device=/dev/davinci0 \
  --device=/dev/davinci_manager \
  --device=/dev/devmm_svm \
  --device=/dev/hisi_hdc \
  -v /usr/local/Ascend/driver:/usr/local/Ascend/driver \
  -v /usr/local/dcmi:/usr/local/dcmi \
  <image> bash
```

四个设备节点分别是什么，值得记一下，因为报错信息会拿它们做区分：

| 节点 | 作用 | 缺了会怎样 |
|---|---|---|
| `/dev/davinci0` | 算力设备 | 看不到卡 |
| `/dev/davinci_manager` | 管理通道（查询、复位、监控） | **报的正是你那个 DCMI 初始化失败** |
| `/dev/devmm_svm` | 共享虚拟内存管理 | 内存分配类报错 |
| `/dev/hisi_hdc` | host-device 通信 | 通道不通、日志拿不到 |

最容易漏的就是 `davinci_manager`——因为它不参与计算，很多人觉得"我只要算力设备就够了"，结果报出来的错误偏偏是"设备管理接口初始化失败"，看起来像环境装坏了，其实只是少了一行 `--device`。

至于 `-v` 那两个挂载，是让容器用**宿主机的驱动库**，而不是在镜像里再装一份。这也顺便解释了为什么镜像里不该带驱动（后面我们会聊到）。

**他**：我 `--privileged` 是不是就够了？

**助手**：不够，这两个是不同层面的东西，很容易混。

`--privileged` 给的是**权限**：让容器能访问大部分设备、能改内核参数、能 mount。但它不会**凭空产生设备节点**——`/dev` 是内核的 devtmpfs，宿主机上有哪些节点，容器里才能看到哪些。你给了全部权限，但那个目录里本来就没有 `davinci0`，权限再大也访问不到不存在的东西。

更直白一点：

- `--device=/dev/davinci0`：**把节点搬进容器**（这是必须的）
- `--privileged`：让容器有资格用这个节点（这是可选的，通常用 `--group-add` 更精细）

所以正确顺序是"先映射，再谈权限"。你现在加了 `--device` 之后报 `Permission denied`，说明节点已经进来了，这一步是对的，问题转移到权限上了——这其实是进展，不是新问题。

顺便提醒一句：生产环境尽量不要用 `--privileged`，它等于把宿主机的大门敞开。用 `--group-add` 或者精确的 `--cap-add` 更合适。

**他**：加了，报 `open /dev/davinci_manager: Permission denied`。另外这个 manager 是干嘛的？跟 davinci0 有什么区别？

**助手**：先说权限，再说它是干嘛的。

**权限问题**：这些设备节点的属组是 `HwHiAiUser`（有的环境是 `HwHiAiUser` 加 `root`），权限位一般是 `crw-rw----`。容器里默认是 root 用户，理论上能读写，但如果镜像里跑的是普通用户，就会撞上 `Permission denied`。

两个解法，按推荐度排：

```bash
# 方案 A：把宿主机的组 ID 带进容器（推荐，权限最小）
--group-add $(getent group HwHiAiUser | cut -d: -f3)

# 方案 B：容器里用 root 跑（最快，但不适合长期）
docker run -u root ...
```

用 `--group-add` 的时候注意：容器里的组名可能不存在，但**组 ID 是生效的**，所以用数字 ID 而不是组名。

**manager 和 davinci0 的区别**：这是两个不同用途的节点，不是一个东西的两个名字。

| 节点 | 角色 | 典型操作 |
|---|---|---|
| `davinci0` | 算力设备本体，你的 kernel 实际跑在这上面 | 内存分配、kernel 下发、同步 |
| `davinci_manager` | 管理面，负责"这台机器有哪些设备、状态如何" | 查询信息、复位、监控、日志 |

所以 `npu-smi`、`dcmi` 这类**管理工具**走的是 manager；而 ACL、算子、kernel 走的是 davinci0。这也解释了为什么缺 manager 时，报错是"管理接口初始化失败"而不是"设备不可用"——两个面是分开的。

顺带说一句：davinci0 后面还有 davinci1..7，对应 8 张卡。如果你只映射了 davinci0，那容器里就只能看到一张卡，`npu-smi` 也只显示一张。多卡场景要把需要的都映射进去，或者用 `--device=/dev/davinci*` 这种通配（注意 shell 展开时机，可能需要在宿主机上先展开）。

**他**：能看到了。但 Health 是 Warning，驱动版本和板卡 Firmware 版本不一样。这个 Warning 我之前一直没管，会有事吗？

**助手**：会有事，而且这类问题最难查，因为**它不立刻报错**。

驱动和固件是配套发布的：驱动（内核态）和固件（跑在设备上的那层）之间有一套私有协议，版本错位时协议对不上，表现通常是"能查到卡、能跑小算子、一到重负载就超时、或者偶发设备侧异常"。你很难第一眼把它和"版本不配套"联系起来，反而会去怀疑自己的 kernel 写错了。

先看清楚现在是什么状态：

```bash
npu-smi info -t board -i 0      # 看单卡的 board id、固件版本
npu-smi info -t health -i 0     # 看具体告警项，而不只是 Warning 这个字
```

`-t health` 的输出里通常会给具体原因（比如固件版本不匹配、温度、ECC 计数），比顶层的 Warning 有用得多。

固件的处理方式是**整包刷**，用配套的 `.run` 包，一般带 `--full` 参数。两个注意点：

1. **刷之前记下当前版本号**，出问题能回退；
2. **刷固件会中断这张卡上的业务**，不是热操作。

如果你是接手别人的机器，最好先去查一下这台机器的"驱动-固件-CANN"三者的配套关系表，确认目标版本，而不是直接刷到最新——最新不一定和你的 CANN 版本配套。

**他**：晚上还有训练任务，只刷一张卡行不行？

**助手**：技术上可以，`npu-smi` 支持按卡操作。但我不建议，原因有三个，按严重程度排：

**第一，多卡固件版本不一致，会在集合通信上出问题。** 训练任务里 HCCL 做 all-reduce 时，各卡的固件协议版本不一致，轻则性能下降，重则通信超时、任务 hang 住。这种问题排查起来极痛苦，因为它只在多卡通信时出现。

**第二，调度侧会困惑。** 资源管理器看到 8 张卡版本不同，可能会做保守调度，或者干脆把这张卡标记成不可用——你本来只想修一张，结果整机可用卡数变了。

**第三，回退更麻烦。** 一张卡刷坏了，你还能单卡回退；但如果版本已经分叉，回退要重新对齐所有卡。

所以稳妥的做法是走维护窗口：

```
1. 申请窗口，通知业务方
2. 停掉该机器上的训练/推理任务
3. 记录当前驱动、固件、CANN 版本号
4. 全部卡刷到同版本（--full）
5. npu-smi info 检查全绿，npu-smi info -t health 逐卡确认
6. 跑一个最小用例（比如 device 侧的 vector add）验证
7. 恢复业务
```

如果实在等不到窗口，至少做到"这一次把所有卡刷到同一版本"，别留下 7 张旧卡 1 张新卡的状态。

**他**：行。对了，`/var/log` 下面那一堆 ascend 的日志是干嘛的？我一直没敢删。

**助手**：那是 **plog**，CANN 的 host 侧运行日志，可以删，但建议先别删——它是排障时最直接的一手材料。

几个关键点：

**它记什么**：ACL 初始化、device 打开、内存分配、算子下发、stream 同步这些 host 侧动作，以及 runtime 的错误码。你之前那些 `aclrtMalloc failed`、`初始化 device 失败`，答案基本都在这。

**它不记什么**：设备内部（AI Core）发生了什么。kernel 崩了、trap 了，这些在 device 侧日志里，要用 `msnpureport` 单独导出。这是两套日志，很多人只翻 `/var/log` 找不到 kernel 的崩溃，就是因为找错了地方。

**怎么用**：默认级别是 WARN 以上，排障时临时调高再复现一次：

```bash
export ASCEND_GLOBAL_LOG_LEVEL=1    # 0=DEBUG 1=INFO 2=WARN 3=ERROR
export ASCEND_SLOG_PRINT_TO_STDOUT=1  # 顺便打到终端，省得翻文件
```

**能不能删**：能，但建议按时间清理而不是 `rm -rf`。它默认会滚动，占满磁盘的情况偶尔有，特别是长时间跑训练。真要清，先 `du -sh` 看看是哪个子目录涨起来的，通常是 `plog` 或 `device-*`。

顺带一个经验：出问题的时候，**先看时间戳**。把你复现的时间点记下来，然后在日志里找那个时间窗口，比从头读快得多。

**他**：那这些东西我每次都得手动查一遍？有没有个脚本。

**助手**：可以封一个，关键是**按依赖顺序查，失败就退出**——顺序错了就会在"装没装坏"上绕圈。

```bash
#!/bin/bash
# ascend_env_check.sh —— 任何一项失败就退出，并打印原因
set -u

fail() { echo "[FAIL] $1"; exit 1; }

echo "[1/6] 设备发现"
npu-smi info >/dev/null 2>&1 || fail "npu-smi 不可用：检查驱动/设备映射"
npu-smi info | head -5

echo "[2/6] 设备健康"
npu-smi info -t health -i 0 2>/dev/null | grep -qi "warning\|error" \
  && echo "[WARN] 健康状态异常，执行 npu-smi info -t health -i 0 查看"

echo "[3/6] toolkit 环境"
[ -n "${ASCEND_HOME_PATH:-}" ] || fail "ASCEND_HOME_PATH 为空：set_env.sh 没生效"
[ -d "$ASCEND_HOME_PATH" ]     || fail "ASCEND_HOME_PATH 指向的目录不存在"

echo "[4/6] OPP 配置"
[ -n "${ASCEND_OPP_PATH:-}" ] || fail "ASCEND_OPP_PATH 为空"
[ -f "$ASCEND_OPP_PATH/vendors/config.ini" ] \
  || echo "[WARN] vendors/config.ini 不存在，自定义算子可能加载不到"

echo "[5/6] 驱动版本"
head -3 /usr/local/Ascend/driver/version.info 2>/dev/null \
  || fail "驱动信息读取失败"

echo "[6/6] 冒烟"
ls "$ASCEND_HOME_PATH/compiler" >/dev/null 2>&1 \
  && echo "[OK] 编译器目录可访问" \
  || echo "[WARN] 编译器目录不可访问"

echo "全部检查通过"
```

为什么顺序是这样：**设备 → 健康 → 环境变量 → OPP → 驱动 → 编译器**。前两步不通，后面全是白搭；环境变量不通，编译器一定找不到头文件。按这个顺序走，第一个 FAIL 就是根因，不用往下猜。

**他**：我们 CI 每次拉新容器跑测试，环境老不一致，这个能放进去吗？

**助手**：能，而且强烈建议放——但要先想清楚一件事：**环境其实分两半，一半跟机器走，一半跟镜像走**。混在一起就永远不一致。

| 部分 | 归属 | 怎么固定 |
|---|---|---|
| 驱动、固件 | 宿主机（内核态） | 标准化机器，不能进镜像 |
| CANN toolkit | 镜像（用户态） | 版本号写进 tag |
| 自定义算子包 | 镜像或挂载 | 跟着 CANN 版本一起固定 |
| 模型/数据集 | 挂载 | 单独管理 |

具体做法：

1. **镜像 tag 带版本**，比如 `cann:8.x.x-910b-py3.10`，禁用 `latest`；
2. **容器启动脚本第一步就跑体检**，失败立即 exit 1，让 CI 在"环境阶段"就红，而不是跑到第 40 个算子才挂；
3. **把体检结果写进构建产物**（`env.log`），出问题时不用重现就知道当时是什么环境；
4. **驱动版本记进报告**，因为同一份镜像在不同机器上行为可能不同，而这个差异只可能来自驱动。

还有一个 CI 特有的坑：**并行跑多个容器抢同一张卡**。体检脚本最好加一步检查卡是不是被别人占着：

```bash
npu-smi info | grep -A2 "davinci" | grep -q "No running processes" || echo "[WARN] 卡上已有进程"
```

否则你会得到一堆"偶发失败"，最后发现是并行任务互相干扰。

**他**：那为什么驱动不能打进镜像，打进去不就一致了吗。

**助手**：这个想法很自然，但结论是**不行**，原因是架构层面的：

**驱动是内核态的，容器共享宿主内核。** 你在镜像里放一份 `.ko`，容器启动时既没有权限加载它（需要 `CAP_SYS_MODULE`，而且加载的是**宿主内核**的模块），版本也必须和宿主内核严格匹配。换句话说：

- 如果宿主已经装了驱动，容器里那份是多余的，还可能造成版本混乱；
- 如果宿主没装驱动，容器里那份也加载不了。

所以驱动只能是"宿主机的属性"，镜像能做到的只有"假设宿主有驱动，我只挂载它的用户态部分"——这就是为什么 `docker run` 里要 `-v /usr/local/Ascend/driver`。

这条边界记住了，很多问题都能自己解释：

- **为什么换一台机器就要重新装驱动**：因为驱动跟着内核走，不跟着镜像走。
- **为什么同一个镜像在不同机器上表现不同**：因为驱动/固件不同。
- **为什么 CI 要固定机器型号**：因为驱动和固件没法用镜像固化。

一句话总结：**内核态的东西跟机器走，用户态的东西跟镜像走。** 想彻底一致，就得两边都固定——镜像固定版本，机器固定型号和驱动。

## 2. Tiling 到底该怎么设计

**他**：接了个模型，batch 从 1 到 64，seq 从 128 到 8192。现在每个 shape 都要重调一遍 tiling，基本靠试，试到不崩、不慢为止。这个有没有方法，还是只能这样？

**助手**：有方法，而且"靠试"通常是因为把三件事混在一起试了。

Tiling 本质上是三个**独立**的决策，按顺序做，每个都有明确约束：

| 决策 | 回答什么问题 | 主要约束 |
|---|---|---|
| ① 多核切分 | 任务按哪个维度、怎么分给 N 个核 | 连续性、局部性、负载均衡 |
| ② UB 切分 | 每个核一次处理多少 | UB 容量、对齐、尾块 |
| ③ buffer 规划 | 这些块放哪、几份、要不要双缓冲 | 容量、流水重叠 |

大部分人"试"的时候，是在同时调这三个，所以看不出哪个变量在起作用。先把 ① 定死，再调 ②，最后调 ③，会快很多。

**他**：那第一步，按哪个维度切？

**助手**：三个判断标准，按优先级：

**1. 连续性**——切完之后，每个核拿到的数据在 GM 上尽量连续。

这直接决定搬运效率。比如 `{1024, 1024}` 的矩阵，按行切，每个核拿到的是一段连续内存；按列切，每次只能搬 2KB 有效数据，中间跳 2KB，带宽直接砍半。

**2. 局部性**——相邻数据尽量给同一个核。

因为 L2 是共享的，同一个核连续访问相邻区域，命中率高；打散了就变成"每个核都在到处跳"。

**3. 负载均衡**——各核工作量接近。

这条最容易做到，但也最容易被忽略（后面会讲木桶效应）。

具体到你这类算子：

- **elementwise**（scale、add）：按元素总数切，第一维摊平最省事；
- **reduce**（sum、max）：按**输出**切，一个核负责一段输出，而不是一段输入；
- **matmul**：按 M 或 N 切，别按 K 切（K 是累加维，切了要汇总）。

**他**：每个核分多少？我一直是 `total / blockNum`。

**助手**：`total / blockNum` 是起点，但有两个坑必须补：

**坑一：余数丢了。**

`1002 / 8 = 125`，余 2。这 2 个元素如果没人管，就是"大部分对、少数位置偏小"。

**坑二：木桶效应。**

整体时间由**最慢的核**决定。所以"余数全给最后一个核"看起来很整齐，实际上让最后一个核多干一倍的活（如果余数接近 perCore 的话），整体反而更慢。

正确写法是把余数**摊到前几个核**：

```cpp
int64_t perCore = total / blockNum;
int64_t tail    = total % blockNum;

int64_t start = blockIdx * perCore + std::min<int64_t>(blockIdx, tail);
int64_t len   = perCore + (blockIdx < tail ? 1 : 0);
```

验算 `total=1002, blockNum=8`：

| block | start | len |
|---|---|---|
| 0 | 0 | 126 |
| 1 | 126 | 126 |
| … | … | … |
| 7 | 877 | 125 |

总额 1002，无缝、无重叠，最大最小差 1 个元素。

**他**：那 tile 大小怎么定？我一般是 8K 或者 16K，凭感觉。

**助手**：tile 有闭式解，不用凭感觉。核心是 UB 预算：

```
可用 UB ≈ 总 UB × 0.75

单份 tile 占用 = tile × 输入份数
               + tile × 输出份数
               + 临时 buffer（fp32 累加、cast 中转）
               + 对齐 padding

tile ≤ 可用 UB / (深度 × (输入份数 + 输出份数))
```

举个具体的：假设 UB 有效可用 160KB，一进一出，深度 2：

```
tile ≤ 160KB / (2 × 2) = 40KB
```

再考虑对齐（32B）和临时 buffer，取 32KB 比较稳。

三个经验补充：

1. **tile 太小**（< 8KB）：DMA 启动开销占比高，带宽上不去；
2. **tile 太大**：深度只能降到 1，双缓冲没了，搬运和计算串行；
3. **最优值通常在"能放下的最大值"和"深度 2 能成立"之间**，要扫一遍确认。

**他**：tile 和队列深度要怎么一起调？我每次改一个，另一个就出问题。

**助手**：因为它们共享同一个约束（UB 容量），所以必须**联合扫描**，不能单变量调。

做法：固定"总 UB 占用"不变，在 tile 和深度之间做交换：

| 组 | tile | 深度 | 总占用 |
|---|---|---|---|
| A | 8KB | 2 | 32KB |
| B | 16KB | 2 | 64KB |
| C | 32KB | 2 | 128KB |
| D | 16KB | 4 | 128KB |
| E | 32KB | 1 | 64KB |

跑一遍，看 `Task Duration`。通常会看到一个拐点：

- 往小了走：启动开销变大，变慢；
- 往大了走：深度被迫降低，流水重叠减少，也变慢。

**默认值我一般给"能放下深度 2 的最大 tile"**，然后在它附近 ±1 档扫一遍。

**他**：可我 shape 变化很大，每个 shape 都扫一遍不现实。

**助手**：不用每个都扫，用**分档 + 公式**。

**第一步：把 tiling 写成函数，不要写死常量。**

```cpp
TilingResult CalcTiling(int64_t total, int64_t blockNum, uint64_t ubBudget) {
    // 1. 多核切分（余数摊前几个核）
    // 2. UB 预算倒推 tile（留 25% 余量）
    // 3. tile 向下对齐到 32B
    // 4. 算 tileNum / tail
}
```

**第二步：定几个"档位"，而不是连续值。**

比如按 `total` 分三档：

- 小（< 8K）：单核，tile = total；
- 中（8K ~ 256K）：多核，tile 固定 16KB；
- 大（> 256K）：多核，tile 固定 32KB。

档位边界用实测定（找性能拐点），档内用公式。这样只有 3 组参数要调，不是 N 组。

**第三步：把档位和阈值写进日志**，跑的时候打出来，方便定位"为什么这个 shape 走了慢路径"。

**他**：负载不均怎么办？我 8 个核，最后一个核经常闲着。

**助手**：先分清"闲置"和"慢"——这两个不是一回事。

- **闲置**：尾块分得少，那个核早早干完在等；
- **慢**：那个核拿到的块更大/更难算。

因为整体时间取决于**最慢的核**，所以只要有一个核慢，其他核再闲也没用。

三个处理方向，成本从低到高：

**1. 余数均摊**（前面讲过）——把最大最小差距压到 1 个元素，成本几乎为零。

**2. 动态 blockDim**——`total` 小的时候直接减少核数：

```cpp
int64_t blockNum = std::min(physicalCores, CeilDiv(total, minTaskPerCore));
```

8 个核抢 3 个元素，不如 1 个核干完。

**3. 两级切分**——大块按核分，核内再按 UB 分块。这样核内是流水，核间是并行，两个层次各管各的。

**他**：有没有一个通用的 tiling 模板？我照着填就行。

**助手**：给你一个骨架，覆盖大部分 elementwise / reduce：

```cpp
struct TilingData {
    int64_t total;       // 总元素数
    int64_t perCore;     // 每核基础长度
    int64_t tail;        // 余数（摊给前 tail 个核）
    int64_t tileLen;     // 单次处理元素数（32B 对齐）
    int64_t tileNum;     // 每核轮数
    int64_t lastLen;     // 最后一轮长度（可能不满）
};

TilingData CalcTiling(int64_t total, int64_t blockNum, uint64_t ubBudget) {
    TilingData t{};
    t.total   = total;
    t.perCore = total / blockNum;
    t.tail    = total % blockNum;

    // UB 预算倒推 tile（0.75 余量，一进一出，深度 2）
    uint64_t perTileBytes = ubBudget * 3 / 4 / (2 * 2);
    int64_t tile = perTileBytes / sizeof(half);
    tile = (tile / 16) * 16;              // 32B 对齐（fp16 = 16 元素）
    if (tile <= 0) tile = 16;

    t.tileLen = tile;
    // 按最大核算轮数（前 tail 个核多 1 个元素）
    int64_t maxLen = t.perCore + (t.tail > 0 ? 1 : 0);
    t.tileNum = (maxLen + tile - 1) / tile;
    t.lastLen = maxLen - (t.tileNum - 1) * tile;
    return t;
}
```

这个模板能跑，但**它只是起点**——真正上线前还要做三件事：

1. 用真实 shape 扫一遍 tile，确认拐点在你的档位内；
2. 加单测，覆盖 `total=1`、非整除、超大 shape；
3. 把 `blockNum` 和物理核数的关系确认清楚（是不是所有核都能用上）。

**他**：tiling 怎么测？它又不依赖 NPU，我总不能每次都上板试。

**助手**：对，tiling 是**纯 CPU 逻辑**，完全可以单测，而且应该单测——它比上板快一百倍，还能覆盖边界。

最小测试集：

```cpp
TEST(Tiling, Coverage) {
    for (int64_t total : {1, 15, 16, 1023, 1024, 1002, 1000000}) {
        for (int64_t blockNum : {1, 2, 8, 20}) {
            auto t = CalcTiling(total, blockNum, 160 * 1024);

            // 1. 每个核的区间必须落在 [0, total) 内
            // 2. 区间首尾相接，无空洞、无重叠
            // 3. 总长度 == total
            // 4. tileLen 必须 32B 对齐
        }
    }
}
```

这四条性质一旦写成断言，大部分 tiling bug 在 CPU 阶段就挡住了，不用等上板。

**他**：那如果 tiling 已经有问题了，会表现成什么样？

**助手**：三种症状，对应不同的错法：

| 症状 | 说明 | 可能原因 |
|---|---|---|
| 部分结果不对，位置固定 | 某些元素没算/重复算 | 余数丢失、区间重叠 |
| 大 shape 崩、小 shape 正常 | 越界 | tile 超出 UB、末块长度算错 |
| 结果全对但很慢 | 切分不均衡 | 木桶效应、tile 太小 |

最快的确认方式：在 kernel 入口把 tiling 打出来，和你在 host 侧算的对比：

```cpp
AscendC::printf("blk=%d start=%ld len=%ld tile=%ld num=%ld\n",
                AscendC::GetBlockIdx(), start, len, tileLen, tileNum);
```

二十行日志，比读代码快。

**他**：行，我先把这套公式落到 tiling 函数里。

**助手**：给你一个收尾清单，按顺序检查：

```
① 切分维度：连续 → 局部 → 均衡
② 余数：摊到前几个核，别全给最后一个
③ tile：UB 预算倒推，向下 32B 对齐，留 25% 余量
④ 深度：默认 2，和 tile 联合扫描
⑤ 分档：3 档左右，边界用实测定
⑥ blockDim：小 shape 动态收缩
⑦ 单测：覆盖 1 / 非整除 / 超大 shape
⑧ 日志：把 start/len/tile 打出来
```

这八条固化下来之后，"每个 shape 都重调"就变成"改一个档位参数"。

## 3. 换了新镜像，编译又过不去

**他**：新项目的镜像，`msopgen gen` 生成工程，`bash build.sh` 报：

```
fatal error: kernel_operator.h: No such file or directory
```

**助手**：这个错很典型，先看一个变量：

```bash
echo "ASCEND_HOME_PATH=$ASCEND_HOME_PATH"
```

如果它是空的，答案就有了——**编译器的头文件搜索路径没建立**。`kernel_operator.h` 是 CANN 编译器组件自带的头文件，位置大致在 `$ASCEND_HOME_PATH/compiler/tikcpp/...` 下面（具体路径随版本略有差异），这个路径靠 `set_env.sh` 注入。

顺便解释一下这个文件是干嘛的，免得下次又懵：它是 Ascend C 的"入口头文件"，里面聚合了 Kernel 侧的 API 声明（`DataCopy`、`TQue`、`Pipe`、各种 `AscendC::` 命名空间下的东西）。所以只要它找不到，基本等于"编译器不认识 Ascend C"。

如果 `ASCEND_HOME_PATH` 不是空的，那就往下查两件事：

```bash
ls $ASCEND_HOME_PATH/compiler | head          # 编译器组件在不在
find $ASCEND_HOME_PATH -name "kernel_operator.h" 2>/dev/null | head
```

- 找到头文件但编译找不到 → 环境变量没传给编译进程（下一轮说）
- 压根没有这个文件 → 镜像里的 CANN 装得不完整，是镜像问题，不是你的工程问题

**他**：是空的。我 source 过 `set_env.sh` 啊，是不是这次 CANN 装坏了？

**助手**：不是装坏了，是**环境变量没有跨进程继承**。这是新手最常踩、也最容易自我怀疑的一个坑。

原因很简单：`source` 只影响**当前这个 shell 进程**。而你跑编译的时候，可能是：

- 另一个终端窗口（各自独立）
- IDE 的内置终端（可能是另一套 shell 初始化）
- `bash build.sh` 起的**子进程**——子进程能继承父进程的环境，但如果父进程自己没 source，子进程也没有
- CI 里的非交互 shell（`.bashrc` 可能压根不执行）

所以"我明明 source 过"和"编译时没有"可以同时成立。

三个层次的解法，按场景选：

```bash
# 1. 一次性验证：和 build 写在同一个 shell 里，&& 保证顺序
source /usr/local/Ascend/ascend-toolkit/set_env.sh && bash build.sh

# 2. 长期：写进 shell 初始化文件（注意非交互 shell 读的是 BASH_ENV）
echo 'source /usr/local/Ascend/ascend-toolkit/set_env.sh' >> ~/.bashrc

# 3. CI / Docker：写进 ENTRYPOINT 或启动脚本，别依赖 .bashrc
```

验证是否真的生效，别只看 `echo`：

```bash
bash -c 'echo $ASCEND_HOME_PATH'    # 新起一个子 shell 看，能验出继承问题
```

如果你在 IDE 里，还要单独确认 IDE 的终端用的是哪个 shell、加载了哪个 rc 文件。

**他**：好。不过我先干了个事：把 include 改成绝对路径了，能编过。这样行吗？

**助手**：能编过，但**建议改回去**，这是个会给自己埋雷的做法。

绝对路径的问题不在"现在能不能跑"，而在：

1. **换机器就废**：CANN 装在 `/usr/local/Ascend` 是默认，但不是必然，容器里可能在 `/home/xxx/Ascend`；
2. **换版本就废**：不同 CANN 版本的头文件路径结构会调整；
3. **团队协作失效**：你的路径别人没有，代码一提交，别人全编不过；
4. **掩盖了真正的问题**：真正的问题是环境变量没传递，你只是绕过了它，下次换个子进程还会中招。

正确的做法是先解决环境变量，然后保持 `#include "kernel_operator.h"` 不变。如果确实需要兼容多种安装位置，应该用构建系统传路径，而不是写死：

```cmake
include_directories($ENV{ASCEND_HOME_PATH}/compiler/tikcpp/tikcfw)
```

这样路径来自环境变量，换机器只要环境对就能编。

**他**：改回来变 `undefined reference to 'AscendC::...'` 了。这跟前面那个有关系吗？

**助手**：有间接关系，但不是同一个问题——你现在从"编译期"走到了"链接期"，这说明**头文件找到了、语法过了**，但符号没生成或者没链接上。

`undefined reference` 的典型原因：**kernel 源码被当成普通 C++ 编了**。

Ascend C 的工程是两套编译器在干活：

| 代码 | 编译器 | 目标 |
|---|---|---|
| `op_kernel/` 下的 kernel 实现 | ascendc 编译器（`ccec`） | AI Core（device） |
| `op_host/` 下的 tiling、原型 | `g++` / `clang++` | CPU（host） |

如果 CMake 里把 `*_kernel.cpp` 错放进了 host 目标，g++ 会用系统 ABI 去编它——语法能过（头文件里有声明），但 `AscendC::` 那些函数只有 ccec 才能生成实现，链接时自然找不到。

判断方法：看编译命令行。

```bash
cmake --build build -- VERBOSE=1 2>&1 | grep -E "ccec|g\+\+"
```

命令行里带 `--cce-aicore-arch=dav-2201` 这类参数的，是 ascendc 编译器；只有常规 `-I/-O2/-std=` 的，是 g++。然后对照文件名，看该在 ccec 组的文件是不是跑到 g++ 组去了。

**他**：等等，我 CMakeLists 里怎么知道哪个文件该给谁编？

**助手**：一般不用你手动指定——`msopgen` 生成的模板里已经按目录和文件名约定好了，你要做的是**别破坏这个约定**。

约定大致是：

```
ops/<your_op>/
├── op_host/            → g++ 编
│   ├── <op>_tiling.cpp     tiling 计算
│   └── <op>.cpp            算子原型/注册
└── op_kernel/          → ccec 编
    └── <op>.cpp            kernel 实现
```

几个实操要点：

1. **文件别乱挪**。有人习惯把工具函数抽到 `utils.cpp` 放根目录，结果它被默认归到 host 组，kernel 里引用就链接不上。共用代码要么放头文件（`inline`），要么明确加到 kernel 目标里。
2. **看构建脚本怎么收集文件**。模板里一般是 `file(GLOB ...)` 按目录收集，所以"目录即归属"。
3. **改完 CMakeLists 一定要重新 configure**，`GLOB` 是不会自动感知新文件的：

```bash
rm -rf build && bash build.sh     # 最稳，代价是慢
# 或者
cmake -S . -B build && cmake --build build
```

4. **确认产物形态**：kernel 侧最终应该产出 `.o`（device 二进制），host 侧产出 `.so` 或可执行。如果 `build/` 里只有一个 `.so` 而没有 kernel 的 `.o`，说明 kernel 压根没被 ccec 编。

**他**：我发现 ccec 报错信息特别难读，一堆模板，是我用法不对吗？

**助手**：不是你用法的问题，是**模板 + 宏展开**的固有代价，Ascend C 的 API 大量用了模板和宏（`TQue<QuePosition::VECIN, 2>`、`GET_TILING_DATA` 这类），编译器把展开后的类型原样打出来，可读性就很差。

几个实用技巧：

**1. 只看第一条 error。** 后面 90% 是级联——一个类型推不出来，后面全是"无法匹配"。找到第一条，通常就够定位了。

```bash
bash build.sh 2>&1 | grep -n "error:" | head -3
```

**2. 看 error 里的"最后一行"。** 模板报错是嵌套的，真正的类型不匹配往往在最后一层：

```
error: no matching function for call to 'DataCopy(...)'
  note: candidate template ignored: could not match 'LocalTensor<half>' against 'LocalTensor<float>'
```

最后那句 `could not match ... against ...` 才是真相。

**3. 类型问题先怀疑 dtype。** Ascend C 的 API 是强类型的，`half` 和 `float` 的 `LocalTensor` 不能混用，`T` 模板参数和实际数据不一致就会报一屏。

**4. 缩小到最小复现。** 把报错那段单独抽到一个直调工程里，编一次，比在大工程里改快得多。

**5. 用 `-Wall` 之外别再加花活。** 有些团队开一堆 `-Werror`，模板警告直接变错误，反而挡住真正的 error。

**他**：编过了。顺嘴问一句，我算子叫 `AddCustom`，会不会跟内置 `Add` 撞？

**助手**：`AddCustom` 和 `Add` 不撞，但这个问题问得对——**算子类型名是全局唯一的注册键**，撞了是真会出事的。

撞了会怎样，比报错更麻烦：

- **注册被覆盖**：后注册的赢，你以为在跑自己的实现，其实是别人的；
- **运行时查到内置实现**：`aclnn` 或图引擎按名字找算子，找到的是内置那个，你的自定义实现永远不会被调用；
- **现象**：结果"看起来对"（因为内置也是对的），但你改的代码没生效，白白 debug 半天。

最容易踩的是直接叫 `Add`、`Mul`、`Softmax`、`LayerNorm` 这种通用名。

规范做法：

1. **加团队/项目前缀**：`MyAddCustom`、`xxAddV2`；
2. **三处保持一致**：算子原型注册（`REG_OP`）、`aclnn` 接口名、Python 封装名。只改一处会出现"能编能装但调不到"；
3. **查一下现状**：

```bash
grep -r "REG_OP(AddCustom)" $ASCEND_OPP_PATH/vendors/ 2>/dev/null
```

**他**：那会不会有人已经注册过 `AddCustom`？我在这个镜像里。

**助手**：有可能，尤其是在共享镜像里——别人装过的算子包会留在 `vendors/` 目录下，重启不消失。

查两个地方：

```bash
# 1. 装了哪些自定义算子包
cat $ASCEND_OPP_PATH/vendors/config.ini

# 2. 每个 vendor 里都有什么算子
ls $ASCEND_OPP_PATH/vendors/*/op_impl/ 2>/dev/null
grep -rl "AddCustom" $ASCEND_OPP_PATH/vendors/ 2>/dev/null | head
```

`config.ini` 里的 `load_priority` 决定了加载顺序，同名时优先级高的赢——这意味着即使你装了，也可能被别人的覆盖。这种问题不会报错，只会"行为很奇怪"。

工程上的建议：**镜像里别混装多个团队的自定义算子包**。要么每个项目独立镜像，要么用 `--install-path` 装到项目自己的目录，不要都往默认路径塞。

**他**：装完了，但调用时说算子不存在。

**助手**：装成功和能被找到，是两个阶段。按顺序查三层：

```bash
# 第一层：包装到哪了
cat $ASCEND_OPP_PATH/vendors/config.ini

# 第二层：目录在不在
ls $ASCEND_OPP_PATH/vendors/

# 第三层：符号导出了没有
ls $ASCEND_OPP_PATH/vendors/*/op_api/lib/
nm -D $ASCEND_OPP_PATH/vendors/*/op_api/lib/libcust_opapi.so | grep -i addcustom
```

三层的含义不一样：

- **第一层缺失**：装到了别的路径，`config.ini` 里根本没有你的 vendor；
- **第二层缺失**：装了但没注册到 OPP，通常是 `--install` 时路径不对；
- **第三层缺失**：库在但没导出符号，通常是编译目标不对（比如编了 host 没编 kernel）。

**他**：没有。

**助手**：那基本可以确定是"装到别处去了"。

`.run` 包的默认行为是装到**当前用户目录**（`~/Ascend/...`），而你的 `ASCEND_OPP_PATH` 通常指向 `/usr/local/Ascend/...`——两个路径看起来很像，其实不是一个地方。很多人第一次装完就懵在这。

明确指定路径重装：

```bash
./custom_opp_*.run --install --install-path=$ASCEND_OPP_PATH
```

装完必须**重新 source**，因为环境变量里缓存了路径。然后验证：

```bash
grep -i "customize\|your_vendor" $ASCEND_OPP_PATH/vendors/config.ini
```

还有一个容器场景的坑：**在容器里装、在宿主机上用**（或者反过来）。两边路径字符串一样，但文件系统不同，你以为装了，其实装在了另一侧。

**他**：每次改一行都要重装一遍，太烦了。能不能不装直接跑？

**助手**：能，而且这是我更推荐的工作流——**先用直调跑通逻辑，再打包成算子包**。

直调（direct launch）的意思是：写一个普通的 `main.cpp`，像 CUDA 那样用 `<<<>>>` 直接调 kernel，完全跳过算子原型、tiling 注册、OPP 安装这一整套。

```cpp
// main.cpp
void add_custom_kernel(...);   // kernel 侧的函数声明

int main() {
    AscendC::SetDevice(0);

    aclrtStream stream;
    aclrtCreateStream(&stream);

    // 准备 GM 上的输入输出（host 侧 malloc + copy）
    // ...

    // 直接下发，blockDim 自己指定
    add_custom_kernel<<<blockDim, nullptr, stream>>>(xGm, yGm, zGm, totalLength);

    aclrtSynchronizeStream(stream);
    // 拷回结果、比对
}
```

好处：

- **一次编译一次运行**，几秒钟一轮，不用等打包安装；
- **可以开 CPU 调试**（`ASCENDC_CPU_DEBUG`），先在仿真上跑逻辑；
- **参数是你自己传的**，排障时能精确控制每一维。

代价：直调不经过 OPP，所以**验证不了注册、tiling 下发、aclnn 接口**这些东西。这就是为什么它只能做"前半程"，最终还是得打包验证一次。

**他**：直调是对的，装完就偏。

**助手**：那问题基本锁定在"参数"而不是"kernel 代码"上——同一份 kernel，直调对、打包偏，说明**输入不一样**。按概率排：

**1. tiling 参数不同（最常见）**
直调里 `totalLength` 是你手填的；打包后由 host 的 tiling 函数算出来。如果 tiling 里算错了（尤其是尾块、对齐、`tileNum`），kernel 拿到的切分就是错的。

**2. dtype / shape 不一致**
直调你可能用 fp32 测的，aclnn 那边传的是 fp16；或者 shape 维度顺序不一样。

**3. blockDim 不同**
直调时你可能写死 1，只验证了单核；打包后按 shape 算了多核。

**4. 内存分配方式不同**
直调你自己 malloc，打包后由框架分配，对齐和大小可能不同。

最快的定位方法：**在 kernel 入口打日志，两边对比**。

```cpp
AscendC::printf("blockIdx=%d, totalLength=%d, tileLength=%d\n",
                AscendC::GetBlockIdx(), totalLength, tileLength);
```

两边都打，一比就知道是哪一维对不上。

**他**：找到了，tiling 里 tail 没算对。

**助手**：那就是典型的"直调掩盖了 tiling bug"——因为直调里 tail 是你手算的，绕过了 host 那段代码。

修的方向：tiling 里把 `total` 对 `blockDim` 取余，余数摊到前几个核，并且把 `start/len` 一起写进 `TilingData`，让 kernel 不用再算一遍。同一个分布式逻辑写两遍，必然有一遍会错。

顺便建议：**tiling 单独写单测**。它不依赖 NPU，纯 CPU 就能测：

```cpp
// 给定 total=1002, blockNum=8，验证所有核覆盖 [0,1002) 且不重叠
for (int i = 0; i < blockNum; ++i) { /* 校验 start/len */ }
```

这个测试比在真机上跑快一百倍，而且能覆盖 1、1000、1023 这类边界。

**他**：行，我先把这六步记下来。

**助手**：给你一条完整的链路，以后照着走，每一步都有"可验证的产物"：

```
① 算子原型      REG_OP 定义输入/输出/属性        → <op>.h
② host tiling   计算切分，写 TilingData          → <op>_tiling.cpp
③ kernel 实现   CopyIn → Compute → CopyOut       → <op>.cpp
④ 编译          ccec 编 device + g++ 编 host     → .o / .so
⑤ 打包安装      build.sh → .run --install        → OPP vendors
⑥ 上层调用      aclnn / 图 / PyTorch             → 业务可调
```

每步的"检查点"：

| 步骤 | 检查点什么 |
|---|---|
| ① | 头文件能编过，`REG_OP` 名字唯一 |
| ② | CPU 单测通过（覆盖非整除 shape） |
| ③ | 直调结果与 golden 一致 |
| ④ | `build/` 里同时有 kernel 的 `.o` 和 host 的 `.so` |
| ⑤ | `config.ini` 里有你的 vendor |
| ⑥ | 上层能调到，且结果与直调一致 |

口诀：**头文件找不到看环境变量，符号找不到看 CMake，装完找不到看 config.ini，结果不对看 tiling。**

## 4. 给图像组写的 scale，1000 个元素输出全 0

**他**：`{1,1024}` fp16 结果全对，`{1,1000}` 输出全 0。不报错，不崩。

**助手**：先把两个数算出来：

- `1024 × 2 字节 = 2048`，是 32 的整数倍（2048 / 32 = 64）
- `1000 × 2 字节 = 2000`，不是 32 的整数倍（2000 / 32 = 62.5）

这不是巧合。**`DataCopy` 要求搬运的字节数是 32 字节对齐**，非对齐时不会报错，而是"按整块搬"——多搬或者少搬，结果就是错值或全 0。

fp32 和 fp16 的对齐元素数不一样：

| dtype | 对齐元素数 | 对齐字节 |
|---|---|---|
| fp16 / half | 16 | 32 |
| fp32 / float | 8 | 32 |
| int8 | 32 | 32 |

所以 `1000` 个 fp16 要搬 1000 个元素，但硬件只能按 16 的倍数搬，最后那 8 个元素要么被丢掉、要么被补齐成别的值。

**他**：2000 不是偶数吗？偶数也不行？

**助手**：不行，这里的单位是**字节**，要求是"32 的倍数"，不是"2 的倍数"。

2000 是偶数，说明它能被 2 整除，但它除以 32 余 16。硬件发起 DMA 时按"块"走，块大小是 32 字节，所以它只能搬 62 块（1984 字节）或者 63 块（2016 字节），前者少了 16 字节，后者多了 16 字节。

这也解释了为什么你会看到"全 0"而不是"错一点点"：少搬的那部分，UB 里是未初始化的值；如果后面没写回，或者写回时被截断，输出就整块是 0。它不会给你一个"部分正确"的结果，因为 DMA 是按块工作的，一块不对就是一块全不对。

**他**：哦，那我这个 1024 的 case 是不是也危险？它只是碰巧对？

**助手**：对，**碰巧**。`1024 × 2 = 2048`，正好 64 块，一块不多一块不少，所以从来没有暴露过问题。

这其实是更值得警惕的事：**你现在测过的所有对齐 shape，都不能证明代码是对的**。它们只证明了"在对齐的情况下能跑"。

真正的结论是：

- 只要总字节数不是 32 的倍数，就可能出错；
- 出错的方式不止"全 0"，还可能是"后半段是脏数据""结果整体偏移几个元素"；
- 而 32 的倍数这个条件，取决于 **shape × dtype**，改个 dtype 就全变了（fp16 的 1024 对，换成 fp32 的 1024 就不是 32 倍数了吗？其实 1024×4=4096 也行，但 1000 就是 4000，也不行）。

所以判断标准不是"我测过 1024 没问题"，而是"我要保证任何 shape 都不越界"。这就是下面 `DataCopyPad` 的作用。

**他**：那改 `DataCopyPad`。是不是所有地方都换成 Pad 就行？

**助手**：搬运层可以全换，但**计算层不能跟着全换**，这是两件事。

先看写法：

```cpp
// GM → UB，len 是真实元素数，不要求 32B 对齐
DataCopyExtParams copyParams{
    1,                                        // blockCount：搬几"行"
    static_cast<uint32_t>(len * sizeof(T)),   // blockLen：真实字节数
    0,                                        // srcStride
    0,                                        // dstStride
    0                                         // rsv
};

DataCopyPadExtParams<T> padParams{
    true,   // isPad：是否用指定值填充
    0,      // leftPadding
    0,      // rightPadding
    0       // paddingValue：isPad=true 时生效
};

DataCopyPad(xLocal, xGm[offset], copyParams, padParams);
```

注意两个细节：

1. `blockLen` 是**字节数**，不是元素数。传错了会搬多或搬少。
2. `isPad = true` 时，补的位置用 `paddingValue` 填；`isPad = false` 时由框架决定（通常是补第一个元素的值，或者随机值，取决于有没有 left/right padding）。**归约类算子绝对不能依赖默认填充值**，因为它是不可控的。

**他**：搬 1000 个可能实际搬了 1024 个，多出来的 24 个参与计算怎么办？

**助手**：这是关键问题，分两类处理：

**逐元素算子**（scale、add、relu、sigmoid）：

多算几个位置无所谓，只要满足两个条件——

- 这些位置的**输入不是脏数据**（Pad 已经用固定值填了，所以是安全的）；
- **输出按真实长度写回**，多余部分不要落盘（CopyOut 时用真实 `len`）。

所以逐元素算子只需要改搬运，计算逻辑完全不用动。

**归约 / 归一化算子**（sum、max、softmax、layernorm）：

这里 pad 值会**污染结果**。比如你搬了 1024 个元素，其中 24 个是填充的，做 sum 的时候会被加进去，结果直接偏大。

两个解法：

```cpp
// 方案 A：只处理真实长度
for (int i = 0; i < realLen; ++i) sum += xLocal[i];   // 不遍历 padding 区

// 方案 B：用 mask 关掉尾巴（当计算必须整块进行时）
// 通过 repeatTimes / mask 控制参与计算的 lane
```

判断标准一句话：**这个算子会不会"跨元素"**。会（sum/max/softmax/layernorm），就必须管 pad；不会（逐元素），可以不管。

**他**：我全换了，1024 那个 case 反而慢了 20%。

**助手**：符合预期，原因有两个，都能定位：

**1. 主块本来是对齐的，走 `DataCopyPad` 反而多了一层处理。** `DataCopyPad` 内部要做长度判断、补齐、边界处理，对齐场景下这些是纯开销。

**2. tiling 可能让尾块占比变高了。** 如果你的 tile 设得小，每个 tile 都带一点尾巴，Pad 的调用次数就上去了。

处理方式是按块分两条路径：

```cpp
if (isTail) {
    DataCopyPad(xLocal, xGm[offset], copyParams, padParams);   // 尾块
} else {
    DataCopy(xLocal, xGm[offset], tileLen);                    // 主块，对齐
}
```

经验上这个组合能把损失压到 1% 以内。如果还是慢，先确认 tile 有没有跟着调大——**尾块少、主块大**才是目标，而不是"每个块都小心翼翼地 Pad"。

**他**：那我 shape 要是有 100 万呢，尾块占比很小，是不是就无所谓了？

**助手**：对，尾块占比越小，影响越小。100 万个元素里最后差 24 个，占比 0.0024%，可以忽略。

但这里有个反直觉的点：**大 shape 的瓶颈往往不是尾块，而是切分粒度**。

- 100 万元素，如果 tile 是 8K，就是 122 个 tile，每个 tile 都有一次 DMA 启动，启动开销会累积；
- 如果 tile 是 64K，只有 16 个 tile，启动开销小，但 UB 占用高，队列深度就得降。

所以大 shape 的优化方向是"tile 调大 + 队列深度 2"，而不是"尾块处理"。你现在的 20% 性能损失大概率也在 tile 上，不在 Pad 上——可以做个对照：只把主块改回 `DataCopy`，尾块保持 Pad，看掉多少。

**他**：还有个事我先不问性能了——我怎么确认写回没踩到别人？

**助手**：用**哨兵值（canary）**，这是最便宜也最直接的办法。

思路：在输出 tensor 的前后各留一段"不该被写"的内存，填上一个特殊值，跑完检查它有没有变。

```cpp
// 1. 分配时多留 64 字节
size_t outBytes = total * sizeof(T);
void* outGm = nullptr;
aclrtMalloc(&outGm, outBytes + 128, ACL_MEM_MALLOC_HUGE_FIRST);

// 2. 前后各填 64 字节的魔数
//    建议用 0x5A5A5A5A 这类"不像正常数据"的值

// 3. 跑完检查
for (int i = 0; i < 16; ++i) {
    if (guard[i] != 0x5A5A5A5A) {
        std::cout << "写越界！位置 " << i << std::endl;
    }
}
```

**他**：魔数填什么好？0 行吗？

**助手**：不建议用 0。原因是**0 本身就是很常见的数据**（初始化、padding、relu 的负半轴都是 0），一旦越界写进去的还是 0，你就检测不出来。

推荐几种：

| 值 | 适用场景 |
|---|---|
| `0x5A5A5A5A` | 通用，不像正常浮点/整数 |
| `0xDEADBEEF` | 调试常用，一眼能认出来 |
| `0xCDCDCDCD` | MSVC 的未初始化堆标记，熟悉的人一看就懂 |

如果是 fp16 数据，注意这些魔数解释成 half 会变成 NaN 或者极小的数，正好——**NaN 在计算里会传播**，如果你看到输出里有 NaN，也可能是在提示越界。

**他**：我试了，确实被改了。说明写越界。

**助手**：那基本可以定位到 `CopyOut`。两个常见原因：

**1. 写回长度超了。** 你按 `tileLen` 搬，但最后一个 tile 的真实数据只有 `realLen`，多写的部分就踩到后面去了。

**2. GM 侧目标地址没对齐。** 非对齐写会触发硬件的边界处理，可能多写一个块。

修法：

```cpp
// CopyOut 也用 Pad，它会自动丢弃 dummy
DataCopyPad(yGm[offset], yLocal, copyParams);   // blockLen = realLen * sizeof(T)
```

`DataCopyPad` 在 UB → GM 方向会自动裁掉补齐的部分，所以你只要保证 `blockLen` 填的是真实字节数就行。这一点比 CopyIn 省心。

**他**：改完哨兵没动了。不过我发现一个怪事：CPU 调试里 1000 一直是对的。

**助手**：这个不怪，是两类验证的边界不同。

**CPU 调试（仿真）**：模拟器逐字节搬，它不模拟 DMA 的 32 字节块约束，所以你写 2000 字节它就老老实实搬 2000 字节，看起来一切正常。

**真机**：DMA 按块发起，2000 字节只能搬 62 块或者 63 块，多出来或少掉的部分就出问题。

所以正确的理解是：

| 验证方式 | 验证什么 | 不验证什么 |
|---|---|---|
| CPU 调试 | 公式、循环、分支、边界条件 | 对齐、UB 容量、同步、多核 |
| 真机 | 硬件约束、性能、并发 | — |

**仿真过、真机挂，优先怀疑对齐和容量**，不要去改算法。反过来，真机过、仿真挂，那才是逻辑有问题。

**他**：那我以后是不是都得上真机验一遍？仿真就没意义了？

**助手**：不是，两层都要，只是分工明确。

仿真很快，适合高频迭代——你改一版算法，先仿真跑 100 个 case，几分钟就能过一遍。如果这层就挂了，根本不用上真机。

真机慢，适合低频验证——每完成一个里程碑，跑一遍完整用例，重点验"硬件相关"的部分。

一个实用的流水线是：

```
改代码 → 仿真跑小 case（秒级）→ 仿真跑全 shape（分钟级）
      → 上真机跑核心 case（含非对齐、大 shape、多核）
      → 打包后跑一次回归
```

关键是**别把仿真当准出**。它的定位是"快速反馈"，不是"最终验收"。

**他**：行。我顺便把 1023 和 1 也加进用例了，跑出来 1023 果然也挂。

**助手**：这个结果很有价值——**1023 挂说明是"差一个"类问题，不是"完全不对"**。

它给了两个信息：

1. 你的实现是"长度整除时对，不整除时错"，说明逻辑主体没问题，问题在边界；
2. 1023 比 1000 更极端（只差 1 个元素），能暴露"尾块判断写错"这类 bug——比如 `if (len % 16 == 0)` 写成了 `!=`。

建议把边界用例固化成一组，以后每个新算子都跑：

```
1        # 最小，验证不崩
15 / 16  # 对齐边界两侧
1000     # 非对齐
1023     # 差一个
1024     # 对齐
10000    # 稍大，验证 tiling 分块
```

六个 case，跑一遍几十秒，能挡掉大部分"上板才发现"的问题。

## 5. Ascend C 的 API 到底分几层

**他**：看文档的时候一会儿基础 API，一会儿高阶 API，还有语言扩展层、框架接口。这几个到底是什么关系？我该从哪一层开始写？

**助手**：四层，从"最贴近硬件"到"最贴近业务"，越往上越好用、越往下越可控：

| 层 | 内容 | 典型东西 | 什么时候用 |
|---|---|---|---|
| 语言扩展层 | 修饰符、地址空间 | `__global__` `__aicore__` `__gm__` `__ubuf__` | 写 kernel 声明、标地址空间 |
| 基础 API | 内存、向量、矩阵、设备 | `DataCopy`、`VecAdd`、`Mm`、`GetBlockIdx` | 需要精确控制搬运/计算/切分 |
| 高阶 API | Kernel 级封装 | Matmul、Softmax、LayerNorm 等 | 标准形态的算子 |
| 框架/调用接口 | 算子注册、aclnn | `REG_OP`、aclnn 两段式 | 让上层能调到你的算子 |

一条经验：**能用上层就别下沉**。高阶 API 是"别人已经调优过的实现"，你手写大概率不会更快，但一定会更容易出错。

**他**：语言扩展层那些下划线修饰符，到底影响什么？我看代码里到处都是。

**助手**：它们主要在标两件事：**这段代码跑在哪**、**这个指针指向哪块内存**。

```cpp
__global__ __aicore__ void my_kernel(GM_ADDR x, GM_ADDR y) {
    // __global__  ：这是一个 device 侧入口函数
    // __aicore__  ：运行在 AI Core 上（不是 host）
    // GM_ADDR     ：指向 GM（全局内存）的地址
}
```

几个常见修饰：

| 修饰 | 含义 | 影响 |
|---|---|---|
| `__global__` | kernel 入口 | 只能由 host 侧启动 |
| `__aicore__` | 在 AI Core 上执行 | 不能调用 host 库函数 |
| `__gm__` | 指针指向 GM | 访问延迟高，要配合搬运 |
| `__ubuf__` | 指针指向 UB | 访问快，容量小 |
| `__aicore__ inline` | 内联到 kernel | 减少函数调用开销 |

最容易犯的错是**把 host 代码写进 `__aicore__` 函数**——比如 `std::cout`、`printf`（除非用 `AscendC::printf`）、`new`、异常。编译器可能不报错，但运行时会挂。

**他**：基础 API 那四类（Memory / Vector / Cube / Device）怎么分？

**助手**：按"操作的是什么"分：

| 类别 | 干什么 | 典型接口 |
|---|---|---|
| Memory | GM↔UB、UB↔L1 的搬运和分配 | `DataCopy`、`DataCopyPad`、`TBuf`、`TQue` |
| Vector | 逐元素/归约计算 | `Add`、`Muls`、`Exp`、`ReduceSum`、`Cast` |
| Cube | 矩阵乘 | `Mm`、`LoadData`、矩阵相关 |
| Device | 设备/核级信息与控制 | `GetBlockIdx`、`GetBlockNum`、`SyncAll` |

写一个 elementwise 算子，你基本只会碰 Memory + Vector + Device 这三类，Cube 不用管。写 Matmul 才会大量用 Cube，并且要管 L1/L0 的搬运。

**他**：那 TQue 和 TBuf 属于哪一层？

**助手**：属于**基础 API 的 Memory 类**，但它们是"管理方式"，不是"搬运操作"。

三者的关系：

```
TBuf / TQue   —— 管"内存块怎么分配、怎么复用"
DataCopy      —— 管"数据怎么从 A 搬到 B"
```

| | TBuf | TQue |
|---|---|---|
| 是什么 | 裸内存块 | 带同步语义的队列 |
| 同步 | 自己做 | `EnQue/DeQue` 自动 |
| 复用 | 自己管生命周期 | 深度控制 |
| 适合 | 需要精细复用、临时 buffer | 标准的生产者-消费者流水 |

选型建议：**默认用 `TQue`，需要复用同一块内存做中间计算时用 `TBuf`**。用 `TBuf` 就要自己负责同步，这一点前面聊过。

**他**：高阶 API 会不会限制优化？我总觉得用别人的封装做不了极致性能。

**助手**：会有一定限制，但**大部分场景下这个限制不成立**，原因有两个：

1. 高阶 API 本身就是针对标准形态调优过的，你没那么容易超过它；
2. "极致性能"通常来自切分和流水，而这些高阶 API 内部已经做了。

真正受限的场景是：

- **特殊融合**：比如 bias + 激活 + 量化的组合，高阶 API 覆盖不到；
- **非标准 shape**：某些 shape 下高阶 API 的切分不是最优；
- **特殊数值要求**：需要自定义累加顺序或精度处理。

判断顺序：**先用高阶 API 拿基线 → profiling 看差在哪 → 再有针对性地下沉**。一上来就手写全套流水，通常会在同步和精度上耗掉几周，最后性能还没高阶 API 好。

**他**：那什么情况下必须下沉到基础 API？

**助手**：五种，都是"高阶 API 表达不了"的情况：

1. **自定义融合逻辑**：多个算子的组合，没人封装过；
2. **非标准数据布局**：stride、广播方式很特殊；
3. **需要精确控制流水**：手工多级流水、跨 pipe 精细重叠；
4. **特殊数值算法**：比如 online softmax、Welford 这类增量算法；
5. **性能瓶颈明确在高阶 API 内部**：profiling 证明，并且你确认能改得更好。

反过来说，**只要不属于这五类，就不要手写**。

**他**：我发现同一件事有好几种写法，比如 `DataCopy` 和 `DataCopyPad`、`ReduceSum` 和手写循环。这种怎么选？

**助手**：选择标准是"**语义匹配度**"，不是"哪个高级"。

| 场景 | 选什么 | 为什么 |
|---|---|---|
| 长度可能非 32B 对齐 | `DataCopyPad` | `DataCopy` 会截断或错位，且不报错 |
| 严格对齐、追求极致 | `DataCopy` | 少一层边界处理 |
| 标准归约 | `ReduceSum` 等 | 一条指令，比手写循环快 |
| 需要特殊累加顺序/精度 | 手写循环 | 归约 API 的顺序不可控 |

有个实用原则：**先选"能处理最坏情况"的那个**（比如 `DataCopyPad`），跑通之后再针对热点路径换成特化版本。反过来（先特化，出问题再补）很容易漏掉边界。

**他**：那这几层混用会有问题吗？

**助手**：语法上没问题，但要注意两个隐性冲突：

**1. 同步语义不一致。** 高阶 API 内部可能已经做了同步，你在外面再加一层，可能重复，也可能打乱它的流水。

**2. buffer 归属冲突。** 高阶 API 会用自己的一块 UB/L1，如果你在外面又申请了同名 buffer，可能超出容量。

稳妥做法：**同一个函数里尽量只用一层**。要混用时，先确认高阶 API 的 buffer 预算和同步行为。

**他**：有没有一个"最小可用组合"，让我先把东西跑起来？

**助手**：有，elementwise 类算子的最小组合就这些：

```cpp
// 1. 开流水
TPipe pipe;

// 2. 建队列（Memory 类）
TQue<QuePosition::VECIN, 2> inQueue;
TQue<QuePosition::VECOUT, 2> outQueue;

// 3. 计算 buffer 大小并初始化
pipe.InitBuffer(inQueue, 2, tileBytes);
pipe.InitBuffer(outQueue, 2, tileBytes);

// 4. 主循环
for (int i = 0; i < tileNum; ++i) {
    LocalTensor<T> x = inQueue.AllocTensor<T>();
    DataCopyPad(x, xGm[offset], params);      // Memory
    inQueue.EnQue(x);

    LocalTensor<T> in = inQueue.DeQue<T>();
    LocalTensor<T> out = outQueue.AllocTensor<T>();
    Muls(out, in, scale);                      // Vector
    outQueue.EnQue(out);
    inQueue.FreeTensor(in);

    LocalTensor<T> y = outQueue.DeQue<T>();
    DataCopyPad(yGm[offset], y, params);
    outQueue.FreeTensor(y);
}

// 5. 核编号（Device）
int64_t blk = AscendC::GetBlockIdx();
```

这五行骨架（队列、搬运、计算、回写、核编号）覆盖了 80% 的算子。高阶 API 只是把中间那段换成一次调用。

**他**：那我应该按什么顺序学这几层？

**助手**：从"能跑"到"能调"，四步：

| 步 | 学什么 | 验证 |
|---|---|---|
| 1 | 语言扩展层 + 最小骨架 | 能写一个直调的 vector add |
| 2 | 基础 API 的 Memory + Vector | 能处理非对齐 shape |
| 3 | 高阶 API | 能用 Matmul/Softmax 拼出一个算子 |
| 4 | 下沉与调优 | 能定位"为什么比高阶 API 慢" |

**别跳过第 2 步**。很多人直接上高阶 API，跑通了但一出问题就抓瞎——因为不知道底层在干什么。第 2 步的意义是建立"搬运-计算-同步"的直觉。

**他**：最后一个，实际写的时候，怎么快速判断该用哪层？

**助手**：一个决策树，从上往下问：

```
1. 是不是标准形态（Matmul/Softmax/LayerNorm/Gelu）？
   → 是：用高阶 API，别手写
   → 否：往下

2. 是不是"多个标准算子 + 简单组合"？
   → 是：先试高阶 API 拼装，不够再下沉
   → 否：往下

3. 有没有特殊数值算法 / 非标准布局 / 精细流水需求？
   → 有：基础 API 手写
   → 没有：回到 1，你可能想复杂了
```

大部分人卡在"我是不是该手写"，其实答案多半是"不该"。**先让系统跑起来，再让系统跑得快**——这个顺序反过来会浪费大量时间。

## 6. 推荐组的 ReduceSum，多核偶发错

**他**：`blockDim=8`，结果偶发错，错的位置还不固定。重跑有时候全对。

**助手**：这个现象——**偶发 + 位置不固定**——基本可以排除"算法写错"（算法错会稳定复现），指向**竞争类问题**。

按概率排，三类：

1. **切分错误**：相邻核的区间重叠或漏算（这类通常是稳定错，但你如果同时有下面的问题，就会看起来随机）；
2. **同步缺失**：部分和写进 workspace，还没写完就有核去读；
3. **数据竞争**：多个核写同一块 workspace 地址。

第一件事不是猜，是**二分**：把 `blockDim` 改成 1，跑一遍。

- 单核稳定正确 → 问题在"切分"或"核间"
- 单核也错 → 是算法或搬运问题，方向完全不同

**他**：单核是对的。不过我只测了小 shape，1×1024 那种。

**助手**：这个补充很关键——**小 shape 的单核测试，证明力有限**。

原因是流水重叠：shape 小的时候，搬运还没开始多久就算完了，`CopyIn → Compute → CopyOut` 几乎是串行的，危险窗口根本不会出现。同步类 bug 在这种场景下**天然隐身**。

所以要把测试矩阵补全：

```
单核 + 小 shape     → 验证算法逻辑
单核 + 全 shape     → 验证 tiling 边界（余数、尾块）
多核 + 小 shape     → 验证切分与同步
多核 + 全 shape     → 验证负载均衡与容量
```

你现在只做了第一格。先补第二格：单核 + 你的真实 shape，如果这里就错了，问题在 tiling；如果对，再进第三格。

**他**：全 shape 也过了。那是不是硬件有问题？这台机器之前报过 Warning。

**助手**：先别往硬件上想，概率很低，而且会把你带偏。

硬件出问题的表现通常是**固定的**：某个核永远算错、某段地址永远读不对、错误码稳定出现。你现在是"偶发、位置不固定"，这更像软件时序问题。

判断硬件有没有问题，有个很便宜的验证：**跑一个已知正确的官方样例**（比如 vector add 的直调例子）。它过了，说明卡和驱动基本正常；它挂了，再谈硬件。

排除硬件之后，回来查切分。打印每核的区间：

```cpp
AscendC::printf("block %d: start=%ld, len=%ld\n",
                AscendC::GetBlockIdx(), start, len);
```

检查两件事：**首尾相接无空洞**、**互不重叠**。这一步用 printf 十分钟能查完，比读代码快。

**他**：打出来了，第 7 核的 end 是 1002，但 total 也是 1002，看着没问题。等等，第 0 核到第 6 核每核 125 个，7×125=875，最后只有 127……

**助手**：你算到关键点了。让我把你的数摆开：

- `total = 1002`，`blockNum = 8`
- `perCore = 1002 / 8 = 125`（整除，余 2）
- 前 7 个核（0~6）各 125 个，覆盖 0~874
- 第 7 核如果也是 125 个，覆盖 875~999
- **剩下 1000、1001 这 2 个元素没人管**

所以第 7 核的 `end` 应该是 1002 才对，而不是 1000。你打印出来是 1002，说明你这个 case 的 `len` 可能是特殊处理的（或者是另一段代码算的）——建议把 `start/len` 的**计算代码**贴出来看，别只看打印值。

标准写法是把余数摊到前几个核：

```cpp
int64_t perCore = total / blockNum;
int64_t tail    = total % blockNum;

// 前 tail 个核各多拿 1 个
int64_t start = blockIdx * perCore + std::min<int64_t>(blockIdx, tail);
int64_t len   = perCore + (blockIdx < tail ? 1 : 0);
```

验算一下：

| block | start | len | 覆盖 |
|---|---|---|---|
| 0 | 0 | 126 | 0–125 |
| 1 | 126 | 126 | 126–251 |
| 2 | 252 | 126 | 252–377 |
| … | … | … | … |
| 6 | 752 | 125 | 752–876 |
| 7 | 877 | 125 | 877–1001 |

总额 1002，无缝无重叠。

**他**：哦，我总算明白了。改完还对吗？我加了 `SyncAll()` 之后更奇怪了，有时候直接挂住。

**助手**：挂住是个有价值的信号——它通常说明**同步配对不上**，而不是数据错了。

`SyncAll` 的语义是"所有核都到这里，再一起往下走"。所以它要求：

1. **每个核都必须执行到它**。如果有核走了 `if` 分支没进同步，其他核就会永远等；
2. **次数要一致**。循环里同步 3 次 vs 4 次，就会错位；
3. **地址要一致**。底层的跨核同步需要一个约定的通信地址，没设或者设错，各核同步的不是同一件事。

检查代码里这三处。最常见的写法错误是：

```cpp
if (blockIdx == 0) {
    // 只有 0 号核做事
    ...
    AscendC::SyncAll();      // 其它核没进来 → 死锁
}
```

正确做法是让同步在所有核上对称执行：

```cpp
// 所有核都写自己的槽位
workspace[blockIdx * sizeof(float)] = partialSum;

// 所有核都到这里
AscendC::SyncAll();

// 之后才分叉
if (blockIdx == 0) {
    // 汇总
}
```

**他**：我是先写 workspace 再 SyncAll，然后 0 号核汇总。应该都走了吧。

**助手**：结构是对的。那往下查两个更隐蔽的点：

**1. workspace 有没有清零。**
如果 workspace 是复用的（跨调用、跨批次），上一轮残值会被当成这一轮的部分和加进去。现象是"结果偏大、偶尔偏"。

**2. 同步基地址有没有设置。**
跨核同步不是凭空实现的，它需要一块约定的通信区。这块区域由你（或框架）指定，没指定时各核可能在不同地址上"等"，看起来同步了，其实没同步。

清零的写法：

```cpp
// 每核写之前先写 0（最保险），或者首核统一清零后再 SyncAll
workspace[blockIdx * sizeof(float)] = 0;
AscendC::SyncAll();
workspace[blockIdx * sizeof(float)] = partialSum;
AscendC::SyncAll();
```

两次同步看起来啰嗦，但能彻底排除"读到上一轮"的可能。调通之后再合并。

**他**：好。顺便问一句，workspace 到底是谁分配的？我一直以为是框架给的。

**助手**：**是你自己分配的**，或者由上层传给你。框架不会凭空给你一块。

常见两种形态：

```cpp
// 形态 A：调用方分配，传指针进来（推荐，生命周期清晰）
kernel<<<blockDim, nullptr, stream>>>(xGm, yGm, workspaceGm, totalLen);

// 形态 B：kernel 内部用 GM 上的一块临时区（需要按 blockNum 预留）
```

长度要按 `blockNum × 每核槽位` 算，不能只给一个 float：

```cpp
size_t wsBytes = blockNum * sizeof(float);   // 每核一个槽位
```

槽位必须**按核独立**，这是"不竞争"的根本：

```cpp
workspace[blockIdx] = partialSum;        // 对
workspace[0] += partialSum;              // 错，所有核抢同一个地址
```

第二种写法就是典型的竞争，结果完全不可预测。

**他**：那为什么错的位置不固定？如果是漏算，应该每次都错同一个位置吧。

**助手**：好问题，这说明你在把两种不同的机制拆开看。

**漏算**是确定性的：余数没分配，那个位置永远不参与计算，所以**每次都错同一个位置**，而且错的值有规律（比如比正确值小）。

**竞争**是随机的：谁先写、谁后读，取决于调度，所以**错的位置和值每次都不同**。

你现在看到"位置不固定"，说明至少有竞争。但你也可能同时有漏算——只不过漏算被竞争掩盖了：竞争让结果乱掉，你就看不出"某个位置总是少一点"。

所以正确的做法是**先修确定性的，再修随机的**：

1. 先修切分（余数），让单核和多核在"理想时序"下结果一致；
2. 再修同步（清零、基地址、配对），消除随机性；
3. 最后用重复跑验证。

**他**：怎么区分？

**助手**：打每核的部分和，跑 5 次，看它稳不稳。

```cpp
AscendC::printf("block %d partial=%f\n", AscendC::GetBlockIdx(), partialSum);
```

判读规则：

| 现象 | 结论 |
|---|---|
| 每次部分和都不一样 | 有竞争（读到脏数据，或写冲突） |
| 部分和稳定，但总和不对 | 汇总逻辑错（读的顺序、槽位、清零） |
| 部分和稳定且正确，只有最终输出偶发错 | 写回阶段的问题（CopyOut 与同步的先后） |

这个表能帮你把"哪一层不稳定"钉死。**在不确定层级时改代码，只会引入第二个 bug。**

**他**：我跑了，部分和每次都不一样。所以是竞争。

**助手**：那就锁定在写/读 workspace 这一段。

按这个顺序改，一次只改一处：

1. **槽位独立**：`workspace[blockIdx * sizeof(float)]`
2. **清零**：写之前先 0，或首核清零 + 同步
3. **同步基地址**：确认设置正确
4. **同步位置**：在所有核写完**之后**、汇总读**之前**

改完跑 20 次，每次结果哈希一致才算过。

**他**：clear 了，跑 20 次都一致。不过我发现 7 号核基本没干什么活，这个能优化吗？

**助手**：能，但先确认真的是"没活干"，而不是"干得慢"。

两个不同的问题：

- **负载不均**：尾核拿到的元素少（比如 1002 个元素分 8 核，某些核 125、某些 126）；
- **木桶效应**：整体时间由**最慢的核**决定，所以哪怕只差一个元素，也会被放大成"其他核在等"。

优化方向按成本排：

1. **余数均摊**（你现在的写法）——代价几乎为零，已经把差距压到 1 个元素；
2. **动态 blockDim**：`total` 小时直接减少核数，别让 8 个核抢 3 个元素；
3. **两级切分**：大块按核分，核内再按 UB 分块，减少核内串行。

第 1 条有个反直觉的点：把余数全给最后一个核，会让它明显变慢，整体时间反而更长。**均摊比集中好**，哪怕代码看起来不那么"整齐"。

**他**：先不管了，能跑对就行。我把这个 case 写进测试了。

**助手**：行。补一句测试的建议：**这个 case 要跑够次数**。

竞争类 bug 的特点是"概率性"，跑 1 次通过没有意义。建议：

```bash
for i in $(seq 1 50); do
    ./run_test --case reduce_1002 > out.txt
    md5sum out.txt   # 50 次哈希必须完全一致
done
```

再加一条：**同时跑多个进程/多个核**，模拟真实负载。单进程跑 50 次全过，不代表多进程并发时也过。

## 7. 模型组的 Softmax，FP16 差一点点

**他**：Softmax fp16，MARE 3.2e-3，验收线 1e-3。fp32 就完全过。

**助手**：先给结论：**这不是算法错，是数值精度问题**。判断依据就是你说的那句"fp32 完全过"——同一个算法，换精度就过，说明逻辑链路是对的，误差来自数值表示和运算顺序。

fp16 只有约 3–4 位有效数字（尾数 10 位），Softmax 里恰好有三处会把它放大：

| 位置 | 为什么放大 | 典型表现 |
|---|---|---|
| `exp` 之前没减 max | 结果挤在稀疏区间，尾数不够用 | 大值区误差明显 |
| `sum` 用 fp16 累加 | 大数吃小数，长序列尤其严重 | 序列越长错越多 |
| 最后的除法用 fp16 | 除法误差比乘法大 | 整体性偏移 |

**建议先做最小实验**：只把 sum 改成 fp32 累加，别的都不动，看 MARE 掉到多少。这一步能告诉你误差主要来自哪里，比一次性全改更好定位。

**他**：我把 sum 改成 fp32 了，掉到 1.8e-3。还差一截。

**助手**：这个结果其实很有信息量——**改一处掉了 44%**，说明 sum 是主要贡献者之一，但还有别的。

剩下的一截大概率在 `exp` 前后。先确认一件事：**exp 之前有没有减 max**。

**他**：减了啊，我一开始就减了。

**助手**：那贴一段代码给我看看，顺序经常出错。

**他**：

```cpp
Exp(xLocal, xLocal, len);
ReduceMax(maxVal, xLocal, len);
... 减 max ...
```

**助手**：找到了——**顺序反了**。

你现在是"先 exp，再找 max，再减"。这时候减掉的 max 是 `exp` 之后的最大值，而不是原始输入的最大值。数学上这已经不是标准的 softmax 了。

正确顺序是：

```cpp
// 1. 先找原始输入的 max
ReduceMax(maxVal, xLocal, len);

// 2. 减掉它（结果落在 (-∞, 0]）
Muls(xLocal, xLocal, -1.0f);
Adds(xLocal, xLocal, maxVal);      // 等价于 x - max

// 3. 再 exp（结果落在 (0, 1]）
Exp(xLocal, xLocal, len);

// 4. 再求 sum、再除
```

这样改完，你之前的 fp16 累加 fallback 才有意义——因为 exp 的输入范围被压到了 `(-∞, 0]`，输出在 `(0, 1]`，这是 fp16 表示最密的地方。

**他**：哦……那就是 `x - max` 之后再 exp。不过我不是很确定，这个减 max 到底是为了防溢出还是为了精度？我一直当成防溢出。

**助手**：**两个都是**，而且精度这一面经常被忽略。

**防溢出**：`exp(x)` 在 fp16 下，x 大约超过 11 就溢出成 Inf（fp16 最大值 65504，ln(65504) ≈ 11.09）。真实数据里 logits 到 20、30 很常见，不减 max 必然溢出。

**保精度**：如果不减，`exp` 的结果可能分布在 `[1, 65504]` 这个大范围里，fp16 在这个区间的**绝对间隔**已经很大（比如接近 65504 时，间隔是 32）。你后面做 sum、做除法，有效位数就不够了。

减掉 max 之后，所有结果都落在 `(0, 1]`。这个区间的 fp16 间隔非常细，相对误差能小一到两个数量级。

所以严格说：**减 max 是"必须做"的标准步骤，不是可选的优化**。很多框架的 softmax 实现里，这一步是写死的。

**他**：明白了。改完 1.1e-3。这个算过还是不过？差一点点。

**助手**：这个要看你们的验收口径，但我建议**不要卡在边界上过**。

原因有三个：

1. **1.1e-3 vs 1e-3 只差 10%**，不同输入分布、不同硬件批次，结果会浮动，这次过下次就不过；
2. **验收通常跑多组 case**，你这一组 1.1e-3，说明别组可能更差；
3. **下游模型可能放大误差**，softmax 的输出又会被后续层使用。

再压一档的思路（成本从低到高）：

- 把 `exp` 之后的累加、除法都放在 fp32 上做（只转中间量，不转存储）；
- 检查 `Cast` 的 `RoundMode` 是不是用的 `CAST_ROUND`；
- 如果长序列，考虑分块累加，减少"大数吃小数"。

**他**：我看报告里还有 MERE，那个也要看吗？

**助手**：要，而且**两个数一起看才有诊断价值**。

| 指标 | 定义 | 敏感于 |
|---|---|---|
| MARE | 每个元素的相对误差取绝对值再平均 | 大误差（离群点） |
| MERE | 相对误差的中位数 | 典型元素 |

组合起来能区分三种情况：

| MARE | MERE | 说明 | 优化方向 |
|---|---|---|---|
| 高 | 低 | 少数元素炸了 | 查边界值、除零、极值 |
| 高 | 高 | 整体精度不足 | 提高中间量精度 |
| 低 | 高 | 不太可能，通常是数据问题 | 检查输入 |

你现在的 1.1e-3 如果 MERE 很低（比如 3e-4），说明大部分元素已经很好，只是少数点被放大——那 Epsilon 或边界处理就是重点，而不是整体提精度。

**他**：那我要是把中间量都换成 fp32，能压到多少？

**助手**：通常能到 1e-3 以下，具体看你的序列长度。经验上：

- 短序列（< 1024）：fp32 累加后一般能到 3e-4 量级；
- 长序列（> 4096）：还要注意累加顺序，分块归约比顺序累加稳。

但注意**只转必要的中间量**：

```cpp
// 推荐：累加器 fp32，输入仍是 fp16
float sum = 0.0f;
for (int i = 0; i < len; ++i) sum += static_cast<float>(xLocal[i]);

// 不推荐：整块转 fp32 再算
Cast(yLocal, xLocal, RoundMode::CAST_NONE, len);   // 多占一份 UB，多一次读写
```

**他**：为什么？全 fp32 不是更稳吗。

**助手**：稳，但**代价是两方面的**，而且往往不划算：

**1. UB 占用翻倍。** fp16 的 tile 是 16KB，转成 fp32 就变 32KB。UB 就那么大，tile 变小 → 搬运次数变多 → 整体变慢。

**2. Vector 吞吐下降。** 一条向量指令处理 fp32 的元素数大约是 fp16 的一半。计算密集的算子会明显变慢。

更关键的是：**大部分误差只来自少数几个点**（累加、除法、指数），不需要把所有数据都升级。这就是"混合精度"的由来——**关键路径 fp32，存储保持 fp16**。

具体到 Softmax，必须 fp32 的只有：`sum`、除法、以及可能的 `max`。输入输出、exp 的中间结果都可以留在 fp16。

**他**：行。我试了，9e-4，过了。但性能掉了 8%，这个值得吗？

**助手**：8% 要不要接受，取决于三件事：

1. **这个算子是不是热点**：Softmax 在 Transformer 里通常占比不低，8% 可能就是整体 1–2%；
2. **有没有更便宜的达标路径**：比如只在长序列时走 fp32，短序列保持 fp16；
3. **验收是否有余量**：9e-4 对 1e-3 只有 10% 余量，再优化性能可能又掉回去。

一个折中方案是**按输入长度分档**：

```cpp
if (seqLen > 2048) {
    // fp32 累加（长序列误差大）
} else {
    // fp16 累加（短序列够用）
}
```

分档阈值用实测定，不要拍。这样大部分请求走快路径，只有长序列付代价。

**他**：还有个事，我发现误差集中在输入很小那一段，大值区反而很准。

**助手**：这个现象很典型，是**相对误差在小分母处放大**。

举个例子：真实值是 `1e-5`，你算出来 `1.1e-5`，绝对误差只有 `1e-6`，但相对误差是 10%。MARE 是按相对误差算的，所以这些点会显著拉高指标。

两个处理方式：

**1. 分母加 epsilon**

```cpp
float denom = sum + 1e-6f;
```

但要注意：如果 `sum` 本身很小，`1e-6` 就不"小"了，会引入系统性偏差。更稳的写法是：

```cpp
float denom = std::max(sum, 1e-6f);   // 只在下限兜底，不改变正常值
```

**2. 该区间单独用 fp32**

如果业务对小区间敏感，把这段拉出来走 fp32 分支。

从数学上说，softmax 的输出本来就可能非常小（接近 0），这些位置的**绝对贡献很小**，但对 MARE 很敏感。所以要先确认：**验收标准是不是该用绝对误差**，而不是相对误差。跟验收方确认口径，有时比改代码更有效。

**他**：那我要是把整个算子都改成 fp32，是不是这些都不存在了？

**助手**：理论上是的，但代价刚才说过。而且有个误区值得澄清：**fp32 也不是"精确"的**。

fp32 有 24 位尾数，大约 7 位十进制有效数字。对于累加几万个元素、或者 `exp` 差值很大的情况，fp32 也会累积误差——只是比你现在的量级小得多（1e-7 而不是 1e-3）。

所以正确的目标不是"消除误差"，而是"把误差压到验收线以下，并且留出余量"。这也是为什么精度调试要看指标，而不是追求"和参考实现完全一致"。

**他**：怎么量化每一步的误差贡献？我不想靠猜。

**助手**：**分段打印 + fp64 基准**，这是精度调试里性价比最高的方法。

思路：

```
golden(fp64) → ① exp 后 → ② sum 后 → ③ div 后
```

在每一步后面把整个 tensor 打出来（或者抽样），逐段与 fp64 结果比较：

```cpp
// 伪代码：每步后打 max 相对误差
printf("after exp: MARE=%e\n", computeMare(expOut, expRef));
printf("after sum: MARE=%e\n", computeMare(sumOut, sumRef));
printf("after div: MARE=%e\n", computeMare(divOut, divRef));
```

判读方法：**哪一段的误差突然跳一个量级，问题就在那一段的前一步**。

三个注意点：

1. **基准要用 fp64**（CPU 上用 `double` 算），不要用 fp32——fp32 自己就有 1e-7 误差，会掩盖小问题；
2. **固定输入**，不要用随机数，否则两次跑没法对比；
3. **抽样打印**，全量打印会把日志撑爆，也看不懂。

**他**：官方对精度的验收标准是什么？我们内部定 1e-3，不确定口径一致。

**助手**：官方是**分层**的（常见的 L0 / L1 / L2 分级），不同等级对应不同阈值和对比基准，而且**不同算子类别要求不一样**——逐元素算子和长序列归约算子不可能用同一把尺子。

几个实操建议：

1. **先查你这类算子归到哪一档**，再决定内部阈值；
2. **内部可以比官方更严**，但不要比官方更松——否则上线后会被卡；
3. **把"对比基准"写进报告**：和谁比（CPU 参考实现？fp64？原框架？）、用什么指标、在什么输入分布上。

我这边不掌握你们具体版本的验收表，这一条建议你直接查对应版本的精度验收文档，或者问一下验收方口径——比在这里猜准。

**他**：改完怎么保证以后不被别人改坏？

**助手**：把这个 case 变成**回归资产**，三步：

**1. 固定最小用例**

不要用随机数。把出错的那组输入（shape + dtype + 具体数值）落成文件，提交进仓库。随机数的问题是"这次错下次不错"，回归测试就失去了意义。

**2. 固化阈值**

```bash
# 用例里写死：MARE <= 1e-3 才算过，超了就 fail
./run_test --case softmax_fp16_1024 --mare-limit 1e-3
```

**3. 进 CI，和功能用例分开跑**

精度用例通常更慢，混在功能测试里容易被"嫌慢"而整个跳过。分开之后，可以只在改动涉及数值计算的 PR 上跑。

再加一条经验：**精度用例要覆盖"数值恶劣区间"**——接近 0 的输入、长序列、极值混合。否则你测的永远是"好走"的那部分。

## 8. 动态 shape 到底怎么支持

**他**：模型输入长度不固定，seq 从 128 到 4096 都有。我现在的 tiling 是按固定 shape 写死的，换个 shape 就错。动态 shape 到底该怎么支持？

**助手**：先说一个容易误解的点：**动态 shape 不是"kernel 支持变长"**。

kernel 本身不知道 shape，它只知道 tiling 参数——`perCore`、`tileLen`、`tileNum`。所以"支持动态 shape"的真正含义是：

> **每次调用时，host 侧重新算一次 tiling，把结果传给 kernel。**

kernel 侧要做的是：**不要假设任何编译期常量**（长度、轮数、tile 大小），一切从 tiling 读。

**他**：那每次调用都算一遍 tiling，开销大吗？

**助手**：不大，前提是你别在 tiling 里做重活。

tiling 是 host 侧的纯计算：几次除法、取整、比较，微秒级。相比 kernel 执行（几十微秒到几毫秒），可以忽略。

真正会让它变大的情况：

- 在 tiling 里做**内存分配**（`malloc`/`new`）——这是大忌；
- 在 tiling 里做**字符串/日志**操作；
- 在 tiling 里**查表**（比如扫一遍 shape 找匹配项）。

原则：**tiling 只做算术，不做 IO、不做分配**。

**他**：那 kernel 里能不能有编译期常量？我看模板里有些长度是写死的。

**助手**：能，但要分清"哪些可以写死"：

| 常量类型 | 能写死吗 | 例子 |
|---|---|---|
| 数据类型大小 | 可以 | `sizeof(half)` |
| 对齐粒度 | 可以 | 32B、16 元素 |
| **总长度** | **不行** | `total`、`perCore` |
| **轮数** | **不行** | `tileNum` |
| **tile 大小** | **不行** | `tileLen` |

如果确实想用编译期常量换性能，可以用**模板特化 + 有限实例化**：

```cpp
template <int TILE>
__aicore__ void kernel_impl(...);

// 只实例化几个常用档位
if (tileLen == 8192)  kernel_impl<8192>(...);
else if (tileLen == 16384) kernel_impl<16384>(...);
else                  kernel_impl<0>(...);   // 0 表示运行时决定
```

代价是编译产物变大。**只在你确认"tile 取固定值能显著提速"时才这么做**。

**他**：UB 预算怎么随 shape 变？我 tile 是写死的 16KB。

**助手**：tile 写死，意味着小 shape 时浪费、大 shape 时可能不够。正确做法是**从 UB 预算倒推**，而不是反过来。

```cpp
uint64_t ubSize = 0;
AscendC::GetCoreMemSize(AscendC::CoreMemType::UB, ubSize);

// 留 25% 给临时 buffer 和对齐
uint64_t budget = ubSize * 3 / 4;

// 深度 × (输入份数 + 输出份数) × tile ≤ budget
int64_t tile = budget / (2 * 2) / sizeof(half);
tile = (tile / 16) * 16;              // 32B 对齐
tile = std::min(tile, total);          // 不能超过总长度

// 再按档位取整，避免 tile 值抖动太大
```

注意最后一步"按档位取整"——如果 `tile` 随着 shape 连续变化，每次调用都换一个值，性能曲线会很难看。**把它量化到 8K/16K/32K 几档**，既省心又稳。

**他**：blockDim 也要动态吗？

**助手**：要，而且这个比 tile 更容易被忽略。

写死 `blockDim = 8` 的问题：shape 很小时（比如 total=100），8 个核里 7 个在等 1 个干活；shape 很大时，8 个核可能又不够。

```cpp
int64_t blockNum = std::min(physicalCores,
                            CeilDiv(total, minPerCore));   // 每核至少 64 个元素
blockNum = std::max<int64_t>(blockNum, 1);
```

`minPerCore` 要实测：太小时启动开销占比高，太大时并行度不够。经验值几十到几百个元素。

**他**：workspace 大小也随 shape 变，这个怎么处理？

**助手**：workspace 的大小是**算出来的**，不是固定的：

```cpp
// 例子：每核一个部分和槽位
size_t wsBytes = blockNum * sizeof(float);
```

然后传给上层（aclnn 的第一段接口会告诉你需要多大）：

```cpp
aclnnMyOpGetWorkspaceSize(..., &workspaceSize, &executor);
```

三个注意点：

1. **不要预分配一个巨大的固定值**——浪费内存，而且大小 shape 不一致时容易踩边界；
2. **workspace 要清零**（如果语义需要），别假设新分配的内存是 0；
3. **不同 shape 的 workspace 大小可能不同**，如果做缓存，key 要用 "shape + blockNum"，不能只用 shape。

**他**：动态 shape 下，尾块和余数是不是更容易错？

**助手**：是，而且错得更隐蔽——因为你的测试用例往往只覆盖了少数几个 shape。

三个高发点：

**1. `total % blockNum` 的余数**（前面讲过，摊到前几个核）。

**2. `perCore % tileLen` 的余数**——每核内部的最后一轮也可能不满：

```cpp
int64_t lenLast = len - (tileNum - 1) * tileLen;   // 可能是 0 到 tileLen-1
if (lenLast > 0) {
    // 最后一轮走尾块逻辑（DataCopyPad）
}
```

**3. `len == 0` 的核**——shape 小时，某些核可能分到 0 个元素。要在开头就返回：

```cpp
if (len <= 0) return;
```

如果不返回，`AllocTensor` 之后 `DataCopy` 长度 0，行为不确定。

**他**：动态 shape 会不会影响性能？不能特化了。

**助手**：会，主要三方面：

| 影响 | 说明 | 缓解 |
|---|---|---|
| 不能编译期特化 | 循环边界是变量，少了展开优化 | 关键路径模板特化几个档位 |
| 分支变多 | 尾块/空核判断进入热路径 | 把判断提到循环外 |
| tile 抖动 | 每个 shape 的 tile 不同 | 量化到几个档位 |

但要说清楚：**这些影响通常在 5%–15%**，远小于"写死 shape 导致大 shape 直接错"的代价。

如果某个 shape 是绝对热点（比如固定的 batch=1, seq=2048），可以给它单独做一条特化路径：

```cpp
if (total == 2048 && /* 其他固定条件 */) {
    kernel_specialized<<<...>>>(...);   // 编译期常量版本
} else {
    kernel_generic<<<...>>>(...);       // 通用版本
}
```

**他**：那有没有"分档"的策略？我想把常见的 shape 都覆盖。

**助手**：有，而且这是工业界常用的做法：**shape 分档（shape bucketing）**。

思路：把连续的 shape 映射到几个固定档位，每个档位用一套预编译/预调好的参数。

```
档位 1：seq ∈ [1, 512]     → tile 8K,  depth 2, blockDim = min(核数, ...)
档位 2：seq ∈ (512, 2048]  → tile 16K, depth 2
档位 3：seq ∈ (2048, 8192] → tile 32K, depth 1
```

三个要点：

1. **档位边界用实测定**，不要按"2 的幂"拍；
2. **档位内取上界**，比如 seq=600 走档位 2 的参数，宁可稍微浪费一点；
3. **档位表要能打印**，出问题时一眼看出走了哪档。

代价是"非边界 shape 会有一点浪费"，收益是"参数可预测、可调优、可回归"。

**他**：那我怎么调试动态 shape？总不能每个 shape 都跑一遍。

**助手**：用"边界 + 抽样"的组合，别穷举。

**必测的边界值**：

```
1          最小
tileLen-1  差一个
tileLen    正好一个 tile
tileLen+1  一个 tile 多一点
blockNum   正好每核一个
blockNum-1 有一个核分不到
```

**再抽样几个真实值**：模型实际会用的 shape（比如 128/512/2048/4096）。

**调试时把 tiling 全打出来**：

```cpp
printf("shape=%ld total=%ld blk=%ld perCore=%ld tail=%ld tile=%ld num=%ld\n", ...);
```

这样一旦某个 shape 出错，你能直接看到它的切分，而不用重现。

**他**：最后一个问题，动态 shape 和静态 shape，我该选哪个？我们模型其实只有几个固定 shape。

**助手**：如果 shape 是**有限的几个**，我建议**用固定的几套参数，而不是完全动态**。

理由：

1. **可预测**：每个 shape 的性能可以单独测、单独回归；
2. **可优化**：可以给热点 shape 做特化；
3. **少踩坑**：不用处理"任意 shape"带来的所有边界。

实现上就是"动态的框架 + 静态的表"：

```cpp
const ShapeConfig* cfg = LookupConfig(total);   // 查表
if (cfg) {
    // 用预调好的参数
} else {
    // 兜底：走公式计算
}
```

完全动态适合"shape 真的不可预测"的场景（比如用户输入长度任意的 NLP 服务）。只要 shape 集合可控，表驱动永远更稳。

## 9. 同事留下的一段 kernel，里面手写了 SetFlag

**他**：接手一段代码，`CopyIn` 和 `Compute` 之间手写了 `SetFlag`/`WaitFlag`。文档里说 `EnQue/DeQue` 已经做同步了，这段是不是可以删？

**助手**：先别删，这里有个关键分叉：**buffer 是从 `TQue` 拿的，还是从 `TBuf` 拿的？**

这两种情况的答案完全相反：

| buffer 来源 | 有没有自动同步 | 能不能删手写 flag |
|---|---|---|
| `TQue`（`AllocTensor/EnQue/DeQue/FreeTensor`） | 有 | 大概率能删（但要确认同步对象一致） |
| `TBuf`（`GetBuffer/Alloc/Free`） | **没有** | **不能删，删了就炸** |

`TQue` 是"带同步语义的队列"，`TBuf` 是"裸内存"。很多人以为名字里都有 buffer 就差不多，其实前者帮你管了事件，后者什么都没管。

**他**：TBuf。因为这个 buffer 要复用做中间计算。

**助手**：那就**不能删**。而且你这段代码在 `TBuf` 上做"复用 + 手动同步"，是合理的写法，不是历史包袱。

原因：`TBuf` 只保证"分配一块内存给你"，不保证"上一个操作写完了没有"。你复用同一块 buffer 做中间计算时，如果不手动插同步，就会出现"上一轮的计算还没读完，下一轮的搬运已经覆盖了它"——这就是数据竞争。

顺带说一句，`TBuf` 复用确实是常见需求（省 UB），但要注意：**复用的代价就是同步责任转移给了你**。如果这段代码后面要重构，可以往两个方向走：

1. 改成 `TQue` + 多 depth（让队列管同步，代码更简单，但占更多 UB）；
2. 保留 `TBuf`，但把同步封装成明确的函数，加注释说明"这里为什么必须同步"。

在没搞清依赖关系之前，**保持现状**是最安全的。

**他**：那我能不能把这段直接重构成 TQue？反正也是复用。

**助手**：能，但**现在不建议**，理由有三个：

**1. 你还没完全搞清同步关系。** 现在的代码能跑，说明同步至少是"碰巧对"的。在没搞清之前重构，等于把"未知的正确"换成"未知的错误"。

**2. 重构范围可能比你想的大。** `TQue` 需要 `TPipe` 管理，`AllocTensor/EnQue/DeQue/FreeTensor` 是成套的，改动会牵扯到函数边界、buffer 生命周期。

**3. 收益不明确。** `TQue` 的收益是"少写同步 + 不易出错"，但如果这段代码已经稳定，收益接近零，风险却不为零。

如果确实想重构，建议顺序是：

```
先加注释，说明每一对 flag 在同步什么
→ 跑 100 次稳定性测试（建立基线）
→ 再重构，每改一处跑一次
```

**他**：行吧。但我看这段代码里 EnQue 和 SetFlag 同时存在，是不是有一个多余的？

**助手**：要看它们同步的是不是**同一对**生产者/消费者。

典型情况是这样的：

```
MTE2 (搬运) --写 UB--> EnQue（setFlag）
                            ↓
V (计算)    <--读 UB--  DeQue（waitFlag）
```

如果这段代码里，`EnQue` 管的是"CopyIn → Compute"，而手写的 `SetFlag` 管的是"Compute → 下一次 CopyIn 覆盖这块 buffer"（也就是反向依赖），那**两个都不是多余的**——它们同步的是两个不同方向。

判断方法：把每一对 `SetFlag/WaitFlag` 的**前后操作**写出来，看是不是同一组。如果两组操作的边界完全重合，才是冗余。

**他**：说实话我一直不太理解，为什么 Ascend 要搞这么多同步原语？CUDA 里一个 `__syncthreads` 就完了。

**助手**：因为两者的**并行模型**不一样，不是设计者故意复杂。

CUDA 的 `__syncthreads()` 是**线程级屏障**：一个 block 里的所有线程到齐，再一起往下走。它背后假设的是"同一时刻只有一段代码在跑，只是有很多线程"。

Ascend 的 AI Core 里，实际在并行的是**几条独立的流水**：

```
MTE2（搬入） ─┐
V    （计算） ─┼─ 三条流水同时推进
MTE3（搬出） ─┘
```

它们各有各的指令队列，互相之间只靠"事件"通信。所以你需要的是：

- **同一流水内**的顺序：`PipeBarrier`（比如写完 UB 再读）
- **跨流水**的先后：`SetFlag/WaitFlag`（比如搬完再算）
- **跨核**的同步：`SyncAll`
- **有依赖的搬运**：`TQue` 的 `EnQue/DeQue`（封装了上面这些）

CUDA 里这些大部分由硬件/编译器隐式处理了，所以你只看到一个 `__syncthreads`。Ascend 把它们暴露出来，灵活但也啰嗦。

**他**：那 `PipeBarrier` 和 `SetFlag` 到底什么时候用哪个？

**助手**：一句话区分：**`PipeBarrier` 是"我自己这条流水里，前后别乱序"；`SetFlag` 是"我等另一条流水"**。

| 场景 | 用什么 | 原因 |
|---|---|---|
| 同一 pipe 内，写完再读 | `PipeBarrier<PIPE_V>` | 不需要跨流水，屏障就够 |
| 搬运完 → 计算开始 | `SetFlag/WaitFlag`（或队列） | 跨流水，必须事件通知 |
| 计算完 → 搬运走 | `SetFlag/WaitFlag`（或队列） | 同上，反方向 |
| 所有流水都停一下 | `PipeBarrier<PIPE_ALL>` | 调试用，性能代价大 |

一个实用原则：**调试阶段用 `PipeBarrier<PIPE_ALL>` 求稳，把功能跑对；优化阶段再换成精确的 `SetFlag`**。因为 Barrier 是"一刀切串行"，正确但慢；`SetFlag` 是点对点，快但容易配错。

**他**：eventId 有多少个？我这段代码用了 0 到 3。

**助手**：数量是有限的，具体几个取决于芯片和编译配置，通常是个位数。重点是：**它不是"你要多少有多少"的资源，而且框架内部也在用**。

这就是为什么手写 `SetFlag` 危险：

- 你用了 0–3，框架在某个路径上也用了 0–3，两边的 set/wait 会互相"冒充"；
- 症状是**偶发读到旧数据**，而且改一行无关代码（影响了调度）就"好了"或者"更差"；
- 这种 bug 极其难查，因为它伪装成随机故障。

所以原则是：**能用队列就让队列管**。队列内部会分配事件，而且保证不冲突；手写等于自己管理一个稀缺资源，还要和框架抢。

**他**：那我这段用 0 到 3，会撞吗？

**助手**：**有可能，但没法从代码上直接判断**——要看框架在这段路径里用了哪些。

给你三个处理方式，按风险从低到高：

1. **保持现状**（如果代码稳定）：不动，风险最低；
2. **改成队列**：把这块 buffer 换成 `TQue`，事件管理交给框架；
3. **显式查证**：看框架头文件/文档里这段用了哪些事件 ID，避开它们——但这依赖版本，升级就可能失效。

如果没有明确的性能收益，我建议 1 或 2，别选 3。

**他**：我改了一版，同一输入跑 100 次结果一致，是不是可以了？

**助手**：**还不够**，100 次一致只能说明"在当前的时序下没问题"。

原因：同步类 bug 的触发依赖**危险窗口**，而窗口的宽度受这些因素影响：

- **shape 大小**：小 shape 流水几乎不重叠，窗口很窄；
- **核数**：单核没有核间同步，多核才有；
- **tile 大小**：tile 越大，搬运时间越长，窗口越宽；
- **机器负载**：空闲机器和满负载机器，调度时序不一样。

所以要把测试条件往"更容易暴露"的方向推：

```
① 加大 shape（让流水重叠更充分）
② 加多核（触发核间同步）
③ 加大 tile（拉长搬运时间）
④ 同时跑其他任务（制造调度抖动）
⑤ 然后再跑 100 次
```

**他**：加大之后，确实偶尔会错。那我这个改动还是有问题的。

**助手**：对，这就是**"看起来对"的典型**：单核小 shape 是同步问题最好的藏身处。

现在的信息很有用：说明你的改动**引入了新的竞争**，而不是修好了旧问题。

建议按这个顺序回退和验证：

1. 先回退到改动前的版本，用同样的条件（大 shape、多核）跑 100 次，确认它也错——这样你才知道"原来就有问题"还是"我改出来的"；
2. 如果原版也错，说明这段代码本来就有隐患，你的改动只是换了个表现；
3. 如果原版不错，只在你的版本错，那就是你新引入的，重点看你动的那几行同步。

**他**：行，我把改动回滚了。顺便问一句，这种代码 review 的时候我该怎么提意见？别人写的，我不好直接说"这段多余"。

**助手**：先问，别先下结论。这个技巧比技术本身更重要。

开场可以这样：

> "这段 `SetFlag` 和 `EnQue` 我有点没看懂，它们同步的是同一对吗？"

让对方讲。讲的过程中通常会出现两种情况：

- 他讲得清楚（"这个是防止下一轮 CopyIn 覆盖"）→ 你学到了，而且确认了不是冗余；
- 他讲不清楚（"应该是同步用的吧"）→ 问题自己浮出来了，而且是他自己发现的，不是你指出的。

直接说"这段多余"的问题是：它变成了**立场之争**（你觉得他写得烂，他觉得你不懂），而不是技术讨论。

如果确认是冗余，也别说"删掉"，说"要不要试试删掉跑一遍 100 次稳定性，看看有没有影响"——把结论变成实验，对方更容易接受。

**他**：有道理。我先记着。

**助手**：另外提醒一句：这类代码最好在**文件头写一段同步说明**，比如：

```cpp
// 同步说明：
//   EnQue/DeQue 负责 CopyIn → Compute（正向）
//   手写 SetFlag(0) 负责 Compute → 下一轮 CopyIn 覆盖（反向）
//   TBuf 复用同一块内存，所以两个方向都必须显式同步
```

下次接手的人（可能是半年后的你）就不用重新推理一遍了。

## 10. 视频组的 elementwise，带宽只有 30%

**他**：elementwise 算子，实测带宽只有理论值 30%。`mte2_ratio` 18%、`vec_ratio` 60%。这算搬运瓶颈还是计算瓶颈？

**助手**：先纠正一个很常见的误读：**`mte2_ratio` 低，不等于"搬运不是瓶颈"**。

这个指标的含义是"搬运单元在采样窗口里有百分之多少的时间是忙的"。它低，只能说明搬运单元大部分时间在空闲——但空闲的原因可能是：

1. 没有数据可搬（上游没喂上，比如计算太慢）；
2. 搬运任务太小、太碎，启动开销占了大头，真正"忙"的时间很短；
3. 同步在等，搬运根本没被发起。

所以 `vec 60% / mte2 18%` 这个组合，更像"计算单元在等小块数据"，而不是"搬运带宽不够"。

要看三个更直接的数：

| 指标 | 为什么看它 |
|---|---|
| 单次搬运字节数（tile 大小） | 太小 → DMA 启动开销占比高 |
| `blockDim` / 物理核数 | 并行度够不够 |
| `Task Duration` ÷ 理论时间 | 你到底差多少倍 |

**他**：tile 8KB，blockDim 8。我直接把 tile 改到 64KB 试试？

**助手**：**先别，会撞 UB 上限**。tile 不是越大越好，它受一个硬约束：

```
UB 占用 ≈ 深度 × tile × 输入份数
        + 深度 × tile × 输出份数
        + 临时 buffer（fp32 累加、cast 中转）
        + 对齐 padding
```

假设你现在是深度 2、一进一出：

```
2 × 8KB × 1 + 2 × 8KB × 1 = 32KB
```

改到 64KB 就是 `2×64 + 2×64 = 256KB`——远超 UB 容量（不同芯片百 KB 级，具体看型号）。所以大概率直接报"UB 超限"或者编译期就失败。

更关键的是：**tile 和队列深度是一对联动参数**。你把 tile 放大，深度就得降；深度降到 1，double buffer 就没了，搬运和计算会串行——收益可能被抵消掉。

建议的调法：

```cpp
// 先固定深度 2，扫 tile
8KB → 16KB → 32KB → 48KB
// 找到 Task Duration 的拐点，再试着调深度
```

**他**：已经试了，跑起来报 UB 超限。那我怎么算能放多大？

**助手**：给你一个可以手算的估算式，先粗后细：

```cpp
// 1. 拿到 UB 的真实大小（别写死）
uint64_t ubSize = 0;
AscendC::GetCoreMemSize(AscendC::CoreMemType::UB, ubSize);

// 2. 按你的 buffer 规划倒推 tile
//    假设：输入 1 份 + 输出 1 份，深度 D
//    留 20% 余量给临时 buffer 和对齐
uint64_t perTile = ubSize * 0.8 / (2 * D);
```

几个容易漏的占用项：

- **fp32 累加器**：如果中间要转 fp32 累加，多一份 buffer；
- **Cast 中转**：fp16→fp32 再→fp16，中间那块也算；
- **对齐 padding**：按 32B 向上取整，小 tile 时这个占比不小；
- **框架自身**：`TPipe`、队列管理结构也占一点。

所以实际能用的不是"UB 总大小"，而是"UB 减去这些之后剩下的"。经验上按 70%–80% 估比较稳。

**他**：16KB、深度 2，到 45% 了。还是差一半，是不是没救了。

**助手**：45% 已经说明方向对了（从 30% 到 45% 是实打实的提升），先别下"没救"的结论。

现在需要知道"剩下的差距在哪"，方法是 **ablation**——一次只改一个变量，看影响：

| 实验 | 做法 | 若明显改善，说明 |
|---|---|---|
| A. 纯搬运 | 只 CopyIn + CopyOut，不做计算 | 搬运路径没问题，瓶颈在计算/同步 |
| B. 放大 tile | 16KB → 32KB | DMA 启动开销占比高 |
| C. 加核 | blockDim 8 → 16/物理上限 | 并行度不足 |
| D. 去 Cast | 去掉类型转换 | Cast 是隐形成本 |
| E. 改对齐 | 输入改成 32B 对齐 | 非对齐走了慢路径 |

**先做 A**，因为它给你一个"分母"：这个 shape 在这张卡上的搬运上限是多少。

**他**：纯搬运能到 80%。那说明什么？

**助手**：说明三件事，都很重要：

**1. 你的搬运路径基本没问题**，理论上限是 80%，不是 100%。剩下 20% 是 DMA 启动开销、对齐损耗、尾块这些"硬成本"。

**2. 你现在 45% 和上限 80% 之间，有 35 个点花在计算或同步上**。这才是你要优化的地方，而不是继续折腾搬运。

**3. 80% 这个数本身要记住**——它是你这个 shape 的"实际可达上限"。以后任何优化，都以它为分母，而不是以规格书的理论带宽为分母。很多人卡在"为什么到不了 90%"，其实是目标本身设错了。

接下来做 B/C/D，看哪个能把 45% 往上推：

- B（tile 32KB）改善明显 → 启动开销是主因；
- C（加核）改善明显 → 并行度不足；
- D（去 Cast）改善明显 → 转换开销大。

**他**：我这段有三次 Cast，这个贵吗？

**助手**：贵，而且它的开销是**隐形的**，容易被低估。三块：

**1. 多一次 UB 读写。** `fp16 → fp32` 要写一块新 buffer，`fp32 → fp16` 再写回。UB 带宽是有限的，来回拷就是实打实的开销。

**2. 占 UB 空间。** 中间那块 fp32 buffer 会让 tile 变小，间接影响搬运效率。

**3. 和计算抢同一个单元。** Cast 本身是 Vector 操作，会占用 `vec_ratio`。你看到的 60% 里，可能有一部分就是 Cast 贡献的。

处理原则：**能在原 dtype 上算完的，不要转**。只有这两类才值得转：

- **归约/累加**（sum、mean、variance）：fp16 累加会"大数吃小数"；
- **数值敏感运算**（exp、log、除法）：需要更多有效位。

而且**只转累加器，不转整块数据**：

```cpp
// 好：累加器 fp32，输入仍 fp16
float sum = 0.f;
for (int i = 0; i < len; ++i) sum += static_cast<float>(xLocal[i]);

// 差：整块转 fp32 再算
Cast(tmpFp32, xLocal, RoundMode::CAST_NONE, len);
```

**他**：去掉一次，62%。说实话，再往下优化还值得投入几天吗？

**助手**：给你三条停止条件，满足任一条就可以停：

**1. 和同类算子差距在 10% 以内。** 找个官方实现或竞品，同 shape 对比，差距不大就说明没什么"独特优化空间"了。

**2. 达到 roofline 的合理区间。** elementwise 通常能到规格带宽的 70%–85%，归约类低一些（多读一遍）。你现在 62%，如果上限是 80%，还有 18 个点，属于"值得再花半天"，但"不值得花一周"。

**3. 连续两轮收益 < 3%。** 这是最实用的信号——优化进入尾声了，投入产出比开始变差。

另外算一笔账：**这个算子在整网里占多少时间？** 如果它只占 5%，你把它从 62% 优化到 75%，整体收益不到 1%。那就不值得。

**他**：那 70% 到 80% 之间这段呢，还要不要追？

**助手**：通常不值，除非满足下面任一条：

- 这个算子是**明确的瓶颈**（profiling 里排名前二）；
- 业务对**端到端延迟**敏感，1% 都有意义；
- 这段优化有**可复用性**（比如能沉淀成模板，惠及十几个算子）。

否则 70% 已经进入"收益递减区"，同样的时间花在别处更划算。

我一般建议：**先把 80% 这个上限测出来，再决定追到哪**。知道上限之后，"62% vs 75%"的意义就清楚了，而不是盲目追一个数字。

**他**：行，先到这儿。顺便问下，`{1,1000}` 这种小 shape 也按这个套路调吗？

**助手**：**不用，口径完全不同**。

小 shape 的时间构成里，**启动开销占主导**，带宽根本不成立：

```
小 shape 耗时 ≈ 固定的启动/同步开销 + 很少的搬运时间
```

这时候你算"带宽利用率"会得到一个很低的数，但这个数没有意义——因为你优化的方向根本不是带宽，而是：

- 减少 kernel 启动次数；
- 减少同步次数；
- 能不能把小算子合并（融合）掉。

所以判断标准要换：

| shape 规模 | 看什么 | 优化方向 |
|---|---|---|
| 大（> 数万元素） | 带宽利用率 | tile、队列深度、核数 |
| 小（< 数千元素） | 延迟（绝对耗时） | 融合、减少启动、减少同步 |

**他**：那我看板上的数字不就废了？我们报表是按带宽算的。

**助手**：**数字没废，但口径要分组**。

混在一起算的问题是：小 shape 的"低带宽"会拉低整体均值，让你误判"这个算子性能很差"，实际上它只是"小到不适用带宽口径"。

建议报表分三组：

```
group A: 大 shape   → 报带宽利用率
group B: 小 shape   → 报延迟（us），不报带宽
group C: 极小 shape → 报"启动开销占比"
```

这样每个数字都有明确的解释，优化方向也不会跑偏。很多团队的性能看板就是因为没分组，导致"优化了半天，看板数字没变"。

## 11. 算子融合与图模式

**他**：单算子我都调过了，每个看着都还行。但整网还是慢，同事说要做算子融合。融合到底能救多少？值不值得投入？

**助手**：能救多少，取决于你的瓶颈在哪。先把融合的收益拆开，你才能判断值不值：

| 收益来源 | 机制 | 典型量级 |
|---|---|---|
| 减少 GM 往返 | 中间结果不落 GM，留在 UB | 最大的一块，往往 30%+ |
| 减少 kernel 启动 | 一次启动代替多次 | 小 shape 明显，大 shape 不明显 |
| 提高单元利用率 | Cube/Vector 交错，填满空闲 | 取决于算子组合 |

判断方法很简单：**算一下"融合能省掉多少次 GM 读写"**。

比如 `LayerNorm → Gelu → Add`：

```
不融合：LN 读 x 写 y1；Gelu 读 y1 写 y2；Add 读 y2 写 z
        = 3 读 + 3 写 = 6 次 GM 访问
融合：  读 x，算完直接写 z
        = 1 读 + 1 写 = 2 次 GM 访问
```

理论上省掉 2/3 的访存。如果你的算子链是 memory bound，收益就接近这个数；如果是 compute bound，收益就小得多。

**他**：那什么样的算子适合融合？

**助手**：三类最适合，按收益排序：

**1. elementwise 链**（scale → relu → add → mul）

最适合。它们都是"读一块、算一下、写一块"，融合后中间结果完全不用落 GM。而且 UB 占用可控（同一块 tile 反复用）。

**2. reduce/normalize + elementwise**（softmax → dropout，layernorm → gelu）

收益也大，因为中间结果通常比输入还大（比如 softmax 的输出和输入同尺寸）。但要注意：这类算子往往需要多遍遍历，融合后 UB 压力会上升。

**3. matmul + 激活/bias**（matmul → bias → gelu）

收益中等。Cube 算完的结果直接留在 L0C 或 UB，交给 Vector 处理，省一次 GM 往返。但 Cube 和 Vector 的 buffer 是分开的，搬运路径要设计好。

**不适合融合的**：

- 两个 compute-bound 的算子（融合后还是 compute bound，省不了多少）；
- 中间结果特别大的（UB 放不下，被迫落 GM，等于没融）；
- 有严格数值顺序要求的（融合可能改变累加顺序）。

**他**：Ascend 上做融合有什么限制？我听说 UB 是瓶颈。

**助手**：主要三个限制，都跟"中间结果放哪"有关：

**1. UB 容量。** 融合意味着中间结果要留在片上。如果中间 tensor 比输入还大（比如 softmax 的中间结果），UB 很可能放不下。

粗算：

```
融合后 UB 占用 ≈ 输入 tile + 中间 tile × 个数 + 输出 tile
```

超过 70% 就要警惕。

**2. Cube / Vector 的 buffer 是分开的。** matmul 的输出在 L0C，Vector 在 UB，中间要搬一次。这个搬运省不掉，只是从"GM 往返"变成"片上搬运"，快很多但不是零成本。

**3. 同步更复杂。** 融合后流水更长（搬入 → 计算 A → 计算 B → 搬出），任何一处同步写错，都会表现为"偶发错"。

**他**：图模式的融合是自动的吗？我是不是什么都不用做？

**助手**：GE 会做一部分自动融合（比如相邻的 elementwise），但**不是所有融合都能自动完成**，尤其是：

- 需要改变数据布局的融合；
- 跨 kernel 的中间结果复用；
- 需要手工编排流水的融合。

所以现实是：**自动融合能拿到一部分收益，剩下的要靠人写融合算子**。

判断方法：先看 GE 的图优化日志/融合后的图结构，确认哪些已经被融合了，再决定手写哪些。别上来就手写一个大融合 kernel——很可能 GE 已经做了，你只是把它拆得更碎。

**他**：融合之后怎么调？一个大 kernel，出了问题很难定位。

**助手**：两个手段，配合用：

**1. 拆开对比。** 保留未融合版本，两个都跑，对比：

- 总耗时差多少（确认收益）；
- 逐段耗时（确认瓶颈）。

**2. 分段打点。** 在融合 kernel 内部，用 `AscendC::printf` 或者 profiling 的 marker 打时间戳，看每一段花了多少。

更实用的做法是：**先写未融合版本，跑通、跑对、拿到基线，再写融合版本**。这样你永远有一个"正确但慢"的参照物。直接写融合版本，出了问题你都不知道是"融合的 bug"还是"原始逻辑的 bug"。

**他**：融合会不会反而更慢？我见过有人融合完性能下降的。

**助手**：会，三种典型情况：

**1. UB 超限导致退化。** 为了融合，tile 被迫变小，搬运次数变多，抵消了省下的 GM 往返。

**2. 并行度下降。** 融合后一个大 kernel 占满所有核，但每个核的活变少了，尾块浪费增加。

**3. 同步开销。** 融合后流水更长，同步点更多，如果写得不够精细，反而串行。

判断标准：**融合后的 GM 访问量减少了吗？** 如果没减少（比如中间结果还是落 GM 了），那融合就没有意义，只是在增加复杂度。

**他**：那什么情况下应该拆 kernel，而不是融合？

**助手**：四种情况，都是"融合的代价大于收益"：

1. **中间结果 UB 放不下**：被迫落 GM，融合等于白做；
2. **Cube/Vector 配比差异大**：一个阶段 Cube 忙、Vector 闲，另一个反过来，拆开可以让不同 kernel 用不同核数；
3. **可调试性优先**：线上出问题时，拆开的版本更容易定位；
4. **复用性**：某些中间算子被多处调用，融合进去就不好复用了。

一句话：**融合是为了省访存，不是为了少写代码**。省不了访存就别融合。

**他**：那怎么估算融合收益？我想要一个能说服人的数字。

**助手**：用"访存字节数"估算，比拍脑袋靠谱：

```
不融合：Σ(每个算子的 读字节 + 写字节)
融合：  读字节(输入) + 写字节(输出)
```

以 `x → LN → Gelu → y`、shape `{1024, 4096}`、fp16 为例：

```
单算子：LN 读 8MB 写 8MB；Gelu 读 8MB 写 8MB → 32MB
融合：  读 8MB 写 8MB → 16MB
```

省 50%。如果这个算子是 memory bound（大概率是），理论加速接近 2 倍；实际因为同步、启动开销，能拿到 1.3–1.6 倍就不错。

这个估算可以直接写进方案里，比"感觉会快"有说服力。

**他**：融合的时候会做 in-place 复用 buffer，这个有风险吗？

**助手**：有，而且是最容易踩的坑之一。

**风险来源**：输入和输出共用同一块 buffer 时，如果计算顺序不当，会"算到一半把输入覆盖了"。

比如：

```cpp
// 危险：y 和 x 共用 buffer
y[i] = f(x[i], x[i-1]);   // 处理 i 时，x[i-1] 可能已经被覆盖
```

**安全前提**：每个元素只依赖自己（纯 elementwise），或者依赖的数据已经用完。

**实践建议**：

1. 不确定时**别 in-place**，多占一块 buffer 换正确性；
2. 必须复用时，明确写出"为什么安全"（比如"这里每个元素只读自己"）；
3. 加断言/单测：用特殊输入（递增序列）检查输出有没有被污染。

**他**：行，那我该按什么顺序推进？先融合还是先调单算子？

**助手**：先单算子，后融合。理由：

1. **单算子是融合的基础**：每个都调对了，融合才有意义；
2. **基线很重要**：融合后的收益要跟"未融合"比，没有基线就说不清；
3. **定位更容易**：融合出问题时，可以对比未融合版本，快速判断是哪一段。

具体节奏：

```
① 每个单算子跑通 + 精度过
② 单算子性能调到一个合理水平（不用极致）
③ 算一下融合能省多少访存，判断值不值
④ 值 → 写融合版本，对比总耗时
⑤ 不值 → 转向别的优化（并行度、切分、数据布局）
```

**他**：那有没有一个决策树，判断该不该融合？

**助手**：有，从上往下问：

```
1. 算子链里有几次 GM 往返？
   → 估算融合后能省多少字节，< 20% 就别融了

2. 中间结果 UB 放得下吗？
   → 放不下：考虑分块融合，或者放弃

3. 这条链是 memory bound 还是 compute bound？
   → compute bound：收益有限

4. 融合后能不能调？有没有未融合版本做对比？
   → 没有：先别融

5. 都过了 → 融
```

## 12. 把原来的 CUDA LayerNorm 搬过来

**他**：老模型要迁，里面有我之前写的 CUDA LayerNorm：block 内 `blockReduce`，`__syncthreads` 很密。想直接搬过来。

**助手**：先给结论：**别逐行翻译，按数据流重写**。CUDA 的并行是"线程级"，Ascend C 是"核 + 指令级"，没有一一对应关系，硬翻译会得到一份能跑但很慢的代码。

映射关系先建立起来：

| CUDA | Ascend C | 关键差异 |
|---|---|---|
| `grid` / `block` | `blockDim`（AI Core 数） | 一个核 ≈ 一个粗粒度 block，没有 warp 概念 |
| `threadIdx.x` | 无显式线程 | 由 Vector 指令的 lane 并行替代 |
| `__shared__` | UB | 必须显式 `DataCopy` 进出，没有"自动缓存" |
| `__syncthreads()` | 队列同步 / `PipeBarrier` / 归约 API | 不是"等所有线程"，而是"等某条流水" |
| `warp shuffle` | Reduce 类 API | 无 warp 原语，归约是一条指令 |
| `atomicAdd` | 原子接口（慎用） | 确定性差，优先 workspace |
| `float4` 手工向量化 | 不需要 | 向量化由指令粒度承担 |

最重要的一条：**CUDA 里你操心"哪个线程算哪个元素"，Ascend C 里你操心"哪个核处理哪块数据，块内怎么用向量指令铺开"**。抽象层级变了。

**他**：shared memory 那块我最不放心。UB 到底多大？我按多大来切行？

**助手**：**别按固定数字切**，按接口取实际值，再留余量。

```cpp
uint64_t ubSize = 0;
AscendC::GetCoreMemSize(AscendC::CoreMemType::UB, ubSize);
```

为什么不能写死：不同芯片型号的 UB 大小差异很大（百 KB 级），而且同一个芯片上，你也不是全部都能用——

- **队列**：`TQue` 的 buffer 占一块；
- **临时区**：fp32 累加、Cast 中转；
- **对齐 padding**：按 32B 向上取整；
- **框架自身**：`TPipe` 管理结构。

经验上按 **70%–80%** 估可用空间比较稳。

对你这个 LayerNorm，UB 预算大致是：

```
输入 tile（fp16）       2 × tile       （双缓冲）
输出 tile（fp16）       2 × tile
fp32 累加/中间量        1 × tile/2     （视实现）
对齐损耗                ~5%
```

先按这个算，跑起来再看 `msprof` 里的实际占用。

**他**：那我先按 N ≤ 4096 常驻 UB 写，超过就走两遍，行不行？

**助手**：可以，这是标准的分档策略。但三个细节别漏：

**1. `N × sizeof(T)` 只是输入。** 常驻意味着整行都在 UB 里，你还要放：

```cpp
// 一行 N=4096 的 fp16 输入 = 8KB
// 输出同尺寸            = 8KB
// fp32 累加中间量       = 16KB（如果转换）
// 合计                  ≈ 32KB + 余量
```

**2. 多行并行会翻倍。** 如果你一次处理多行（提高并行度），上面的数要乘行数。

**3. 阈值要实测。** 4096 是拍的，实际可能 2048 或 6144 更合适——取决于你还有多少 UB 留给别的 buffer。

建议把阈值做成可配置参数，跑几个点找拐点：

```
N=1024 / 2048 / 4096 / 8192，分别测两种路径的耗时，找交叉点
```

**他**：对了，我原来 `__syncthreads` 是在做跨 warp 的规约。现在换成 Reduce API，但我这个规约是跨行的，不是一个 tile 内。

**助手**：那就不能直接用"核内归约"了，得按**轴**重新设计。

先明确你的数据布局：

```
行方向（row）：每一行是一个样本，要算该行的 mean / var
列方向（col）：同一列跨行
```

**如果规约是行内（沿列方向）**：每行独立，一个核处理一行或几行，用核内 `ReduceSum` 就够，不需要跨核同步。

**如果规约是跨行（沿行方向，比如按列求 mean）**：数据天然被行切分到不同核上，就必须走：

```
每个核算自己那部分的部分和
→ 写 workspace（按核独立槽位）
→ SyncAll
→ 一个核汇总
```

这跟你 CUDA 里的 `blockReduce` 是同一个思路，只是"线程树形归约"换成了"核 + workspace"。

判断方法：**看输出 shape 比输入少哪一维**。少的是列 → 行内规约；少的是行 → 跨行规约。

**他**：骨架跑通了，但比 CUDA 慢两倍。

**助手**：先别急着优化算法，按这个顺序查三个数：

**1. blockDim 用了几个核。** 如果只用了 4 个，而机器有 20+ 核，那就是并行度不足，先加核。

**2. 是不是每行读了两遍 GM。** LayerNorm 天然需要"先算统计量、再归一化"，如果整行放不进 UB，就要读两遍。这是固有成本。

**3. 有没有开双缓冲。** 队列深度 1 的话，搬运和计算完全串行。

CUDA 版本能"一遍过"，是因为数据在 shared memory 里——但 shared memory 只有几十 KB，你的 N 如果超过它，CUDA 版本其实也会退化成两遍。

**他**：blockDim 我设的 4。改到 20 好一些，但还是慢。

**助手**：加核有效说明并行度确实是问题之一。剩下的慢，大概率是"两遍读 GM"。

算一笔账：假设 N=8192、fp16，一行 16KB。

- **两遍读**：读 16KB × 2 + 写 16KB = 48KB
- **一遍读（常驻）**：读 16KB + 写 16KB = 32KB

差了 1.5 倍。这跟你观察到的"慢两倍"量级对得上（还有一部分是启动开销）。

所以下一步是**尽量让整行常驻 UB**：

```cpp
if (rowBytes * 2 <= ubBudget) {
    // 一次搬进来，两遍都在片上算
} else {
    // 退化：两遍读 GM
}
```

**他**：改成常驻之后快了不少，但 UB 有点紧。我再加一个算子就放不下了。

**助手**：那就把阈值调低，做**动态分档**，而不是"能常驻就常驻"。

```cpp
// 关键：阈值不是固定的，取决于当前还能用多少 UB
uint64_t budget = ubSize * 0.7 - otherBuffers;
int64_t threshold = budget / (2 * sizeof(T));   // 输入+输出

if (N <= threshold) { 常驻路径 } else { 两遍路径 }
```

三个配套建议：

1. **常驻路径要留够余量**，别卡着 100% 用，否则加一个 buffer 就崩；
2. **两遍路径也要优化**（tile 大一点、双缓冲），别让它成为"慢但没人管"的分支；
3. **阈值写进日志**，跑的时候打出来，方便定位"为什么这个 shape 走了慢路径"。

**他**：迁完精度差 1e-3。CUDA 那边是 fp32 累加的。

**助手**：那 Ascend 这边也必须 fp32 累加。这是最常见的差异源，先对齐它。

然后按顺序检查四项：

**1. 累加器类型**

```cpp
float sum = 0.f, sumSq = 0.f;          // 对
// half sum = 0;                        // 错，长序列必炸
```

**2. `eps` 是否一致**

两边 `1/sqrt(var + eps)` 的 eps 不同，结果会系统性偏移。CUDA 常用 `1e-5` 或 `1e-6`，确认 Ascend 这边是同一个值。

**3. 中间量有没有偷偷降精度**

比如 `mean` 算完存成 half，再参与 `x - mean`，前面的 fp32 就白做了。

**4. 有没有 fast math**

CUDA 的 `--use_fast_math` 会把 `sqrt`、`div` 换成近似指令；Ascend 侧如果也开了类似选项，两边结果就不一致。要么都开，要么都关。

对比方法：**打中间量，逐段比**。

```cpp
printf("mean=%f var=%f rstd=%f\n", mean, var, rstd);
```

和 CUDA 版本同一组输入的结果对一下，哪一步开始分叉，问题就在那一步。

**他**：找到问题了，我第二遍的 `x - mean` 用了 fp16 的 mean。

**助手**：对，这就是"中间量降精度"，很隐蔽——因为 `mean` 本身是个标量，看起来"存成 fp16 省点空间"，实际上它参与整行运算，误差会扩散到每个元素。

改法很简单：`mean`、`rstd` 全程 fp32，只在最后写回时转。

```cpp
float mean = sum / N;               // fp32
float rstd = 1.f / sqrt(var + eps); // fp32

// 归一化
Muls(yLocal, xLocal, rstd);          // 用 fp32 标量
Adds(yLocal, yLocal, -mean * rstd);  // 注意顺序：先乘后加
```

注意 `Adds` 那一步：`(x - mean) * rstd = x * rstd - mean * rstd`，所以要先 `Muls` 再 `Adds`，参数是 `-mean * rstd`。顺序写反了会得到一个完全不同但"看起来合理"的结果。

**他**：行，我整理了一份 checklist，回头贴文档里。

**助手**：给你一版可以直接用的，八条：

```
① 对齐：所有 GM↔UB 搬运 32B 对齐，尾块用 DataCopyPad
② 切分：核间区间无缝无重叠，余数摊到前几核
③ 同步：队列深度、EnQue/DeQue 成对，跨核用 SyncAll
④ 精度：关键中间量 fp32，Cast 的 RoundMode 正确
⑤ 边界：shape=1、非对齐、超大 shape 都有用例
⑥ 并行度：blockDim 接近物理核数，尾块占比合理
⑦ 性能：与 CUDA 版本对比，差距在 10% 以内
⑧ 可维护：tiling 参数可配置，切分策略有注释
```

其中 ③ 和 ④ 最容易出错，因为它们**不报错，只是错**。建议在 code review 时专门过这两条。

## 13. 算子进推理服务，Python 里调不到

**他**：算子都过了，接进推理服务，Python 里报：

```
RuntimeError: Could not run 'my_add_custom' with arguments from the 'PrivateUse1' backend.
```

`config.ini` 里有我的 vendor，`nm -D` 也能找到符号。那是框架的问题？

**助手**：你这个排查已经把"算子包"这一层排掉了，方向是对的。这个报错来自 **PyTorch 的 dispatcher**，含义很具体：

> "这个算子名我认识，但没有注册在当前 backend（PrivateUse1，也就是昇腾私有后端）的实现表里。"

所以它不是"算子没装上"，而是"**PyTorch 不知道怎么调它**"。算子包和框架之间，还差一层注册。

两条路：

| 路线 | 做什么 | 适合 |
|---|---|---|
| A. op-plugin 注册 | `TORCH_LIBRARY` 定义 schema + `PrivateUse1` 实现 + meta 函数 | 要进图、要 autograd、长期维护 |
| B. pybind 直调 aclnn | 写一层 C++ 扩展，Python 里 `import` 直接用 | 推理、不改图、快速验证 |

推理服务场景，B 通常够用，而且调试成本低。

**他**：能用 pybind 吗？我不太想动 op-plugin，改起来牵扯太多。

**助手**：能，而且我一般建议服务侧先走 B，把链路跑通再考虑 A。

最小结构：

```
my_op_ext/
├── my_op.cpp        // 调 aclnn 的 C++ 代码
├── CMakeLists.txt   // 链接 libaclnn / libascendcl
└── setup.py         // pybind11 封装
```

C++ 侧的核心是 aclnn 的**两段式**：

```cpp
uint64_t workspaceSize = 0;
aclOpExecutor* executor = nullptr;

// 第一段：算 workspace 大小 + 校验参数
aclnnMyAddCustomGetWorkspaceSize(x, y, z, &workspaceSize, &executor);

// 分配 workspace
void* workspace = nullptr;
if (workspaceSize > 0) {
    aclrtMalloc(&workspace, workspaceSize, ACL_MEM_MALLOC_HUGE_FIRST);
}

// 第二段：真正下发
aclnnMyAddCustom(workspace, workspaceSize, executor, stream);

// 同步
aclrtSynchronizeStream(stream);
```

为什么要分两段：**workspace 大小要等 shape/dtype 确定后才能算出来**。框架没法替你预分配，所以先问"要多大"，你自己分配，再执行。

**他**：workspace 还要我自己 malloc？我以为框架会分配。

**助手**：必须你自己分配，这是 aclnn 的设计约定。但有三点可以省心：

**1. 同一 shape 下可以复用。** 不要每个 step 都 malloc/free，那是明显的性能损耗。按 shape 做个缓存：

```cpp
// 伪代码
static std::unordered_map<size_t, void*> wsCache;
if (!wsCache.count(workspaceSize)) {
    aclrtMalloc(&wsCache[workspaceSize], workspaceSize, ...);
}
```

**2. 用 `aclrtMalloc`，别用 `new` / `malloc`。** 前者分配的是 device 内存，后者是 host 内存，传错了会在执行时报奇怪的错。

**3. `workspaceSize == 0` 时不分配**，直接传 `nullptr, 0`。

释放用 `aclrtFree`，和 `free` 不要混用。

**他**：跑通了。但偶发报设备侧异常，日志里有个 507015。是不是我 workspace 释放早了？

**助手**：有可能，但先别急着改，**先拿证据**。

`507015` 这类错误是设备侧的 AI Core 异常（trap），常见原因四类，按概率排：

| 原因 | 典型特征 |
|---|---|
| 越界读写 | 和 shape 相关，大 shape 更容易中 |
| 空指针 / 未初始化 | 必现，和调度无关 |
| UB 超限 | 小 shape 能过，大 shape 崩 |
| 提前释放（stream 未同步） | **偶发**，和宿主负载有关 |

你说的"偶发"确实更像第 4 类，但也可能是越界刚好踩到边界。**先导日志**：

```bash
msnpureport -d 0 -f .
```

导出来看 `device-0/` 下的日志，找 `trap` 之前的最后几条，以及访问的地址和长度。

**他**：导出来一堆，看哪？

**助手**：四个抓手，按优先级：

**1. 第一条异常，不是最后一条。** 设备日志会有连锁反应，最后一条通常是"前面出错的后果"。

**2. PC 地址。** 如果有，配合编译时 `-g` 保留符号，能定位到 kernel 的具体行。

**3. 访问的地址和长度。** 越界类日志通常会给"访问了哪个地址、长度多少"，和你的 tensor 大小一比就清楚。

**4. trap 前后的算子名。** 确认崩的是你的算子，还是前一个算子留下的烂摊子（异步执行时，错误的"归属"会错位）。

**他**：找到了，访问长度比我分配的多了 128 字节。是我 tiling 里算错了。

**助手**：那就对上了——**不是 workspace 释放问题，是 tiling 算错了长度**。

这类"多 128 字节"特别典型，通常是：

- 尾块按 `tileLen` 算，而不是按 `realLen`；
- 对齐时向上取整，但没做边界检查；
- `blockNum × perCore` 超过了 total。

修完之后建议加一道**运行时断言**，把这类问题挡在执行前：

```cpp
ASCENDC_ASSERT((offset + len <= totalLen), "copy out of range");
```

**他**：顺便问一句，这种设备侧异常会影响别的进程吗？我这台卡上还有别人的服务。

**助手**：**会，而且比你想的严重。**

同卡进程之间的隔离是有限的：一个进程让 AI Core trap，可能导致：

- 整卡复位（其他进程的连接断掉）；
- 其他进程的 kernel 被连带中断；
- 严重时驱动需要重新加载。

所以两条纪律：

1. **别在共用卡上做破坏性实验**（大 shape 压测、越界试探）；
2. **容器/进程要能优雅失败**，被连带 kill 后能重试，而不是整个服务挂掉。

如果这台卡上确实有别人的服务，建议先申请一张独占卡做调试，别直接把整个测试流程跑在共享卡上。

**他**：明白了。那我改完之后和 PyTorch 对不上，差了 1e-3。

**助手**：先排**语义**，再排**数值**——顺序反了会浪费很多时间。

**语义层（先查）**：

| 检查项 | 常见问题 |
|---|---|
| dtype | PyTorch 默认 fp32，你的算子按 fp16 算 |
| 内存格式 | NCHW vs NHWC，stride 不同导致整块错位 |
| broadcast 规则 | 维度为 1 的处理方式不一样 |
| 边界行为 | padding、`keepdim`、空 tensor |

**数值层（后查）**：累加顺序、Cast 的 RoundMode、eps。

验证技巧：用**三组特殊输入**跑一遍，比随机数好用得多：

```python

torch.zeros(...)     # 全 0：能暴露初始化/覆盖问题
torch.eye(...)       # 单个 1：能精确定位是哪个位置错
```

随机数的问题是"错了也看不出错在哪"，这三种输入能把错误模式放大。

**他**：确实是 NHWC。改了之后对上了。

**助手**：对，NHWC/NCHW 是最常见的"整块错位"来源——因为数据在内存里的排列变了，kernel 按错误的 stride 读，读到的就是"另一批元素"，结果看起来"差不多对但有偏差"。

建议在算子入口加一个格式检查或者显式转换：

```cpp
// 明确约定：算子只接受 NHWC，或者内部统一转一次
```

**他**：最后问个事，这个算子要给业务团队，我交什么？

**助手**：六样，缺一样都会在对接时返工：

② 接口说明      aclnn 头文件 + 两段式调用示例（含 workspace 处理）

## 14. fp16、bf16、fp32 到底怎么选

**他**：一直不太确定，我的算子该用 fp16 还是 fp32。用 fp32 怕慢，用 fp16 怕精度不够。有没有判断标准？

**助手**：有三个维度，按顺序判断，基本能定下来：

| 维度 | 问题 | 影响 |
|---|---|---|
| 动态范围 | 数据跨度大不大 | 会不会溢出/下溢 |
| 有效位 | 需要几位精度 | 累加、除法会不会失真 |
| 下游敏感度 | 后面谁用它 | 误差会不会被放大 |

先看三种格式的差别：

| 格式 | 指数位 | 尾数位 | 有效数字 | 范围 |
|---|---|---|---|---|
| fp16 | 5 | 10 | ~3–4 位 | ±65504 |
| bf16 | 8 | 7 | ~2–3 位 | 与 fp32 同 |
| fp32 | 8 | 23 | ~7 位 | 很大 |

**一句话选型**：范围不够用 bf16，精度不够用 fp32，都不缺用 fp16。

**他**：bf16 和 fp16 到底差在哪？我一直以为 bf16 更"高级"。

**助手**：不是高级，是**取舍不同**：

| | fp16 | bf16 |
|---|---|---|
| 指数位 | 5（范围小） | 8（范围和 fp32 一样） |
| 尾数位 | 10（精度高） | 7（精度低） |
| 适合 | 值域集中、需要精度 | 值域跨度大、怕溢出 |

举例：

- **神经网络权重/激活**：值通常集中在 ±10 以内，fp16 够用，精度也更好；
- **梯度、loss**：可能到 1e-8 或者 1e5，fp16 会溢出/下溢，bf16 更稳；
- **需要高精度的累加**：两个都不够，要 fp32。

所以训练里常见"bf16 存参数、fp32 累加"，推理里常见"fp16 全流程"。

**他**：为什么 fp16 在昇腾上更快？是硬件只支持 fp16 吗？

**助手**：不是"只支持"，是**吞吐不同**。

Vector 单元一次能处理的元素数，取决于数据宽度。fp16 是 2 字节，fp32 是 4 字节，同样一条指令，fp16 能处理两倍的元素。

再加上 UB 带宽占用减半（同样元素数，fp16 只占一半空间），搬运压力也小。

所以同一个算子：

```
fp16：一次指令处理 N 个元素，UB 占 2N 字节
fp32：一次指令处理 N/2 个元素，UB 占 4N 字节
```

实测下来，fp16 相对 fp32 通常有 1.5–2 倍的速度优势（取决于算子类型）。

**他**：精度不够的典型表现是什么？我怎么知道是精度问题还是逻辑问题？

**助手**：几个特征，能帮你快速区分：

| 现象 | 更像 |
|---|---|
| 结果全错、位置固定 | 逻辑/搬运问题 |
| 结果"差不多对"，误差在 1e-3 量级 | 精度问题 |
| 误差只在大值/小值区间明显 | 精度问题（溢出/抵消） |
| 换个 dtype 就好了 | 精度问题 |
| sum 类算子误差随长度增长 | 累加精度问题 |

最直接的判据：**fp32 版本对不对**。fp32 对、fp16 错，就是精度问题；fp32 也错，那是逻辑问题，别在精度上浪费时间。

**他**：那怎么判断"精度够不够"？有没有量化标准？

**助手**：三个层次：

**1. 验收指标**（硬标准）：MARE / MERE / RMSE Ratio 等，按算子类别查对应阈值。

**2. 误差传播**（软判断）：这个算子的输出会进到哪一层？如果后面是 softmax、layernorm 这类"对输入敏感"的操作，要求要更严。

**3. 端到端**（最终标准）：整网精度掉没掉。有时候单算子误差大一点，但整网看不出来；有时候单算子很好，但累积起来崩了。

实践建议：**单算子按验收指标卡，整网按端到端卡**。两个都要过，不能只看一个。

**他**：为什么累加一定要用 fp32？我用 fp16 累加，误差也没大到不能看。

**助手**：因为 fp16 累加的误差**随长度增长**，短序列看不出来，长序列会崩。

原理是"大数吃小数"：

```
sum = 1.0
再 + 0.0001  → fp16 里 1.0001 存不下，直接变成 1.0，增量丢失
```

序列越长，被吃掉的增量越多。1024 个元素的 sum，误差可能到 1e-2 量级。

fp32 的尾数多 13 位，同样的累加能保住更多增量。所以：

- **累加器**：fp32（几乎无脑）
- **存储**：fp16（省空间）
- **除法/开方**：fp32（误差敏感）

这就是"混合精度"的核心：**不是全局选一个精度，而是按运算类型选**。

**他**：那 fp8 呢？我看新芯片支持 fp8，什么时候能用？

**助手**：fp8 主要是**量化场景**用的，不是通用计算格式。

它的有效位非常少（尾数 2–3 位），只适合两类：

1. **推理的权重/激活**，而且做过量化校准（scale 是精心选的）；
2. **对精度不敏感的中间层**（比如某些 attention 的 QK^T）。

不适合：

- 累加（误差会爆炸）；
- 归一化（数值范围变化大）；
- 任何需要"看得清细节"的计算。

如果你的模型没做量化，直接用 fp8 大概率精度崩。这不是"格式不好"，是"用错了场景"。

**他**：混合精度具体怎么落地？我不想全局改。

**助手**：按"存储 / 计算 / 累加"三段分开设计，而不是一刀切：

| 环节 | 建议 | 理由 |
|---|---|---|
| 存储（GM / UB） | fp16 | 省带宽、省 UB |
| 计算（Vector） | fp16 为主 | 吞吐高 |
| 累加 / 归约 | fp32 | 抗"大数吃小数" |
| 除法 / sqrt | fp32 | 误差敏感 |
| 输出 | 按下游要求 | 通常 fp16 |

实现上就是"局部转换"：

```cpp
// 读进来 fp16
DataCopyPad(xLocal, xGm, ...);

// 累加时转 fp32（按元素转，不是整块转）
float sum = 0.f;
for (int i = 0; i < len; ++i) sum += static_cast<float>(xLocal[i]);

// 算完转回 fp16 写回
```

**他**：精度和性能的取舍怎么量化？我想给老板一个说法。

**助手**：做一张"精度-性能"曲线，比说"我们用 fp16 所以快"有说服力。

方法：

1. 同一组输入，分别跑 fp32 / fp16 / bf16 三个版本；
2. 记录：MARE、耗时、带宽利用率；
3. 画在一张图上，标注验收线。

通常会看到：

```
fp32：MARE 1e-6，耗时 100%
fp16：MARE 8e-4，耗时 60%
bf16：MARE 3e-3，耗时 58%
```

如果验收线是 1e-3，那 fp16 就是最优解（过线且最快），bf16 不够，fp32 浪费。

这张图还能回答"万一验收线收紧到 5e-4 怎么办"——你知道要付出多少性能代价。

**他**：有没有"精度预算"这种方法？我想在设计阶段就定下来。

**助手**：有，思路跟"误差传播"一样：把总误差预算分配到每一层。

```
整网允许误差 1e-2
  → 每层分配（按敏感度加权）
    → 单个算子允许 1e-3
      → 再拆到每一步：exp 5e-4、sum 3e-4、div 2e-4
```

实际操作中不需要这么精确，但**方向**要对：

- 越靠近输入的层，误差会被后面放大，要求更严；
- 越靠近输出的层，误差影响越小，可以放宽；
- 有归一化/softmax 的层，误差会被"重新缩放"，要看相对误差。

有预算之后，你在选 dtype 时就有依据，而不是"先跑跑看"。

**他**：那最后给我一个能直接用的判断流程吧。

**助手**：五步，按顺序：

```
1. 数据范围有多大？
   → 超出 fp16（±65504）或低于 1e-5：用 bf16 或 fp32

2. 有没有长序列累加？
   → 有：累加器必须 fp32，存储可以 fp16

3. 下游是不是敏感算子（softmax/layernorm）？
   → 是：提高一档精度，或加误差预算

4. 先按 fp16 跑，看验收指标
   → 过：用 fp16
   → 不过：定位是哪一步超的（分段打印）

5. 定位到累加/除法 → 局部转 fp32；定位到范围 → 换 bf16
```

核心原则：**能用 fp16 就用 fp16，把 fp32 留给"真正需要它的那几步"**。全局 fp32 是最省事的偷懒，也是最容易在性能上吃亏的选择。

## 15. 评审被问住：为什么不能像 CUDA 一个 kernel 搞定

**他**：方案评审被问"为什么非要 host tiling + kernel 两段，不能像 CUDA 一样一个 kernel 里切分"。我当时答"文档就这么写的"，被追问就没词了。

**助手**：这个问题确实值得答清楚，因为它是**编程模型层面**的差异，不是风格问题。

核心原因三条，每条都是硬约束：

**1. AI Core 没有线程抽象，不能动态扩并行。**
CUDA 里你在 kernel 里 `if (threadIdx.x < n)` 就能控制并行度，因为线程数是启动参数，block 内部还能再分层。Ascend C 的并行度在 **kernel 启动时**就定了（`blockDim`），kernel 内部没有"再启动更多并行"的手段。所以"怎么分"必须提前算好。

**2. 片上存储很小，且必须显式管理。**
UB 是百 KB 级，不是"自动缓存"。一块 tile 放多少、开几个 buffer、什么时候搬，全部要提前规划。这个规划需要知道 shape、dtype、对齐，这些信息在 host 侧最全。

**3. kernel 二进制静态展开。**
循环次数、buffer 数量在编译期确定，运行期不能"按需申请"。所以 tiling 参数必须是"数据"，从 host 传进来，而不是 kernel 里现算。

合起来就是：**kernel 只负责"按给定的切分执行"，不负责"决定怎么切"**。这个分工在 CUDA 里是隐式的（硬件和编译器帮你做了），在 Ascend C 里是显式的。

**他**：那 Scalar 是干嘛的？我看它性能很差，为什么不干脆去掉。

**助手**：因为它干的是**控制流**，不是数据并行，这两类工作没法用同一个单元做。

Scalar 负责：

- 算地址（基址 + 偏移 + stride）
- 判断边界（是不是最后一块、要不要走尾块分支）
- 控制循环（搬几块、算几轮）
- 发指令（什么时候启动 MTE，什么时候启动 Vector）

这些都是"决定做什么"，而 Vector/Cube 是"做"。打个比方：Vector/Cube 是工人，Scalar 是工头。工头不搬砖，但没有他，工人不知道下一车砖从哪来。

所以优化 kernel 有一条重要经验：**减少 Scalar 的工作量**。具体做法：

- 别在循环里做逐元素的标量运算（能向量化就向量化）；
- 地址用增量算，不要每次重算；
- 循环适当展开，减少分支判断。

Scalar 一旦成为瓶颈，表现是"各单元利用率都不高，但就是快不起来"。

**他**：Cube 和 Vector 能同时跑吗？

**助手**：能，它们是**独立的流水**，硬件上可以并行推进。

```
MTE2（搬入） ──┐
V    （向量） ──┼── 三条流水同时推进
MTE3（搬出） ──┘
Cube （矩阵） ──   与 V 独立
```

但"能并行"不等于"会自动并行"。要真正重叠，需要满足：

1. **没有数据依赖**：Cube 的输出不被当前 Vector 任务依赖；
2. **buffer 分开**：Cube 用 L0A/L0B/L0C，Vector 用 UB，别抢同一块；
3. **同步点合适**：用事件精确同步，别用 `PIPE_ALL` 一刀切。

**他**：可我写的 kernel 里它们看起来像串行的。

**助手**：大概率是这两个原因之一：

**1. 有依赖，但你没意识到。**
比如 Cube 算完写到 GM，Vector 再从 GM 读回来——中间隔了一次 GM 往返，天然串行。

**2. 同步写得太粗。**
如果你在每个阶段之间都插了 `PipeBarrier<PIPE_ALL>`，那就等于强制串行。调试时这么写没问题，性能敏感时必须换成精确事件。

判断方法：看 profiling 里的流水图。如果两条流水的"忙"区间完全不重叠，就是串行了；如果只是部分重叠，说明同步点还可以再优化。

**他**：UB 和 L1 是什么关系？我老看到 L0A、L0B、L0C。

**助手**：一张图能说清：

```
GM（HBM，大而慢）
 └─ L1（片上缓存，存矩阵块）
     ├─ L0A  ← Cube 的左输入
     ├─ L0B  ← Cube 的右输入
     └─ L0C  ← Cube 的输出（常驻累加）
UB（另一块独立的片上空间，Vector 的工作区）
```

关键区别：**UB 和 L1 是两块不同的片上空间**，不是包含关系。

| | 服务对象 | 谁在用 |
|---|---|---|
| UB | Vector / Scalar | elementwise、reduce、softmax |
| L1 / L0 | Cube | Matmul、卷积 |

所以你写 elementwise 基本只碰 UB；写 Matmul 才需要管 L1/L0 的搬运。两者不要混着理解。

**他**：那为什么不能把 L1 和 UB 合并？

**助手**：这个我只能讲到"设计取舍"这一层，具体的微架构原因要看官方架构文档。

从外部能观察到的取舍是：Cube 和 Vector 的访问模式差别很大——Cube 需要大块、规整、可复用的矩阵块；Vector 需要灵活的、逐元素的访问。如果合成一块，两者会争抢同一份带宽和容量，反而都变慢。

至于"为什么是这样划分、容量怎么定的"，属于硬件设计细节，我不掌握，建议查对应芯片的架构白皮书。

**他**：行。那图模式和单算子模式，对我的写法有影响吗？

**助手**：**对 kernel 写法没影响，对性能表现有影响。**

| | 单算子模式 | 图模式 |
|---|---|---|
| 调用 | 直接调 aclnn，一个算子一次下发 | 整图编译，GE 调度 |
| 优化空间 | 单算子内部 | 跨算子融合、内存复用、并行编排 |
| 适合 | 调试、单点验证 | 整网推理/训练 |
| 调试难度 | 低（能单独跑） | 高（要拆图定位） |

实用建议：**先在单算子模式下把 kernel 调对、调快，再放进图里**。

原因：图模式下如果性能不对，你很难判断是"算子本身慢"还是"调度/融合没做好"。先有单算子的基线，才有对比。

**他**：aclnn、aclop、GE 这三个我一直分不清。

**助手**：按调用层次，从下往上：

```
业务代码
  ├─ aclnn    单算子 C API（推荐）。两段式：GetWorkspaceSize + Execute
  ├─ aclop    老一代单算子接口，逐步被 aclnn 取代
  └─ GE       图引擎。接图、做融合/调度，最终也落到算子实现
       └─ OPP  算子库（内置算子 + 自定义算子 vendor）
            └─ kernel  真正跑在 AI Core 上的代码
```

一句话记：**GE 管"多个算子怎么排"，aclnn 管"一个算子怎么调"，OPP 是仓库，kernel 是货。**

你写算子时接触的是 kernel；给别人用时，对方接触的是 aclnn（或图）。

**他**：那什么算子该用高阶 API？

**助手**：原则：**能用就用，除非有明确理由不用**。

| 情况 | 选择 | 原因 |
|---|---|---|
| 标准形态（Matmul、Softmax、LayerNorm、Gelu） | 高阶 API | 省掉 tiling、流水、精度的坑，性能通常也更好 |
| 自定义融合（bias+激活+量化） | 基础 API 手写 | 高阶 API 覆盖不到 |
| 极限优化 | 先高阶，profiling 证明是瓶颈后再下沉 | 避免过早优化 |

反模式很常见：一上来就手写全套流水（CopyIn/Compute/CopyOut + 手写同步），最后在同步和精度上耗掉几周，而高阶 API 可能一天就到位。

正确顺序是：**高阶 API 拿基线 → 有明确瓶颈 → 再下沉**。

**他**：那我要是给组里讲这一套，按什么顺序讲比较好？

**助手**：五段，每段配一个"可验证的产出"，别只讲概念：

| 段 | 讲什么 | 验证标准 |
|---|---|---|
| 1 | 架构与编程模型 | 能画出去 host/kernel 分工图，并解释"为什么不能一个 kernel" |
| 2 | 跑通一个样例 | 改一个参数能看到效果变化 |
| 3 | 写 elementwise + reduce | 非对齐 shape（1000、1023）也能过 |
| 4 | 排一次故障 | 能独立定位一次偶发错 + 一次精度差 |
| 5 | 高阶 API 与融合 | 能把两个算子融合并说明收益 |

最容易跳过、也最该补的是**第 4 段**。大部分人卡在"能跑通但不能交付"，缺的不是 API 知识，而是调试方法论——而这一块恰恰是最难自学的。

**他**：行，我把这页补到方案里，顺便把"为什么不是 CUDA 那套"单独画一页。

**助手**：画的时候建议加一句对比，能直接堵住追问：

> CUDA 的并行度是"线程数"，由硬件调度器动态分配；Ascend 的并行度是"核数 × 指令 lane"，在启动时确定。前者灵活但有调度开销，后者固定但可以精确编排流水。tiling 就是把"编排"这件事提前到 host 侧完成。

这句话基本能解释"为什么不能一个 kernel 搞定"，也解释了"为什么 Ascend 的代码看起来更啰嗦"。
