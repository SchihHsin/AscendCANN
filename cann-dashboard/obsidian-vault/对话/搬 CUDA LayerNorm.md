# 搬 CUDA LayerNorm

> 迁移 · 共 10 轮

## 第 1 轮

**他**：老模型要迁，里面有我之前写的 CUDA LayerNorm：block 内 blockReduce，__syncthreads 很密。想直接搬过来。

**助手**：先给结论：别逐行翻译，按数据流重写。CUDA 的并行是"线程级"，Ascend C 是"核 + 指令级"，没有一一对应关系，硬翻译会得到一份能跑但很慢的代码。 映射关系先建立起来： 最重要的一条：CUDA 里你操心"哪个线程算哪个元素"，Ascend C 里你操心"哪个核处理哪块数据，块内怎么用向量指令铺开"。抽象层级变了。

## 第 2 轮

**他**：shared memory 那块我最不放心。UB 到底多大？我按多大来切行？

**助手**：别按固定数字切，按接口取实际值，再留余量。 为什么不能写死：不同芯片型号的 UB 大小差异很大（百 KB 级），而且同一个芯片上，你也不是全部都能用—— 队列：TQue 的 buffer 占一块； 临时区：fp32 累加、Cast 中转； 对齐 padding：按 32B 向上取整； 框架自身：TPipe 管理结构。 经验上按 70%–80% 估可用空间比较稳。 对你这个 LayerNorm，UB 预算大致是： 先按这个算，跑起来再看 msprof 里的实际占用。

**他**：那我先按 N ≤ 4096 常驻 UB 写，超过就走两遍，行不行？

## 第 4 轮

**他**：对了，我原来 __syncthreads 是在做跨 warp 的规约。现在换成 Reduce API，但我这个规约是跨行的，不是一个 tile 内。

**助手**：那就不能直接用"核内归约"了，得按轴重新设计。 先明确你的数据布局： 如果规约是行内（沿列方向）：每行独立，一个核处理一行或几行，用核内 ReduceSum 就够，不需要跨核同步。 如果规约是跨行（沿行方向，比如按列求 mean）：数据天然被行切分到不同核上，就必须走： 这跟你 CUDA 里的 blockReduce 是同一个思路，只是"线程树形归约"换成了"核 + workspace"。 判断方法：看输出 shape 比输入少哪一维。少的是列 → 行内规约；少的是行 → 跨行规约。

## 第 5 轮

**他**：骨架跑通了，但比 CUDA 慢两倍。

**助手**：先别急着优化算法，按这个顺序查三个数： 1. blockDim 用了几个核。 如果只用了 4 个，而机器有 20+ 核，那就是并行度不足，先加核。 2. 是不是每行读了两遍 GM。 LayerNorm 天然需要"先算统计量、再归一化"，如果整行放不进 UB，就要读两遍。这是固有成本。 3. 有没有开双缓冲。 队列深度 1 的话，搬运和计算完全串行。 CUDA 版本能"一遍过"，是因为数据在 shared memory 里——但 shared memory 只有几十 KB，你的 N 如果超过它，CUDA 版本其实也会退化成两遍。

## 第 6 轮

**他**：blockDim 我设的 4。改到 20 好一些，但还是慢。

**助手**：加核有效说明并行度确实是问题之一。剩下的慢，大概率是"两遍读 GM"。 算一笔账：假设 N=8192、fp16，一行 16KB。 两遍读：读 16KB × 2 + 写 16KB = 48KB 一遍读（常驻）：读 16KB + 写 16KB = 32KB 差了 1.5 倍。这跟你观察到的"慢两倍"量级对得上（还有一部分是启动开销）。 所以下一步是尽量让整行常驻 UB：

## 第 7 轮

**他**：改成常驻之后快了不少，但 UB 有点紧。我再加一个算子就放不下了。

**助手**：那就把阈值调低，做动态分档，而不是"能常驻就常驻"。 三个配套建议： 常驻路径要留够余量，别卡着 100% 用，否则加一个 buffer 就崩； 两遍路径也要优化（tile 大一点、双缓冲），别让它成为"慢但没人管"的分支； 阈值写进日志，跑的时候打出来，方便定位"为什么这个 shape 走了慢路径"。

## 第 8 轮

**他**：迁完精度差 1e-3。CUDA 那边是 fp32 累加的。

**助手**：那 Ascend 这边也必须 fp32 累加。这是最常见的差异源，先对齐它。 然后按顺序检查四项： 1. 累加器类型 2. eps 是否一致 两边 1/sqrt(var + eps) 的 eps 不同，结果会系统性偏移。CUDA 常用 1e-5 或 1e-6，确认 Ascend 这边是同一个值。 3. 中间量有没有偷偷降精度 比如 mean 算完存成 half，再参与 x - mean，前面的 fp32 就白做了。 4. 有没有 fast math CUDA 的 --use_fast_math 会把 sqrt、div 换成近似指令；Ascend 侧如果也开了类似选项，两边结果就不一致。要么都开，要么都关。 对比方法：打中间量，逐段比。 和 CUDA 版本同一组输入的结果对一下，哪一步开始分叉，问题就在那一步。

## 第 9 轮

**他**：找到问题了，我第二遍的 x - mean 用了 fp16 的 mean。

**助手**：对，这就是"中间量降精度"，很隐蔽——因为 mean 本身是个标量，看起来"存成 fp16 省点空间"，实际上它参与整行运算，误差会扩散到每个元素。 改法很简单：mean、rstd 全程 fp32，只在最后写回时转。 注意 Adds 那一步：(x - mean) * rstd = x * rstd - mean * rstd，所以要先 Muls 再 Adds，参数是 -mean * rstd。顺序写反了会得到一个完全不同但"看起来合理"的结果。
