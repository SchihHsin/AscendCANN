# 评审被问住

> 原理 · 共 11 轮

## 第 1 轮

**他**：方案评审被问"为什么非要 host tiling + kernel 两段，不能像 CUDA 一样一个 kernel 里切分"。我当时答"文档就这么写的"，被追问就没词了。

**助手**：这个问题确实值得答清楚，因为它是编程模型层面的差异，不是风格问题。 核心原因三条，每条都是硬约束： 1. AI Core 没有线程抽象，不能动态扩并行。 CUDA 里你在 kernel 里 if (threadIdx.x < n) 就能控制并行度，因为线程数是启动参数，block 内部还能再分层。Ascend C 的并行度在 kernel 启动时就定了（blockDim），kernel 内部没有"再启动更多并行"的手段。所以"怎么分"必须提前算好。 2. 片上存储很小，且必须显式管理。 UB 是百 KB 级，不是"自动缓存"。一块 tile 放多少、开几个 buffer、什么时候搬，全部要提前规划。这个规划需要知道 shape、dtype、对齐，这些信息在 host 侧最全。 3. kernel 二进制静态展开。 循环次数、buffer 数量在编译期确定，运行期不能"按需申请"。所以 tiling 参数必须是"数据"，从 host 传进来，而不是 kernel 里现算。 合起来就是：kernel 只负责"按给定的切分执行"，不负责"决定怎么切"。这个分工在 CUDA 里是隐式的（硬件和编译器帮你做了），在 Ascend C 里是显式的。

## 第 2 轮

**他**：那 Scalar 是干嘛的？我看它性能很差，为什么不干脆去掉。

**助手**：因为它干的是控制流，不是数据并行，这两类工作没法用同一个单元做。 Scalar 负责： 算地址（基址 + 偏移 + stride） 判断边界（是不是最后一块、要不要走尾块分支） 控制循环（搬几块、算几轮） 发指令（什么时候启动 MTE，什么时候启动 Vector） 这些都是"决定做什么"，而 Vector/Cube 是"做"。打个比方：Vector/Cube 是工人，Scalar 是工头。工头不搬砖，但没有他，工人不知道下一车砖从哪来。 所以优化 kernel 有一条重要经验：减少 Scalar 的工作量。具体做法： 别在循环里做逐元素的标量运算（能向量化就向量化）； 地址用增量算，不要每次重算； 循环适当展开，减少分支判断。 Scalar 一旦成为瓶颈，表现是"各单元利用率都不高，但就是快不起来"。

## 第 3 轮

**他**：Cube 和 Vector 能同时跑吗？

**助手**：能，它们是独立的流水，硬件上可以并行推进。 但"能并行"不等于"会自动并行"。要真正重叠，需要满足： 没有数据依赖：Cube 的输出不被当前 Vector 任务依赖； buffer 分开：Cube 用 L0A/L0B/L0C，Vector 用 UB，别抢同一块； 同步点合适：用事件精确同步，别用 PIPE_ALL 一刀切。

## 第 4 轮

**他**：可我写的 kernel 里它们看起来像串行的。

**助手**：大概率是这两个原因之一： 1. 有依赖，但你没意识到。 比如 Cube 算完写到 GM，Vector 再从 GM 读回来——中间隔了一次 GM 往返，天然串行。 2. 同步写得太粗。 如果你在每个阶段之间都插了 PipeBarrier<PIPE_ALL>，那就等于强制串行。调试时这么写没问题，性能敏感时必须换成精确事件。 判断方法：看 profiling 里的流水图。如果两条流水的"忙"区间完全不重叠，就是串行了；如果只是部分重叠，说明同步点还可以再优化。

## 第 5 轮

**他**：UB 和 L1 是什么关系？我老看到 L0A、L0B、L0C。

**助手**：一张图能说清： 关键区别：UB 和 L1 是两块不同的片上空间，不是包含关系。 所以你写 elementwise 基本只碰 UB；写 Matmul 才需要管 L1/L0 的搬运。两者不要混着理解。

## 第 6 轮

**他**：那为什么不能把 L1 和 UB 合并？

**助手**：这个我只能讲到"设计取舍"这一层，具体的微架构原因要看官方架构文档。 从外部能观察到的取舍是：Cube 和 Vector 的访问模式差别很大——Cube 需要大块、规整、可复用的矩阵块；Vector 需要灵活的、逐元素的访问。如果合成一块，两者会争抢同一份带宽和容量，反而都变慢。 至于"为什么是这样划分、容量怎么定的"，属于硬件设计细节，我不掌握，建议查对应芯片的架构白皮书。

## 第 7 轮

**他**：行。那图模式和单算子模式，对我的写法有影响吗？

**助手**：对 kernel 写法没影响，对性能表现有影响。 实用建议：先在单算子模式下把 kernel 调对、调快，再放进图里。 原因：图模式下如果性能不对，你很难判断是"算子本身慢"还是"调度/融合没做好"。先有单算子的基线，才有对比。

## 第 8 轮

**他**：aclnn、aclop、GE 这三个我一直分不清。

**助手**：按调用层次，从下往上： 一句话记：GE 管"多个算子怎么排"，aclnn 管"一个算子怎么调"，OPP 是仓库，kernel 是货。 你写算子时接触的是 kernel；给别人用时，对方接触的是 aclnn（或图）。

## 第 9 轮

**他**：那什么算子该用高阶 API？

**助手**：原则：能用就用，除非有明确理由不用。 反模式很常见：一上来就手写全套流水（CopyIn/Compute/CopyOut + 手写同步），最后在同步和精度上耗掉几周，而高阶 API 可能一天就到位。 正确顺序是：高阶 API 拿基线 → 有明确瓶颈 → 再下沉。

## 第 10 轮

**他**：那我要是给组里讲这一套，按什么顺序讲比较好？

**助手**：五段，每段配一个"可验证的产出"，别只讲概念： 最容易跳过、也最该补的是第 4 段。大部分人卡在"能跑通但不能交付"，缺的不是 API 知识，而是调试方法论——而这一块恰恰是最难自学的。

## 第 11 轮

**他**：行，我把这页补到方案里，顺便把"为什么不是 CUDA 那套"单独画一页。

**助手**：画的时候建议加一句对比，能直接堵住追问： CUDA 的并行度是"线程数"，由硬件调度器动态分配；Ascend 的并行度是"核数 × 指令 lane"，在启动时确定。前者灵活但有调度开销，后者固定但可以精确编排流水。tiling 就是把"编排"这件事提前到 host 侧完成。 这句话基本能解释"为什么不能一个 kernel 搞定"，也解释了"为什么 Ascend 的代码看起来更啰嗦"。
