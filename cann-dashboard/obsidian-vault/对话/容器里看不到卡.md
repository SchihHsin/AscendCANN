# 容器里看不到卡

> 环境 · 共 11 轮

## 第 1 轮

**他**：接了图像组的预处理项目，机器是上一任留下的，8 卡 910B。CANN 我重装了一遍，npu-smi info 还是报： 是不是得重装系统？

**助手**：先别重装，这个报错我也见过不少次，八成不是系统坏了，而是设备管理通道（DCMI）没起来。 dcmi module initialize failed 的字面意思是：npu-smi 想通过 DCMI 接口去问驱动"这台机器上有几张卡"，但驱动那一侧没有响应。它不负责算力，只负责"发现和查询设备"，所以哪怕 CANN 装得完美无缺，只要这条通道不通，你看到的还是这个错。 按概率排，可能的原因有四个： 你在容器里，设备节点没映射进来（最常见，占我见过的大半） 宿主机上驱动模块没加载 设备节点在，但权限不对 驱动和固件版本错配，管理通道拒绝服务 先做三个一分钟的检查，不用改任何东西： 还有一个容易被忽略的认知点：npu-smi 属于驱动包，不属于 CANN。所以"CANN 装好了"和"npu-smi 能用"是两件独立的事——这也解释了为什么有人 CANN 都没装，npu-smi setup 照样能看到卡。

## 第 2 轮

**他**：两个都空。/dev 下一个都没有，lsmod 也没输出。那我是不是驱动没装？我直接在容器里装一遍驱动行不行？

**助手**：先回答你最后那个问题：不行，容器里装不了驱动。 原因不难理解：驱动是内核态模块（.ko），它必须加载到宿主机的内核里，而容器共享宿主内核——容器里既没有加载模块的权限，也没有对应的内核头文件。你在容器里跑 insmod 或装 .run 包，通常会看到 Operation not permitted 或者干脆没有 /lib/modules 目录。这不是权限没给够，是模型上就不成立。 所以「/dev 空 + lsmod 空」这个组合，说明问题在宿主机这一层，而不是容器里缺什么。接下来分两步： 第一步，先确认你到底在哪。 第二步，按结果分叉： 如果在容器里：/dev 空是正常现象，设备节点不会自己长出来，必须由 docker run 映射进去。往下走映射。 如果在物理机上：lsmod 里没有 davinci 相关模块，说明驱动装了但没加载（或者没装成功）。这时看 dmesg | grep -i davinci，通常能看到加载失败的原因，比如版本和内核不匹配。 先告诉我你在容器还是物理机，我们再往下走，别在这两个分支之间来回猜。

## 第 3 轮

**他**：在容器里。

**助手**：那路径就清晰了。容器里要看设备，docker run 必须满足两个条件：设备节点映射 + 驱动库挂载。少一个都不行。 一个能跑起来的最小启动命令长这样： 四个设备节点分别是什么，值得记一下，因为报错信息会拿它们做区分： 最容易漏的就是 davinci_manager——因为它不参与计算，很多人觉得"我只要算力设备就够了"，结果报出来的错误偏偏是"设备管理接口初始化失败"，看起来像环境装坏了，其实只是少了一行 --device。 至于 -v 那两个挂载，是让容器用宿主机的驱动库，而不是在镜像里再装一份。这也顺便解释了为什么镜像里不该带驱动（后面我们会聊到）。

## 第 4 轮

**他**：我 --privileged 是不是就够了？

**助手**：不够，这两个是不同层面的东西，很容易混。 --privileged 给的是权限：让容器能访问大部分设备、能改内核参数、能 mount。但它不会凭空产生设备节点——/dev 是内核的 devtmpfs，宿主机上有哪些节点，容器里才能看到哪些。你给了全部权限，但那个目录里本来就没有 davinci0，权限再大也访问不到不存在的东西。 更直白一点： --device=/dev/davinci0：把节点搬进容器（这是必须的） --privileged：让容器有资格用这个节点（这是可选的，通常用 --group-add 更精细） 所以正确顺序是"先映射，再谈权限"。你现在加了 --device 之后报 Permission denied，说明节点已经进来了，这一步是对的，问题转移到权限上了——这其实是进展，不是新问题。 顺便提醒一句：生产环境尽量不要用 --privileged，它等于把宿主机的大门敞开。用 --group-add 或者精确的 --cap-add 更合适。

## 第 5 轮

**他**：加了，报 open /dev/davinci_manager: Permission denied。另外这个 manager 是干嘛的？跟 davinci0 有什么区别？

**助手**：先说权限，再说它是干嘛的。 权限问题：这些设备节点的属组是 HwHiAiUser（有的环境是 HwHiAiUser 加 root），权限位一般是 crw-rw----。容器里默认是 root 用户，理论上能读写，但如果镜像里跑的是普通用户，就会撞上 Permission denied。 两个解法，按推荐度排： 用 --group-add 的时候注意：容器里的组名可能不存在，但组 ID 是生效的，所以用数字 ID 而不是组名。 manager 和 davinci0 的区别：这是两个不同用途的节点，不是一个东西的两个名字。 所以 npu-smi、dcmi 这类管理工具走的是 manager；而 ACL、算子、kernel 走的是 davinci0。这也解释了为什么缺 manager 时，报错是"管理接口初始化失败"而不是"设备不可用"——两个面是分开的。 顺带说一句：davinci0 后面还有 davinci1..7，对应 8 张卡。如果你只映射了 davinci0，那容器里就只能看到一张卡，npu-smi 也只显示一张。多卡场景要把需要的都映射进去，或者用 --device=/dev/davinci* 这种通配（注意 shell 展开时机，可能需要在宿主机上先展开）。

## 第 6 轮

**他**：能看到了。但 Health 是 Warning，驱动版本和板卡 Firmware 版本不一样。这个 Warning 我之前一直没管，会有事吗？

**助手**：会有事，而且这类问题最难查，因为它不立刻报错。 驱动和固件是配套发布的：驱动（内核态）和固件（跑在设备上的那层）之间有一套私有协议，版本错位时协议对不上，表现通常是"能查到卡、能跑小算子、一到重负载就超时、或者偶发设备侧异常"。你很难第一眼把它和"版本不配套"联系起来，反而会去怀疑自己的 kernel 写错了。 先看清楚现在是什么状态： -t health 的输出里通常会给具体原因（比如固件版本不匹配、温度、ECC 计数），比顶层的 Warning 有用得多。 固件的处理方式是整包刷，用配套的 .run 包，一般带 --full 参数。两个注意点： 刷之前记下当前版本号，出问题能回退； 刷固件会中断这张卡上的业务，不是热操作。 如果你是接手别人的机器，最好先去查一下这台机器的"驱动-固件-CANN"三者的配套关系表，确认目标版本，而不是直接刷到最新——最新不一定和你的 CANN 版本配套。

## 第 7 轮

**他**：晚上还有训练任务，只刷一张卡行不行？

**助手**：技术上可以，npu-smi 支持按卡操作。但我不建议，原因有三个，按严重程度排： 第一，多卡固件版本不一致，会在集合通信上出问题。 训练任务里 HCCL 做 all-reduce 时，各卡的固件协议版本不一致，轻则性能下降，重则通信超时、任务 hang 住。这种问题排查起来极痛苦，因为它只在多卡通信时出现。 第二，调度侧会困惑。 资源管理器看到 8 张卡版本不同，可能会做保守调度，或者干脆把这张卡标记成不可用——你本来只想修一张，结果整机可用卡数变了。 第三，回退更麻烦。 一张卡刷坏了，你还能单卡回退；但如果版本已经分叉，回退要重新对齐所有卡。 所以稳妥的做法是走维护窗口： 如果实在等不到窗口，至少做到"这一次把所有卡刷到同一版本"，别留下 7 张旧卡 1 张新卡的状态。

## 第 8 轮

**他**：行。对了，/var/log 下面那一堆 ascend 的日志是干嘛的？我一直没敢删。

**助手**：那是 plog，CANN 的 host 侧运行日志，可以删，但建议先别删——它是排障时最直接的一手材料。 几个关键点： 它记什么：ACL 初始化、device 打开、内存分配、算子下发、stream 同步这些 host 侧动作，以及 runtime 的错误码。你之前那些 aclrtMalloc failed、初始化 device 失败，答案基本都在这。 它不记什么：设备内部（AI Core）发生了什么。kernel 崩了、trap 了，这些在 device 侧日志里，要用 msnpureport 单独导出。这是两套日志，很多人只翻 /var/log 找不到 kernel 的崩溃，就是因为找错了地方。 怎么用：默认级别是 WARN 以上，排障时临时调高再复现一次： 能不能删：能，但建议按时间清理而不是 rm -rf。它默认会滚动，占满磁盘的情况偶尔有，特别是长时间跑训练。真要清，先 du -sh 看看是哪个子目录涨起来的，通常是 plog 或 device-*。 顺带一个经验：出问题的时候，先看时间戳。把你复现的时间点记下来，然后在日志里找那个时间窗口，比从头读快得多。

## 第 9 轮

**他**：那这些东西我每次都得手动查一遍？有没有个脚本。

**助手**：可以封一个，关键是按依赖顺序查，失败就退出——顺序错了就会在"装没装坏"上绕圈。 为什么顺序是这样：设备 → 健康 → 环境变量 → OPP → 驱动 → 编译器。前两步不通，后面全是白搭；环境变量不通，编译器一定找不到头文件。按这个顺序走，第一个 FAIL 就是根因，不用往下猜。

## 第 10 轮

**他**：我们 CI 每次拉新容器跑测试，环境老不一致，这个能放进去吗？

**助手**：能，而且强烈建议放——但要先想清楚一件事：环境其实分两半，一半跟机器走，一半跟镜像走。混在一起就永远不一致。 具体做法： 镜像 tag 带版本，比如 cann:8.x.x-910b-py3.10，禁用 latest； 容器启动脚本第一步就跑体检，失败立即 exit 1，让 CI 在"环境阶段"就红，而不是跑到第 40 个算子才挂； 把体检结果写进构建产物（env.log），出问题时不用重现就知道当时是什么环境； 驱动版本记进报告，因为同一份镜像在不同机器上行为可能不同，而这个差异只可能来自驱动。 还有一个 CI 特有的坑：并行跑多个容器抢同一张卡。体检脚本最好加一步检查卡是不是被别人占着： 否则你会得到一堆"偶发失败"，最后发现是并行任务互相干扰。

## 第 11 轮

**他**：那为什么驱动不能打进镜像，打进去不就一致了吗。

**助手**：这个想法很自然，但结论是不行，原因是架构层面的： 驱动是内核态的，容器共享宿主内核。 你在镜像里放一份 .ko，容器启动时既没有权限加载它（需要 CAP_SYS_MODULE，而且加载的是宿主内核的模块），版本也必须和宿主内核严格匹配。换句话说： 如果宿主已经装了驱动，容器里那份是多余的，还可能造成版本混乱； 如果宿主没装驱动，容器里那份也加载不了。 所以驱动只能是"宿主机的属性"，镜像能做到的只有"假设宿主有驱动，我只挂载它的用户态部分"——这就是为什么 docker run 里要 -v /usr/local/Ascend/driver。 这条边界记住了，很多问题都能自己解释： 为什么换一台机器就要重新装驱动：因为驱动跟着内核走，不跟着镜像走。 为什么同一个镜像在不同机器上表现不同：因为驱动/固件不同。 为什么 CI 要固定机器型号：因为驱动和固件没法用镜像固化。 一句话总结：内核态的东西跟机器走，用户态的东西跟镜像走。 想彻底一致，就得两边都固定——镜像固定版本，机器固定型号和驱动。 ---
