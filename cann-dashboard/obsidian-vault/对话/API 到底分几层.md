# API 到底分几层

> 概念 · 共 11 轮

## 第 1 轮

**他**：看文档的时候一会儿基础 API，一会儿高阶 API，还有语言扩展层、框架接口。这几个到底是什么关系？我该从哪一层开始写？

**助手**：四层，从"最贴近硬件"到"最贴近业务"，越往上越好用、越往下越可控： 一条经验：能用上层就别下沉。高阶 API 是"别人已经调优过的实现"，你手写大概率不会更快，但一定会更容易出错。

## 第 2 轮

**他**：语言扩展层那些下划线修饰符，到底影响什么？我看代码里到处都是。

**助手**：它们主要在标两件事：这段代码跑在哪、这个指针指向哪块内存。 几个常见修饰： 最容易犯的错是把 host 代码写进 __aicore__ 函数——比如 std::cout、printf（除非用 AscendC::printf）、new、异常。编译器可能不报错，但运行时会挂。

## 第 3 轮

**他**：基础 API 那四类（Memory / Vector / Cube / Device）怎么分？

**助手**：按"操作的是什么"分： 写一个 elementwise 算子，你基本只会碰 Memory + Vector + Device 这三类，Cube 不用管。写 Matmul 才会大量用 Cube，并且要管 L1/L0 的搬运。

## 第 4 轮

**他**：那 TQue 和 TBuf 属于哪一层？

**助手**：属于基础 API 的 Memory 类，但它们是"管理方式"，不是"搬运操作"。 三者的关系： 选型建议：默认用 TQue，需要复用同一块内存做中间计算时用 TBuf。用 TBuf 就要自己负责同步，这一点前面聊过。

## 第 5 轮

**他**：高阶 API 会不会限制优化？我总觉得用别人的封装做不了极致性能。

**助手**：会有一定限制，但大部分场景下这个限制不成立，原因有两个： 高阶 API 本身就是针对标准形态调优过的，你没那么容易超过它； "极致性能"通常来自切分和流水，而这些高阶 API 内部已经做了。 真正受限的场景是： 特殊融合：比如 bias + 激活 + 量化的组合，高阶 API 覆盖不到； 非标准 shape：某些 shape 下高阶 API 的切分不是最优； 特殊数值要求：需要自定义累加顺序或精度处理。 判断顺序：先用高阶 API 拿基线 → profiling 看差在哪 → 再有针对性地下沉。一上来就手写全套流水，通常会在同步和精度上耗掉几周，最后性能还没高阶 API 好。

## 第 6 轮

**他**：那什么情况下必须下沉到基础 API？

**助手**：五种，都是"高阶 API 表达不了"的情况： 自定义融合逻辑：多个算子的组合，没人封装过； 非标准数据布局：stride、广播方式很特殊； 需要精确控制流水：手工多级流水、跨 pipe 精细重叠； 特殊数值算法：比如 online softmax、Welford 这类增量算法； 性能瓶颈明确在高阶 API 内部：profiling 证明，并且你确认能改得更好。 反过来说，只要不属于这五类，就不要手写。

## 第 7 轮

**他**：我发现同一件事有好几种写法，比如 DataCopy 和 DataCopyPad、ReduceSum 和手写循环。这种怎么选？

**助手**：选择标准是"语义匹配度"，不是"哪个高级"。 有个实用原则：先选"能处理最坏情况"的那个（比如 DataCopyPad），跑通之后再针对热点路径换成特化版本。反过来（先特化，出问题再补）很容易漏掉边界。

## 第 8 轮

**他**：那这几层混用会有问题吗？

**助手**：语法上没问题，但要注意两个隐性冲突： 1. 同步语义不一致。 高阶 API 内部可能已经做了同步，你在外面再加一层，可能重复，也可能打乱它的流水。 2. buffer 归属冲突。 高阶 API 会用自己的一块 UB/L1，如果你在外面又申请了同名 buffer，可能超出容量。 稳妥做法：同一个函数里尽量只用一层。要混用时，先确认高阶 API 的 buffer 预算和同步行为。

## 第 9 轮

**他**：有没有一个"最小可用组合"，让我先把东西跑起来？

**助手**：有，elementwise 类算子的最小组合就这些： 这五行骨架（队列、搬运、计算、回写、核编号）覆盖了 80% 的算子。高阶 API 只是把中间那段换成一次调用。

## 第 10 轮

**他**：那我应该按什么顺序学这几层？

**助手**：从"能跑"到"能调"，四步： 别跳过第 2 步。很多人直接上高阶 API，跑通了但一出问题就抓瞎——因为不知道底层在干什么。第 2 步的意义是建立"搬运-计算-同步"的直觉。

## 第 11 轮

**他**：最后一个，实际写的时候，怎么快速判断该用哪层？

**助手**：一个决策树，从上往下问： 大部分人卡在"我是不是该手写"，其实答案多半是"不该"。先让系统跑起来，再让系统跑得快——这个顺序反过来会浪费大量时间。 ---
