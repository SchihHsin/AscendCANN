# 换了镜像编译不过

> 编译 · 共 14 轮

## 第 1 轮

**他**：新项目的镜像，msopgen gen 生成工程，bash build.sh 报：

**助手**：这个错很典型，先看一个变量： 如果它是空的，答案就有了——编译器的头文件搜索路径没建立。kernel_operator.h 是 CANN 编译器组件自带的头文件，位置大致在 $ASCEND_HOME_PATH/compiler/tikcpp/... 下面（具体路径随版本略有差异），这个路径靠 set_env.sh 注入。 顺便解释一下这个文件是干嘛的，免得下次又懵：它是 Ascend C 的"入口头文件"，里面聚合了 Kernel 侧的 API 声明（DataCopy、TQue、Pipe、各种 AscendC:: 命名空间下的东西）。所以只要它找不到，基本等于"编译器不认识 Ascend C"。 如果 ASCEND_HOME_PATH 不是空的，那就往下查两件事： 找到头文件但编译找不到 → 环境变量没传给编译进程（下一轮说） 压根没有这个文件 → 镜像里的 CANN 装得不完整，是镜像问题，不是你的工程问题

## 第 2 轮

**他**：是空的。我 source 过 set_env.sh 啊，是不是这次 CANN 装坏了？

**助手**：不是装坏了，是环境变量没有跨进程继承。这是新手最常踩、也最容易自我怀疑的一个坑。 原因很简单：source 只影响当前这个 shell 进程。而你跑编译的时候，可能是： 另一个终端窗口（各自独立） IDE 的内置终端（可能是另一套 shell 初始化） bash build.sh 起的子进程——子进程能继承父进程的环境，但如果父进程自己没 source，子进程也没有 CI 里的非交互 shell（.bashrc 可能压根不执行） 所以"我明明 source 过"和"编译时没有"可以同时成立。 三个层次的解法，按场景选： 验证是否真的生效，别只看 echo： 如果你在 IDE 里，还要单独确认 IDE 的终端用的是哪个 shell、加载了哪个 rc 文件。

## 第 3 轮

**他**：好。不过我先干了个事：把 include 改成绝对路径了，能编过。这样行吗？

**助手**：能编过，但建议改回去，这是个会给自己埋雷的做法。 绝对路径的问题不在"现在能不能跑"，而在： 换机器就废：CANN 装在 /usr/local/Ascend 是默认，但不是必然，容器里可能在 /home/xxx/Ascend； 换版本就废：不同 CANN 版本的头文件路径结构会调整； 团队协作失效：你的路径别人没有，代码一提交，别人全编不过； 掩盖了真正的问题：真正的问题是环境变量没传递，你只是绕过了它，下次换个子进程还会中招。 正确的做法是先解决环境变量，然后保持 #include "kernel_operator.h" 不变。如果确实需要兼容多种安装位置，应该用构建系统传路径，而不是写死： 这样路径来自环境变量，换机器只要环境对就能编。

## 第 4 轮

**他**：改回来变 undefined reference to 'AscendC::...' 了。这跟前面那个有关系吗？

**助手**：有间接关系，但不是同一个问题——你现在从"编译期"走到了"链接期"，这说明头文件找到了、语法过了，但符号没生成或者没链接上。 undefined reference 的典型原因：kernel 源码被当成普通 C++ 编了。 Ascend C 的工程是两套编译器在干活： 如果 CMake 里把 *_kernel.cpp 错放进了 host 目标，g++ 会用系统 ABI 去编它——语法能过（头文件里有声明），但 AscendC:: 那些函数只有 ccec 才能生成实现，链接时自然找不到。 判断方法：看编译命令行。 命令行里带 --cce-aicore-arch=dav-2201 这类参数的，是 ascendc 编译器；只有常规 -I/-O2/-std= 的，是 g++。然后对照文件名，看该在 ccec 组的文件是不是跑到 g++ 组去了。

## 第 5 轮

**他**：等等，我 CMakeLists 里怎么知道哪个文件该给谁编？

**助手**：一般不用你手动指定——msopgen 生成的模板里已经按目录和文件名约定好了，你要做的是别破坏这个约定。 约定大致是： 几个实操要点： 文件别乱挪。有人习惯把工具函数抽到 utils.cpp 放根目录，结果它被默认归到 host 组，kernel 里引用就链接不上。共用代码要么放头文件（inline），要么明确加到 kernel 目标里。 看构建脚本怎么收集文件。模板里一般是 file(GLOB ...) 按目录收集，所以"目录即归属"。 改完 CMakeLists 一定要重新 configure，GLOB 是不会自动感知新文件的： 确认产物形态：kernel 侧最终应该产出 .o（device 二进制），host 侧产出 .so 或可执行。如果 build/ 里只有一个 .so 而没有 kernel 的 .o，说明 kernel 压根没被 ccec 编。

## 第 6 轮

**他**：我发现 ccec 报错信息特别难读，一堆模板，是我用法不对吗？

**助手**：不是你用法的问题，是模板 + 宏展开的固有代价，Ascend C 的 API 大量用了模板和宏（TQue<QuePosition::VECIN, 2>、GET_TILING_DATA 这类），编译器把展开后的类型原样打出来，可读性就很差。 几个实用技巧： 1. 只看第一条 error。 后面 90% 是级联——一个类型推不出来，后面全是"无法匹配"。找到第一条，通常就够定位了。 2. 看 error 里的"最后一行"。 模板报错是嵌套的，真正的类型不匹配往往在最后一层： 最后那句 could not match ... against ... 才是真相。 3. 类型问题先怀疑 dtype。 Ascend C 的 API 是强类型的，half 和 float 的 LocalTensor 不能混用，T 模板参数和实际数据不一致就会报一屏。 4. 缩小到最小复现。 把报错那段单独抽到一个直调工程里，编一次，比在大工程里改快得多。 5. 用 -Wall 之外别再加花活。 有些团队开一堆 -Werror，模板警告直接变错误，反而挡住真正的 error。

## 第 7 轮

**他**：编过了。顺嘴问一句，我算子叫 AddCustom，会不会跟内置 Add 撞？

**助手**：AddCustom 和 Add 不撞，但这个问题问得对——算子类型名是全局唯一的注册键，撞了是真会出事的。 撞了会怎样，比报错更麻烦： 注册被覆盖：后注册的赢，你以为在跑自己的实现，其实是别人的； 运行时查到内置实现：aclnn 或图引擎按名字找算子，找到的是内置那个，你的自定义实现永远不会被调用； 现象：结果"看起来对"（因为内置也是对的），但你改的代码没生效，白白 debug 半天。 最容易踩的是直接叫 Add、Mul、Softmax、LayerNorm 这种通用名。 规范做法： 加团队/项目前缀：MyAddCustom、xxAddV2； 三处保持一致：算子原型注册（REG_OP）、aclnn 接口名、Python 封装名。只改一处会出现"能编能装但调不到"； 查一下现状：

## 第 8 轮

**他**：那会不会有人已经注册过 AddCustom？我在这个镜像里。

**助手**：有可能，尤其是在共享镜像里——别人装过的算子包会留在 vendors/ 目录下，重启不消失。 查两个地方： config.ini 里的 load_priority 决定了加载顺序，同名时优先级高的赢——这意味着即使你装了，也可能被别人的覆盖。这种问题不会报错，只会"行为很奇怪"。 工程上的建议：镜像里别混装多个团队的自定义算子包。要么每个项目独立镜像，要么用 --install-path 装到项目自己的目录，不要都往默认路径塞。

## 第 9 轮

**他**：装完了，但调用时说算子不存在。

**助手**：装成功和能被找到，是两个阶段。按顺序查三层： 三层的含义不一样： 第一层缺失：装到了别的路径，config.ini 里根本没有你的 vendor； 第二层缺失：装了但没注册到 OPP，通常是 --install 时路径不对； 第三层缺失：库在但没导出符号，通常是编译目标不对（比如编了 host 没编 kernel）。

## 第 10 轮

**他**：没有。

**助手**：那基本可以确定是"装到别处去了"。 .run 包的默认行为是装到当前用户目录（~/Ascend/...），而你的 ASCEND_OPP_PATH 通常指向 /usr/local/Ascend/...——两个路径看起来很像，其实不是一个地方。很多人第一次装完就懵在这。 明确指定路径重装： 装完必须重新 source，因为环境变量里缓存了路径。然后验证： 还有一个容器场景的坑：在容器里装、在宿主机上用（或者反过来）。两边路径字符串一样，但文件系统不同，你以为装了，其实装在了另一侧。

## 第 11 轮

**他**：每次改一行都要重装一遍，太烦了。能不能不装直接跑？

**助手**：能，而且这是我更推荐的工作流——先用直调跑通逻辑，再打包成算子包。 直调（direct launch）的意思是：写一个普通的 main.cpp，像 CUDA 那样用 <<<>>> 直接调 kernel，完全跳过算子原型、tiling 注册、OPP 安装这一整套。 好处： 一次编译一次运行，几秒钟一轮，不用等打包安装； 可以开 CPU 调试（ASCENDC_CPU_DEBUG），先在仿真上跑逻辑； 参数是你自己传的，排障时能精确控制每一维。 代价：直调不经过 OPP，所以验证不了注册、tiling 下发、aclnn 接口这些东西。这就是为什么它只能做"前半程"，最终还是得打包验证一次。

## 第 12 轮

**他**：直调是对的，装完就偏。

**助手**：那问题基本锁定在"参数"而不是"kernel 代码"上——同一份 kernel，直调对、打包偏，说明输入不一样。按概率排： 1. tiling 参数不同（最常见） 直调里 totalLength 是你手填的；打包后由 host 的 tiling 函数算出来。如果 tiling 里算错了（尤其是尾块、对齐、tileNum），kernel 拿到的切分就是错的。 2. dtype / shape 不一致 直调你可能用 fp32 测的，aclnn 那边传的是 fp16；或者 shape 维度顺序不一样。 3. blockDim 不同 直调时你可能写死 1，只验证了单核；打包后按 shape 算了多核。 4. 内存分配方式不同 直调你自己 malloc，打包后由框架分配，对齐和大小可能不同。 最快的定位方法：在 kernel 入口打日志，两边对比。 两边都打，一比就知道是哪一维对不上。

## 第 13 轮

**他**：找到了，tiling 里 tail 没算对。

**助手**：那就是典型的"直调掩盖了 tiling bug"——因为直调里 tail 是你手算的，绕过了 host 那段代码。 修的方向：tiling 里把 total 对 blockDim 取余，余数摊到前几个核，并且把 start/len 一起写进 TilingData，让 kernel 不用再算一遍。同一个分布式逻辑写两遍，必然有一遍会错。 顺便建议：tiling 单独写单测。它不依赖 NPU，纯 CPU 就能测： 这个测试比在真机上跑快一百倍，而且能覆盖 1、1000、1023 这类边界。

## 第 14 轮

**他**：行，我先把这六步记下来。

**助手**：给你一条完整的链路，以后照着走，每一步都有"可验证的产物"： 每步的"检查点"： 口诀：头文件找不到看环境变量，符号找不到看 CMake，装完找不到看 config.ini，结果不对看 tiling。 ---
