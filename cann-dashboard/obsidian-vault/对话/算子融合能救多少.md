# 算子融合能救多少

> 架构 · 共 11 轮

## 第 1 轮

**他**：单算子我都调过了，每个看着都还行。但整网还是慢，同事说要做算子融合。融合到底能救多少？值不值得投入？

**助手**：能救多少，取决于你的瓶颈在哪。先把融合的收益拆开，你才能判断值不值： 判断方法很简单：算一下"融合能省掉多少次 GM 读写"。 比如 LayerNorm → Gelu → Add： 理论上省掉 2/3 的访存。如果你的算子链是 memory bound，收益就接近这个数；如果是 compute bound，收益就小得多。

## 第 2 轮

**他**：那什么样的算子适合融合？

**助手**：三类最适合，按收益排序： 1. elementwise 链（scale → relu → add → mul） 最适合。它们都是"读一块、算一下、写一块"，融合后中间结果完全不用落 GM。而且 UB 占用可控（同一块 tile 反复用）。 2. reduce/normalize + elementwise（softmax → dropout，layernorm → gelu） 收益也大，因为中间结果通常比输入还大（比如 softmax 的输出和输入同尺寸）。但要注意：这类算子往往需要多遍遍历，融合后 UB 压力会上升。 3. matmul + 激活/bias（matmul → bias → gelu） 收益中等。Cube 算完的结果直接留在 L0C 或 UB，交给 Vector 处理，省一次 GM 往返。但 Cube 和 Vector 的 buffer 是分开的，搬运路径要设计好。 不适合融合的： 两个 compute-bound 的算子（融合后还是 compute bound，省不了多少）； 中间结果特别大的（UB 放不下，被迫落 GM，等于没融）； 有严格数值顺序要求的（融合可能改变累加顺序）。

## 第 3 轮

**他**：Ascend 上做融合有什么限制？我听说 UB 是瓶颈。

**助手**：主要三个限制，都跟"中间结果放哪"有关： 1. UB 容量。 融合意味着中间结果要留在片上。如果中间 tensor 比输入还大（比如 softmax 的中间结果），UB 很可能放不下。 粗算： 超过 70% 就要警惕。 2. Cube / Vector 的 buffer 是分开的。 matmul 的输出在 L0C，Vector 在 UB，中间要搬一次。这个搬运省不掉，只是从"GM 往返"变成"片上搬运"，快很多但不是零成本。 3. 同步更复杂。 融合后流水更长（搬入 → 计算 A → 计算 B → 搬出），任何一处同步写错，都会表现为"偶发错"。

## 第 4 轮

**他**：图模式的融合是自动的吗？我是不是什么都不用做？

**助手**：GE 会做一部分自动融合（比如相邻的 elementwise），但不是所有融合都能自动完成，尤其是： 需要改变数据布局的融合； 跨 kernel 的中间结果复用； 需要手工编排流水的融合。 所以现实是：自动融合能拿到一部分收益，剩下的要靠人写融合算子。 判断方法：先看 GE 的图优化日志/融合后的图结构，确认哪些已经被融合了，再决定手写哪些。别上来就手写一个大融合 kernel——很可能 GE 已经做了，你只是把它拆得更碎。

## 第 5 轮

**他**：融合之后怎么调？一个大 kernel，出了问题很难定位。

**助手**：两个手段，配合用： 1. 拆开对比。 保留未融合版本，两个都跑，对比： 总耗时差多少（确认收益）； 逐段耗时（确认瓶颈）。 2. 分段打点。 在融合 kernel 内部，用 AscendC::printf 或者 profiling 的 marker 打时间戳，看每一段花了多少。 更实用的做法是：先写未融合版本，跑通、跑对、拿到基线，再写融合版本。这样你永远有一个"正确但慢"的参照物。直接写融合版本，出了问题你都不知道是"融合的 bug"还是"原始逻辑的 bug"。

## 第 6 轮

**他**：融合会不会反而更慢？我见过有人融合完性能下降的。

**助手**：会，三种典型情况： 1. UB 超限导致退化。 为了融合，tile 被迫变小，搬运次数变多，抵消了省下的 GM 往返。 2. 并行度下降。 融合后一个大 kernel 占满所有核，但每个核的活变少了，尾块浪费增加。 3. 同步开销。 融合后流水更长，同步点更多，如果写得不够精细，反而串行。 判断标准：融合后的 GM 访问量减少了吗？ 如果没减少（比如中间结果还是落 GM 了），那融合就没有意义，只是在增加复杂度。

## 第 7 轮

**他**：那什么情况下应该拆 kernel，而不是融合？

**助手**：四种情况，都是"融合的代价大于收益"： 中间结果 UB 放不下：被迫落 GM，融合等于白做； Cube/Vector 配比差异大：一个阶段 Cube 忙、Vector 闲，另一个反过来，拆开可以让不同 kernel 用不同核数； 可调试性优先：线上出问题时，拆开的版本更容易定位； 复用性：某些中间算子被多处调用，融合进去就不好复用了。 一句话：融合是为了省访存，不是为了少写代码。省不了访存就别融合。

## 第 8 轮

**他**：那怎么估算融合收益？我想要一个能说服人的数字。

**助手**：用"访存字节数"估算，比拍脑袋靠谱： 以 x → LN → Gelu → y、shape {1024, 4096}、fp16 为例： 省 50%。如果这个算子是 memory bound（大概率是），理论加速接近 2 倍；实际因为同步、启动开销，能拿到 1.3–1.6 倍就不错。 这个估算可以直接写进方案里，比"感觉会快"有说服力。

## 第 9 轮

**他**：融合的时候会做 in-place 复用 buffer，这个有风险吗？

**助手**：有，而且是最容易踩的坑之一。 风险来源：输入和输出共用同一块 buffer 时，如果计算顺序不当，会"算到一半把输入覆盖了"。 比如： 安全前提：每个元素只依赖自己（纯 elementwise），或者依赖的数据已经用完。 实践建议： 不确定时别 in-place，多占一块 buffer 换正确性； 必须复用时，明确写出"为什么安全"（比如"这里每个元素只读自己"）； 加断言/单测：用特殊输入（递增序列）检查输出有没有被污染。

**他**：行，那我该按什么顺序推进？先融合还是先调单算子？

**助手**：先单算子，后融合。理由： 单算子是融合的基础：每个都调对了，融合才有意义； 基线很重要：融合后的收益要跟"未融合"比，没有基线就说不清； 定位更容易：融合出问题时，可以对比未融合版本，快速判断是哪一段。 具体节奏：
